# Считаем текучесть одним запросом

В первом модуле вы посчитали текучесть «Ромашки» за 2025 год: 23 увольнения, среднесписочная численность 119,6, итог 19,2 %. Тогда числа были даны в тексте. Теперь у вас есть всё, чтобы получить их из базы самостоятельно — одним запросом, который можно перезапустить в январе и получить свежую цифру без единого ручного шага. Это и есть момент, ради которого модуль затевался.

## Раскладываем метрику на шаги

Формула текучести — дробь: увольнения за период делить на среднюю численность, умножить на 100. Значит, запрос — это CTE с шагами: «числитель», «знаменатель», деление.

Числитель вы уже писали не раз: `count(*)` по `terminations` с BETWEEN по 2025 году.

Знаменатель интереснее. Численность на дату D — по соглашению курса — это сотрудники, у которых `hire_date <= D` и (`termination_date` пуста или `>= D`). «Взрослый» расчёт среднесписочной перебирает так все 12 концов месяцев:

```sql
select round(avg(cnt), 1)
from (
  select (m + interval '1 month' - interval '1 day')::date as konec_mesyaca,
         (select count(*) from employees
           where hire_date <= (m + interval '1 month' - interval '1 day')::date
             and (termination_date is null
                  or termination_date >= (m + interval '1 month' - interval '1 day')::date)) as cnt
  from generate_series(date '2025-01-01', date '2025-12-01', interval '1 month') as m
) t;
```

Он возвращает те самые 119,6. Показываю его, чтобы вы узнали приём при встрече: `generate_series` генерирует ряд дат — по строке на месяц. Сама генерация рядов — за рамками курса, писать такое от вас не потребуется.

Для практики возьмём честное упрощение: **среднесписочная ≈ (численность на 1 января 2025 + численность на 31 декабря 2025) / 2**. Это две обычные проверки «кто числился на дату», без всяких рядов.

## Определение — часть метрики

С упрощённой формулой результат получится не 19,2 %, а немного другой: численность по двум точкам года — не то же, что по двенадцати. Это не ошибка, и прятать расхождение не нужно. Кто усредняет 12 месяцев — получает одно число, кто две точки — другое, и оба правы, **если подписали, как считали**. Помните из первого модуля: метрика без зафиксированного определения — просто число. Когда две цифры текучести не сходятся, первым делом сравнивают не запросы, а определения.

## Ловушка: целочисленное деление

Одна техническая засада, которая портит именно такие запросы. Поделите в SQL целое на целое:

```sql
select 23 / 118;
```

Ответ — 0. Не 0,19, а именно 0: Postgres делит целые нацело и отбрасывает остаток. А `count(*)` возвращает как раз целое, так что дробь «увольнения / численность» молча обнулится, и текучесть выйдет 0,0 % — цифра, которой позавидовал бы любой директор. Лекарство: сделать хотя бы один из операндов дробным — написать `/ 2.0` вместо `/ 2` или приписать к значению `::numeric` («считай это дробным числом»). Сравните: `23 / 118.0` даёт уже 0,1949…

Финальный штрих — `round(x, 1)`: округление до одного знака, как в отчётах модуля 1.

## Задание

Соберите текучесть 2025 года одним запросом по упрощённой формуле. Прежде чем смотреть на вердикт — прикиньте: результат должен быть близко к 19,2 %, но не равен ему. Если у вас 0,0 — перечитайте раздел про деление; если десятки тысяч процентов — проверьте, что на что делите.
