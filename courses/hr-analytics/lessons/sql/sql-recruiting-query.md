# Считаем time-to-fill и воронку

«Почему мы так долго нанимаем?» — в первом модуле вы отвечали на это готовыми числами: time-to-fill «Ромашки» за 2025 год — 44,6 дня в среднем по 26 закрытым вакансиям, а в ИТ — 91,5. Пора получить эти числа из базы самим и разрезать их по отделам.

## time-to-fill из двух дат

Срок закрытия вакансии — это просто разность дат, как в уроке про даты: `closed_on - opened_on`, результат — целое число дней. Среднее по всем закрытым в 2025 году:

```sql
select round(avg(closed_on - opened_on), 1) as srednee, count(*) as vakansiy
from vacancies
where closed_on between date '2025-01-01' and date '2025-12-31';
```

Вернётся 44,6 и 26 — сошлось с модулем 1. Обратите внимание, чем фильтруем: вакансия попадает в «закрытые за 2025» по дате **закрытия**. Отфильтруйте по `opened_on` — и получите другой набор: туда влезут открытые в 2025, но закрытые в 2026, а вакансии, открытые в декабре 2024 и закрытые в январе 2025, выпадут. Какая дата определяет период — часть определения метрики, и путаница здесь встречается в отчётах постоянно.

Разрез по отделам — это те же GROUP BY и JOIN, что вы уже собирали: название отдела из `departments`, `avg` и `count` по группе.

## Воронка найма из applications

В `applications` у каждого отклика есть `stage` — **максимальный достигнутый** этап: «отклик» значит «дальше не продвинулся», «нанят» — прошёл всё. Сгруппируем отклики по вакансиям, закрытым в 2025 году:

```sql
select a.stage, count(*)
from applications a
join vacancies v on v.id = a.vacancy_id
where v.closed_on between date '2025-01-01' and date '2025-12-31'
group by a.stage;
```

| stage | count |
|---|---|
| отклик | 263 |
| скрининг | 126 |
| интервью | 78 |
| оффер | 7 |
| нанят | 26 |

Но знакомая воронка из модуля 1 выглядела иначе: 500 → 237 → 111 → 33 → 26. Противоречия нет — это одни и те же данные, прочитанные по-разному. Воронка отвечает «сколько дошло **хотя бы до** этапа»: до скрининга дошли все, кто остановился на скрининге или прошёл дальше — 126 + 78 + 7 + 26 = 237; до интервью — 78 + 7 + 26 = 111; до оффера — 7 + 26 = 33. А GROUP BY по `stage` отвечает «сколько **остановилось на** каждом этапе». Оба ответа полезны, но в отчёт для директора идёт воронка — и теперь вы знаете, как она получается из сырых строк.

## Сортировка по номеру столбца

В отчётах по метрикам сортируют чаще всего по вычисленному столбцу — среднему, количеству. Писать выражение с `avg` второй раз в ORDER BY не нужно: Postgres разрешает сослаться на столбец по его номеру в выдаче — `order by 2 desc` значит «по второму столбцу, по убыванию». Можно и по псевдониму (`order by srednee desc`) — выберите один способ и держитесь его; номер короче, псевдоним понятнее.
