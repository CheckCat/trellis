# Схема данных «Ромашки»: семь таблиц, ключи и связи

Перед тем как писать запросы, нужно знать, *куда* их писать. В базе «Ромашки» семь таблиц — это те же данные, что вы видели в CSV-файлах модуля про Excel, но уже разложенные по правилам прошлого урока: у каждой таблицы свой смысл, у строк — ключи, между таблицами — связи. Пройдём по всем семи; к этой странице вы будете возвращаться весь модуль.

## Справочник и главная таблица

**departments** — отделы, 8 строк.

| столбец | тип | что это |
|---|---|---|
| id | число | первичный ключ |
| name | текст | название отдела |

**employees** — сотрудники, 185 строк: все, кто когда-либо работал в «Ромашке» с 2018 года, включая уже уволившихся.

| столбец | тип | что это |
|---|---|---|
| id | число | первичный ключ |
| full_name | текст | ФИО |
| sex | текст | «м» / «ж» |
| birth_date | дата | дата рождения |
| department_id | число | внешний ключ → departments.id |
| position | текст | должность |
| hire_date | дата | дата приёма |
| termination_date | дата | последний рабочий день; пусто, если работает |
| fte | число | ставка: 1.00 — полная, 0.50 — половина |

## NULL: «значения нет»

В `termination_date` у работающих сотрудников стоит особое значение — **NULL**. Это не ноль и не пустая строка, а именно *отсутствие значения*: даты увольнения нет, потому что увольнения не было. Соглашение курса: `termination_date` **NULL — сотрудник работает**; если дата есть — это его последний рабочий день (в этот день он ещё числился в компании). NULL нам будет встречаться постоянно — например, «сколько людей работает сейчас?» на языке базы значит «у скольких строк в employees нет даты увольнения».

## События: увольнения, вакансии, отклики

**terminations** — увольнения, 65 строк, по одной на событие.

| столбец | тип | что это |
|---|---|---|
| id | число | первичный ключ |
| employee_id | число | внешний ключ → employees.id |
| term_date | дата | дата увольнения (последний рабочий день) |
| reason | текст | основание: «по собственному желанию», «соглашение сторон»… |
| voluntary | булево | true — уход добровольный |

Заметьте: *дата* увольнения продублирована в employees для удобства, а вот *причина* — только здесь. Вопрос «из каких отделов уходят чаще» потребует пройти по цепочке ключей: terminations → employees → departments.

**vacancies** — вакансии, 55 строк: id, department_id (→ departments), position, opened_on — дата открытия, closed_on — дата закрытия (NULL — вакансия ещё открыта), hired_employee_id (→ employees; NULL, пока никто не нанят).

**applications** — отклики кандидатов, 1012 строк: id, vacancy_id (→ vacancies), candidate_name, source (откуда пришёл: hh.ru, реферал…), applied_on, stage — максимальный достигнутый этап: «отклик», «скрининг», «интервью», «оффер», «нанят». Это те самые данные, из которых в модуле 1 считалась воронка найма.

## История и «сырьё»

**salary_history** — история окладов, 367 строк: id, employee_id (→ employees), valid_from — с какой даты действует оклад, monthly_salary — оклад в рублях. На одного сотрудника здесь несколько строк — по одной на каждое изменение оклада; текущий оклад — тот, у которого valid_from самая поздняя.

**ats_raw** — «сырая» выгрузка из ATS, 47 строк, и это таблица-исключение: без ключей, все столбцы текстовые (fio, telefon, data_otklika, vakansiya, istochnik, etap), внутри — дубли и разнобой форматов. Она нарочно оставлена грязной: на ней в конце модуля мы будем учиться находить проблемы в данных запросами. Остальные шесть таблиц чистые.

## Как это читать целиком

Держите в голове звезду связей: в центре employees, от неё ключи ведут к departments (где человек работает), terminations (как ушёл), salary_history (сколько получал), vacancies (на какую вакансию нанят). Кандидаты живут в паре vacancies ← applications и до employees дотягиваются только через факт найма.

Со следующего урока начинаем задавать этой базе вопросы — сначала командой SELECT к одной таблице, а соединять таблицы между собой научимся в уроке про JOIN.
