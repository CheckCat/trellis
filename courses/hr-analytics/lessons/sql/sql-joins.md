# JOIN: соединяем таблицы

Из какого отдела ушло больше всего людей в 2025 году? Откройте `terminations` — там есть дата и основание, но нет ни имени человека, ни отдела: только `employee_id`. Имя лежит в `employees`, название отдела — в `departments`. Ответ на вопрос директора размазан по трём таблицам, и это не недосмотр, а устройство базы: каждая таблица хранит своё, а связывают их внешние ключи — вы видели это на схеме «Ромашки».

До сих пор каждый ваш запрос читал одну таблицу. **JOIN** — команда, которая склеивает строки двух таблиц по условию.

## Как это пишется

```sql
select e.full_name, e.position, d.name
from employees e
join departments d on d.id = e.department_id;
```

Читается так: возьми `employees`, к каждой строке подбери строку `departments`, у которой `id` равен `department_id` сотрудника, и склей их в одну широкую строку. Условие после `on` — правило подбора пары, почти всегда это «внешний ключ = первичный ключ».

Обратите внимание на буквы `e` и `d` — это **алиасы**, короткие имена таблиц на время запроса. Когда таблиц две, столбец `id` есть в обеих, и надо говорить, чей именно: `e.id` — сотрудника, `d.id` — отдела. Без алиасов запрос превращается в `employees.department_id = departments.id` — работает, но читать тяжело.

Запрос выше вернёт 185 строк — по одной на каждого сотрудника, потому что отдел нашёлся у всех.

## Цепочка соединений

Таблиц можно склеить и три, и четыре — JOIN просто пишется ещё раз. Кто из нанятых в закрытые вакансии кандидатов в какой отдел попал:

```sql
select a.candidate_name, v.position, d.name
from applications a
join vacancies v on v.id = a.vacancy_id
join departments d on d.id = v.department_id
where a.stage = 'нанят';
```

Каждый следующий `join` пристёгивается к тому, что уже склеено. Порядок чтения тот же: отклики → их вакансии → отделы вакансий, и в конце обычный `where`.

## Что теряет JOIN — и что возвращает LEFT JOIN

Теперь ловушка. Соедините сотрудников с их увольнениями:

```sql
select e.full_name, t.term_date, t.reason
from employees e
join terminations t on t.employee_id = e.id;
```

Вернётся 65 строк — а сотрудников 185. Куда делись остальные 120? У них нет записи в `terminations`: они работают. Обычный JOIN (его ещё называют внутренним, inner) оставляет **только строки, у которых пара нашлась**. Для отчёта «кто когда уволился» это правильно. Для отчёта «все сотрудники и их статус» — тихая катастрофа: работающие просто исчезнут, и запрос не скажет об этом ни слова.

Когда терять строки без пары нельзя, пишут `left join`:

```sql
select e.full_name, t.term_date, t.reason
from employees e
left join terminations t on t.employee_id = e.id;
```

Теперь строк 185: все из левой таблицы (той, что написана до `left join`) остались, а там, где пары нет, столбцы правой заполнены NULL:

| full_name | term_date | reason |
|---|---|---|
| Лебедева Юлия Борисовна | NULL | NULL |
| Филиппов Данил Игоревич | 2025-01-15 | по собственному желанию |
| Афанасьев Павел Михайлович | 2025-09-26 | по собственному желанию |

Практическое правило: перед соединением спросите себя, **кого нельзя терять**. Нужны только пары — JOIN; нужны все строки левой таблицы, даже одинокие — LEFT JOIN. Проверить себя просто: прикиньте, сколько строк ждёте, и сравните с тем, что вернулось. 185 против 65 — расхождение, которое видно сразу, если его искать.
