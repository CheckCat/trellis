# Тестирование бэкенда: пирамида, testcontainers, контрактные тесты, что мокать

Уровень 1 — закрывает эксплуатационный модуль. Ты автоматизировал
тестирование критичных сценариев на фронте — здесь серверная
специфика: настоящая база в тестах, контракты между сервисами и
дисциплина моков.

## Боль: зелёные тесты, красный прод

Сервис покрыт юнит-тестами на 90 %, всё зелёное. В проде: SQL с
опечаткой в имени колонки (репозиторий был замокан), 409 вместо
контрактного 422 (HTTP-слой не тестировался), сосед сломался от
нашего нового формата события (никто не проверял контракт). Тесты
проверяли то, что легко проверить, а не то, что ломается.

## Пирамида и её серверная поправка

Классика: много юнитов — меньше интеграционных — мало e2e (быстрое и
дешёвое внизу). Серверная поправка, которую стоит проговорить:
ценность бэкенд-кода часто **на стыках** — SQL, HTTP, сериализация,
— поэтому середина пирамиды толще, чем учит классика:
**интеграционные тесты сервиса — рабочая лошадка**. Юниты — для
логики с ветвлениями (доменные правила, наши агрегаты и лимитеры —
всё, что мы писали в практиках, тестируется юнитами идеально);
интеграционные — для стыков; e2e — несколько сквозных сценариев.

## Интеграционные тесты с настоящей базой

Мок репозитория не поймает ни опечатку в SQL, ни нарушение
уникального индекса, ни поведение `FOR UPDATE SKIP LOCKED`.
**Testcontainers** — библиотека, поднимающая настоящий Postgres (и
Redis, и Kafka) в Docker из теста: контейнер на прогон, миграции,
тесты по реальной базе, снос. Медленнее юнитов (секунды на старт),
но проверяет правду. Изоляция тестов: транзакция с откатом вокруг
каждого, либо чистка таблиц, либо схема на воркер (parallel).

HTTP-слой тестируется без сети: `app.inject()` у Fastify (и аналоги)
— запрос в приложение in-process: маршруты, валидация, формат
ошибок, коды — всё по-настоящему, быстро. (Так устроены тесты
движка, на котором ты сейчас учишься.)

## Что мокать, а что нет

Дисциплина, о которой спрашивают прямо:

- **Мокать (фейками)**: чужие сети — внешние API (провайдер SMS),
  соседние сервисы; время (внедрённые часы — вся практика курса так
  написана!); случайность; всё недетерминированное.
- **Не мокать**: свою базу (testcontainers), свой код (мок соседнего
  класса = тест мока), брокер в интеграционных (или честный фейк
  очереди в памяти с семантикой at-least-once).
- Правило: **мок — на границе процесса, у порта**. Порты и адаптеры
  из модуля архитектуры сюда и стреляют: фейк порта `EventPublisher`
  — легально; мок метода собственного сервиса — запах.
- Осторожно с «поведенческими» проверками (`verify(called with)`) —
  тесты привязываются к реализации и ломаются от рефакторинга;
  проверяй **результат и состояние**.

## Контрактные тесты

Обещанные дважды (модули API и архитектуры) — теперь механика.
Проблема: e2e со всеми сервисами разом — медленно, хрупко, никогда
не зелено. Контрактные тесты режут проверку на две половины:

- **потребитель** пишет ожидания к API провайдера (какие запросы
  шлёт, что ждёт в ответ) — из них рождается контракт (Pact — самый
  известный инструмент);
- **провайдер** прогоняет контракт против себя в своём CI: «мои
  потребители не сломаются от этого изменения».

Итог: совместимость проверяется без общего стенда, и «кто от нас
зависит и чем» записано в контрактах. Для событийных интеграций та
же идея — схемы событий в registry с проверкой совместимости
(модуль архитектуры).

Дешёвая версия без Pact: генерируемый OpenAPI сравнивается в CI на
несовместимые изменения (breaking-diff) — уже ловит переименования и
смену типов.

## Ещё три слова

- **Снапшот-тесты** ответов API — быстро фиксируют формат, но
  превращаются в «обнови снапшот» без чтения; использовать точечно.
- **Нагрузочные** — модуль про ёмкость: профиль, перцентили, точка
  насыщения; в CI — хотя бы smoke на деградацию.
- **Тестируемость — свойство дизайна**: внедрённые зависимости,
  чистые функции, порты. Код, который трудно тестировать, — сигнал о
  дизайне, и все практики этого курса написаны как раз в
  тестируемом стиле — ссылайся на них как на свой подход.

## На чём валят

- **Мок собственного репозитория в «интеграционном» тесте** — SQL не
  проверен; настоящая база в контейнере.
- **«Мокаем всё для скорости»** — тесты проверяют моки; граница мока
  — порт процесса.
- **Не знать контрактные тесты** — при опыте «мы ломали соседей
  релизами» это ожидаемый ответ.
- **Тесты, завязанные на порядок вызовов** — рефакторинг красит их в
  красный без единого бага.
- **Флаки-тесты с реальным временем** — `sleep(100)` в тесте; время
  внедряется и управляется.

## Как ответить за минуту

«Пирамида с толстой серединой: юниты — на доменную логику,
интеграционные — рабочая лошадка стыков: настоящий Postgres через
testcontainers с миграциями и изоляцией транзакцией, HTTP —
inject-ом без сети; e2e — несколько сквозных. Мокаю на границе
процесса: внешние API, время, случайность; свою базу и свой код —
нет. Совместимость между командами — контрактные тесты: потребитель
фиксирует ожидания, провайдер гоняет их в своём CI; минимум —
breaking-diff OpenAPI и схем событий. Проверяю результат, не порядок
вызовов; тестируемость закладывается дизайном — внедрёнными
зависимостями и портами».
