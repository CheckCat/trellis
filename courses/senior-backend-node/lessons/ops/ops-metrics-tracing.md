# Метрики RED и USE, гистограммы, OpenTelemetry и трейсинг

Уровень 1. Логи отвечают «что случилось с этим запросом», метрики —
«как система себя чувствует», трейсы — «где именно потерялось время».
Три столпа наблюдаемости; вопрос «какие метрики повесите на сервис»
— стандартный, и на него есть готовая рамка.

## Боль: «у нас всё зелёное», а операторы страдают

Дашборд показывает CPU и память — всё в норме. При этом p99 экрана —
семь секунд: пул соединений исчерпан (латентность растёт при
скучающей базе — помнишь картину из урока про пул?). CPU-графики не
видят страданий пользователя. Метрики нужно выбирать от того, что
болит у **потребителя**, а не от того, что легко собрать.

## RED и USE

**RED** — для каждого сервиса/эндпоинта, глазами потребителя:

- **Rate** — запросов в секунду;
- **Errors** — доля ошибок;
- **Duration** — распределение латентности (перцентили!).

**USE** — для каждого ресурса (CPU, память, диск, пул соединений,
очередь):

- **Utilization** — насколько занят;
- **Saturation** — очередь/ожидание сверх ёмкости (глубина очереди
  пула! лаг цикла событий! lag консьюмера Kafka!);
- **Errors** — ошибки ресурса.

Пара RED+USE закрывает вопрос «какие метрики»: RED говорит «болит»,
USE говорит «где». Плюс бизнес-метрики (обращений создано,
уведомлений отправлено) — по ним видно инциденты, которые техметрики
не ловят («создание обращений упало до нуля при зелёном RED» —
значит, сломались до нас).

## Типы метрик и гистограммы

- **Counter** — только растёт (запросы, ошибки); скорость роста —
  rate().
- **Gauge** — текущее значение (глубина очереди, соединения,
  память).
- **Histogram** — распределение по бакетам: latency в бакеты
  «≤50мс, ≤100, ≤200...», счётчик на бакет. Из гистограмм считаются
  перцентили **агрегируемо между инстансами** — то, чего нельзя
  сделать с готовыми перцентилями (урок про ёмкость: p99 не
  усредняется; гистограммы — складываются). Цена — заранее выбранные
  границы бакетов под ожидаемые латентности.

Стандартный стек: метрики отдаются эндпоинтом в формате Prometheus,
Prometheus собирает (pull), Grafana рисует, Alertmanager будит.

**Алёрты — по симптомам, не по причинам**: «p99 экрана больше
бюджета», «доля ошибок выше 1 %», «бюджет ошибок сгорает быстрее
нормы» (SLO из прошлого модуля — алёрт на скорость сгорания бюджета
— зрелая практика). Алёрт «CPU 80 %» будит человека, когда
пользователю, возможно, норм, — и приучает игнорировать алёрты.
Каждому алёрту — действие: алёрт без runbook-а (следующие уроки) —
шум.

## Трейсинг

Запрос прошёл BFF → cases → Postgres и customers параллельно — где
потерялись 600 мс? Логи покажут строки, но не **дерево времени**.
Трейс — это дерево спанов: у каждого — начало, длительность,
атрибуты, родитель. Waterfall-вид отвечает мгновенно: вот спан
запроса к базе на 580 мс, вот последовательные вызовы, которые
могли быть параллельными, вот N+1 — сто одинаковых спанов лесенкой
(трейс — лучший детектор N+1 в проде).

**OpenTelemetry (OTel)** — стандарт всего этого: API и SDK
инструментирования (авто-инструментация http, pg, redis, kafkajs в
Node — большая часть спанов бесплатно), **контекст**, который едет
между сервисами заголовком `traceparent` (W3C Trace Context — тот же
correlation id, но стандартизованный и с деревом), и экспорт в
бэкенды — Jaeger, Tempo, коммерческие APM. Внутри процесса контекст
живёт — угадай где — в AsyncLocalStorage.

Цена — объём: трейсить 100 % запросов дорого, поэтому
**сэмплирование** (доля запросов, или tail-based — «сохраняем только
медленные и с ошибками» — дороже, но полезнее). Связка столпов:
в логи пишется traceId — от строки лога один клик до дерева запроса.

## На чём валят

- **«Мониторим CPU и память»** — метрики потребителя (RED) первичны;
  ресурсные — для диагноза.
- **Перцентили без гистограмм** — нельзя агрегировать между
  инстансами; «как посчитаете общий p99 восьми инстансов?»
- **Алёрт на причину** («CPU высокий») вместо симптома (латентность,
  ошибки, сгорание бюджета SLO).
- **Saturation не назвать** — глубина очереди пула и лаг цикла
  событий — самые ранние индикаторы беды в Node-сервисе.
- **«Трейсинг — это дорого»** без слова «сэмплирование».

## Как ответить за минуту

«На каждый сервис — RED: rate, errors, duration гистограммой, из неё
перцентили, агрегируемые между инстансами; на каждый ресурс — USE:
утилизация, насыщение (глубина очереди пула, лаг цикла событий, lag
консьюмера), ошибки; плюс бизнес-метрики. Алёрты — по симптомам и
скорости сгорания бюджета SLO, каждый — с runbook-ом. Трейсинг —
OpenTelemetry: авто-инструментация Node, контекст traceparent между
сервисами, сэмплирование, в логах traceId — от строки до waterfall
один шаг. Логи, метрики, трейсы связаны общим id — это и есть три
столпа».
