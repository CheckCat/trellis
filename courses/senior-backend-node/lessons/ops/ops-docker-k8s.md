# Docker и Kubernetes для Node: образ, сигналы, лимиты, probes, HPA

Уровень 2. Бэкендер не обязан быть девопсом, но обязан понимать, где
живёт его процесс: половина «загадочных» прод-проблем Node — это
стык с контейнером. Всё нижнее — вопросы, которые задают
бэкендеру, а не SRE.

## Образ: Dockerfile для Node

```dockerfile
FROM node:22-alpine AS builder
WORKDIR /app
COPY package*.json ./
RUN npm ci                      # по lock-файлу, воспроизводимо
COPY . .
RUN npm run build && npm prune --omit=dev

FROM node:22-alpine
WORKDIR /app
USER node                       # не root
COPY --from=builder --chown=node:node /app/dist ./dist
COPY --from=builder --chown=node:node /app/node_modules ./node_modules
CMD ["node", "dist/main.js"]
```

Что здесь спрашивают:

- **Multi-stage**: сборка (dev-зависимости, tsc) — в первом этапе,
  в финальный образ едет только рантайм. Образ меньше — быстрее
  деплой и меньше поверхности атаки.
- **Слои и кэш**: `COPY package*.json` + `npm ci` **до** `COPY . .` —
  правка кода не инвалидирует слой с зависимостями; сборки на
  секунды, а не минуты.
- **npm ci, не install** — точно по lock-файлу.
- **USER node** — процесс не под root: сдерживание при компрометации.
- **CMD в exec-форме** (`["node", ...]`) — критично: shell-форма
  (`CMD node ...`) запускает процесс ребёнком шелла, и **сигналы до
  него не доходят**. Node — PID 1 — получает SIGTERM сам, и graceful
  shutdown из модуля рантайма работает.

## Память: два лимита, которые должны дружить

Знакомая пара из модуля Node, теперь с контейнерной стороны: лимит
контейнера (cgroup) и `--max-old-space-size`. Куча по умолчанию
может быть больше лимита контейнера — тогда процесс убивает **ядро**
(OOMKilled, exit 137), внезапно и без стектрейса, вместо аккуратного
падения V8. Правило: куча ≈ 75–80 % лимита контейнера, остальное —
буферам и рантайму. «Под рестартится с exit code 137» — вопрос с
готовым ответом: ядро прибило за память, смотри лимиты и утечки.

CPU-лимиты: жёсткий лимит (limits.cpu) включает троттлинг —
процесс «замирает» кусками, латентность прыгает при низкой средней
утилизации; частая рекомендация — requests ставить честно, с
limits.cpu быть осторожным (или не ставить), memory limits — ставить
всегда.

## Kubernetes: словарь на уровне разговора

- **Pod** — экземпляр приложения (обычно один контейнер); смертен и
  заменяем — весь stateless-разговор из модуля нагрузки про это.
- **Deployment** — «хочу N реплик такого пода»: контроллер
  поддерживает число, ведёт rolling-обновления.
- **Service** — стабильное имя и балансировка на живые поды (то самое
  service discovery через DNS).
- **Ingress** — HTTP-вход снаружи: маршрутизация, TLS.
- **ConfigMap/Secret** — конфигурация и секреты, попадают в env или
  файлы (секреты — лучше из внешнего хранилища, модуль auth).
- **HPA** — автоскейл: держит целевую утилизацию (CPU или свои
  метрики — глубина очереди!), меняя число реплик между min и max.
  Помнить: скейлится stateless; и автоскейл не спасает от ступеньки
  нагрузки быстрее, чем поднимаются поды (прогрев!).

## Probes: три вопроса к поду

- **liveness** — «жив ли процесс?» Провал → рестарт пода. Проверка —
  максимально тупая (процесс отвечает), без зависимостей: liveness,
  проверяющий базу, устраивает **рестарт-шторм** при сбое базы —
  классический анти-паттерн.
- **readiness** — «готов ли принимать трафик?» Провал → под убирают
  из балансировки (не рестартят!). Вот сюда — зависимости: пул
  соединений жив, прогрев сделан. И связка с graceful shutdown из
  модуля Node: на SIGTERM сначала валим readiness, ждём снятия с
  балансировки, потом закрываемся — иначе трафик летит в
  закрывающийся под.
- **startup** — для медленного старта: пока не пройден, liveness не
  проверяется (иначе долгий прогрев убивается рестартом до того, как
  запустился).

Rolling-деплой обвязан этим же: новый под получает трафик только
после readiness; maxUnavailable/maxSurge управляют темпом; плюс
`terminationGracePeriodSeconds` — сколько ждать graceful shutdown
до SIGKILL (те самые 30 секунд из модуля Node — согласованы с твоим
таймаутом остановки).

## На чём валят

- **CMD в shell-форме** — SIGTERM не доходит, все graceful-механизмы
  мертвы; exec-форма.
- **OOMKilled/137** — не узнать симптом «ядро прибило за память» и
  связку лимита контейнера с max-old-space-size.
- **liveness с проверкой базы** — рестарт-шторм всех подов при сбое
  зависимости; зависимости — в readiness.
- **Готовность до прогрева** — под принимает трафик с холодными
  кэшами и пустым пулом: латентность-ступенька после каждого деплоя.
- **cluster внутри пода + HPA** — двойное масштабирование; один
  процесс на под, скейлит оркестратор.

## Как ответить за минуту

«Образ: multi-stage, npm ci до копирования кода ради кэша слоёв,
не-root, CMD exec-формой — иначе SIGTERM не дойдёт и graceful
shutdown не сработает. Память: куча V8 процентов на 75–80 от лимита
контейнера, иначе OOMKilled с кодом 137 от ядра. В Kubernetes:
Deployment держит реплики, Service балансирует, HPA скейлит по
метрике. Probes: liveness тупой и без зависимостей — иначе
рестарт-шторм при сбое базы; readiness — с зависимостями и прогревом,
и на SIGTERM сначала валим его, ждём снятия трафика, потом
закрываемся в terminationGracePeriod».
