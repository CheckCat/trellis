# Фоновые задачи: BullMQ, состояния, cron, приоритеты, массовые операции

Уровень 1. Очередь событий — про «случилось»; очередь **задач** — про
«сделай». Массовые операции и регламентные выгрузки, которые ты
запускал с фронта в реальной платформе, живут ровно на этой механике
— здесь ты достраиваешь их серверную половину.

## Боль: работа длиннее запроса

Супервизор запускает переназначение 10 000 обращений уволенного
оператора. Это минуты работы: в HTTP-запросе её делать нельзя
(таймауты, повтор при обрыве, потеря при деплое). Нужны: принять
задачу, ответить сразу, выполнять в фоне с повторами, показывать
прогресс, пережить рестарт. Это и есть **фоновая задача** — и паттерн
`202 Accepted` из модуля API обретает исполнителя.

## BullMQ: устройство очереди задач на Redis

Стандарт в Node-мире. Задача (job) — запись с данными, опциями и
состоянием; воркер — процесс, который их разбирает.

**Жизненный цикл**: `waiting → active → completed | failed`, плюс
`delayed` (отложена до срока) и `waiting-children` (ждёт дочерние).
Состояния хранятся в структурах Redis — атомарность переходов даёт
Lua (всё из модуля про Redis: ZSET для отложенных, списки для
очереди).

Возможности, которые нужно уметь назвать:

- **повторы с backoff** — встроены: `attempts`, экспоненциальная
  задержка (прошлый урок — из коробки);
- **приоритеты** — важные задачи вперёд; **отложенный запуск** —
  `delay`; **повторяющиеся** — cron-выражения;
- **конкурентность воркера** — сколько задач один воркер ведёт
  параллельно (для I/O-задач — десятки);
- **rate limiting очереди** — «не больше 30 SMS в секунду» — лимит
  провайдера соблюдает очередь, а не каждый воркер по совести;
- **flows** — родительская задача с дочерними (fan-out массовой
  операции);
- **зависшие (stalled)** — воркер умер, не доложив: обнаруживаются по
  пропавшему heartbeat-у и возвращаются в очередь — снова
  at-least-once, снова идемпотентность шага.

## Длинные задачи: дисциплина

Задача на полчаса — отдельный класс проблем:

- **Прогресс** — задача пишет «обработано 3400 из 10000»
  (`job.updateProgress`), интерфейс читает по id — тот самый экран
  «выгрузка готовится», который ты делал с фронтовой стороны.
- **Чекпоинты** — большая работа режется на идемпотентные куски:
  «переназначь обращения 1–500», «501–1000»... Упавший кусок
  повторяется, готовые не трогаются. Родитель агрегирует. Правило:
  **повтор шага не должен ломать результат** — каждый шаг
  идемпотентен (уже третий раз это слово в модуле, и это не случайно).
- **Отмена** — кооперативная: флаг «отменено» в данных задачи, шаги
  проверяют его между кусками. Убить процесс воркера — не отмена:
  зависнет в stalled и перезапустится.
- **Результат** — крупный результат (файл реестра) кладётся в
  объектное хранилище, задача хранит ссылку (модуль Postgres, урок
  про выбор хранилищ).

## Планировщики: cron в распределённом мире

«Каждый день в 03:00 собрать реестр» — а инстансов три, и cron
сработает у всех. Варианты:

- **повторяющиеся задачи BullMQ** — расписание живёт в Redis одной
  записью: сработку получает один воркер; это проще всего, если
  BullMQ уже есть;
- **распределённая блокировка** вокруг запуска (модуль кэша — та
  самая регламентная выгрузка);
- **внешний планировщик** (оркестратор, k8s CronJob) — запускает
  одноразовый под;
- уникальный jobId по периоду (`registry-2026-03-07`) — дубль
  постановки схлопывается по id: идемпотентность и здесь.

Обязательные вопросы к любому расписанию: что при **пропуске** окна
(инстансы лежали в 03:00 — догонять или пропустить?) и что при
**двойном** срабатывании (ответ уже есть: идемпотентность запуска).

## Очередь задач против шины событий — окончательно

Теперь можно закрыть развилку из первого урока модуля целиком:
**команда** («переназначь», «выгрузи», «отправь») — BullMQ/RabbitMQ:
подтверждения, повторы, приоритеты, прогресс. **Факт** («обращение
создано») — Kafka: многие читатели, история, порядок по ключу.
Соблазн сделать всё на одном инструменте — источник кривых систем:
очередь задач на Kafka теряет приоритеты и честное распределение
медленных задач; шина событий на RabbitMQ — историю и replay.

## На чём валят

- **«Запустим долгую работу в setTimeout/сразу в обработчике»** —
  смерть процесса теряет работу молча; фоновая работа живёт в очереди
  с состоянием.
- **Прогресс опросом базы «сколько строк изменилось»** — прогресс —
  атрибут задачи, а не побочное вычисление.
- **Отмена = kill воркера** — задача вернётся как stalled и
  продолжится; отмена кооперативна.
- **Cron на каждом инстансе без координации** — тройной запуск
  регламентной выгрузки; блокировка, единая запись расписания или
  уникальный jobId периода.
- **Неидемпотентные шаги массовой операции** — повтор куска дублирует
  эффект; резать на идемпотентные куски — обязанность, а не
  украшение.

## Как ответить за минуту

«Фоновые задачи — BullMQ поверх Redis: состояния waiting → active →
completed/failed плюс delayed, повторы с backoff из коробки,
приоритеты, отложенные, cron, конкурентность воркера и rate limit
очереди под лимиты провайдера. Длинные операции режу на идемпотентные
чекпоинты с прогрессом в задаче, отмена кооперативная по флагу,
крупный результат — в объектное хранилище со ссылкой. Расписания —
одна запись в Redis или блокировка на запуск, плюс уникальный jobId
периода против двойного срабатывания и явное решение про пропущенное
окно. Команды — в очередь задач, факты — в шину событий, и не
наоборот».
