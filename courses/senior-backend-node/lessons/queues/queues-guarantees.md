# Гарантии доставки: at-most-once, at-least-once, exactly-once и порядок

Уровень 1. Сердце модуля. «Какие бывают гарантии доставки и какую
выбрать» — вопрос, который в том или ином виде звучит на каждом
собеседовании про распределённые системы. Правильный ответ содержит
неприятную правду и вывод из неё.

## Боль: подтверждение может потеряться

Вспомни ключевую сцену из урока про идемпотентность: таймаут — это
отсутствие информации. С брокером то же самое, в обе стороны:

- продюсер отправил, подтверждение брокера не дошло — отправлять
  ещё раз? Если да — возможен дубль в брокере; если нет — возможна
  потеря;
- потребитель обработал, ack не дошёл (умер сразу после обработки) —
  брокер отдаст сообщение снова: дубль обработки. Ack до обработки —
  смерть после ack теряет сообщение.

Из этого следует фундаментальный выбор — **на каждом плече**
(продюсер→брокер, брокер→потребитель):

- **at-most-once** — не повторять: возможна потеря, дублей нет;
- **at-least-once** — повторять до подтверждения: потерь нет, дубли
  есть.

Помнишь гарантию pub/sub у Redis — «доставка сейчас подключённым»?
Это at-most-once в чистом виде: дёшево и с потерями.

## Exactly-once: что это на самом деле

«Ровно один раз» — то, чего все хотят и о чём обязательно спросят.
Честный разбор:

- **Транспортного exactly-once не существует**: между двумя узлами по
  ненадёжной сети нельзя гарантировать «ровно один раз» — это следствие
  проблемы двух генералов. Можно лишь at-least-once + устранение
  эффекта дублей.
- **Kafka даёт exactly-once в своих границах**: идемпотентный
  продюсер (дубль отправки в брокер схлопывается по номеру
  последовательности) и транзакции Kafka для цепочек
  «прочитал из топика → записал в топик» (Kafka Streams). Это честный
  и полезный механизм — но он заканчивается на границе Kafka.
- **Как только эффект уходит наружу** — запись в Postgres, вызов
  провайдера SMS, — «ровно один раз» достигается только на стороне
  эффекта: **at-least-once доставка + идемпотентная обработка =
  effectively-once**. Это формула, которую нужно произнести дословно.

Практический вывод: проектируем **всегда под at-least-once**. Дубль —
не сбой, а штатное событие; следующая практика — идемпотентный
консьюмер, который делает дубли безвредными.

## Как дубль обезвреживают

Три техники, по нарастанию универсальности:

- **Естественная идемпотентность операции**: «установить статус
  blocked» — дубль безвреден сам по себе (модуль API, абсолютные
  операции).
- **Дедупликация по id сообщения**: таблица/набор обработанных
  `messageId` с уникальным ограничением; вставка и эффект — в одной
  транзакции. Окно дедупликации ограничено (хранить вечно нельзя) —
  и это тоже нужно называть: дубль старше окна пройдёт.
- **Версионность/монотонность**: событие несёт версию сущности;
  обработчик применяет только «версия больше моей» — устаревшие и
  повторные отбрасываются. Хорош ещё и против **перепутанного
  порядка**.

## Порядок

Вторая неприятная правда: **глобального порядка нет**, и бороться за
него дорого. Что есть:

- порядок **внутри партиции** (Kafka, по ключу) или внутри очереди с
  **одним** потребителем (RabbitMQ);
- конкуренция потребителей ломает порядок даже в FIFO-очереди: два
  воркера взяли соседние сообщения, закончили в обратном порядке;
- повторы ломают порядок: сообщение 5 упало и повторяется, 6 уже
  обработано.

Проектный ответ: **порядок нужен не глобально, а в рамках сущности**
— и обеспечивается ключом партиционирования (все события caseId=7 в
одной партиции, обрабатываются последовательно), либо версией в
сообщении, по которой потребитель отбрасывает устаревшее. Практика
через урок — планировщик, сохраняющий порядок внутри ключа при
параллельной обработке.

## Сквозной пример: путь одного уведомления

Соберём урок на одной цепочке «Пульта»: `cases` фиксирует обращение →
событие в Kafka (продюсер с подтверждением и повторами — at-least-once
в брокер; дубль продюсера Kafka схлопнет идемпотентностью) →
`notifications` читает (ручной коммит после обработки — at-least-once
из брокера; на повторе спасает дедупликация по id события) → задача в
RabbitMQ (persistent + confirm) → воркер вызывает провайдера SMS
(ack после успеха; сам вызов — с ключом идемпотентности провайдера,
потому что и здесь таймаут — не «нет»). На каждом плече —
at-least-once плюс идемпотентность эффекта. Вот и весь секрет
«надёжной доставки».

## На чём валят

- **«Мы настроили exactly-once, дублей не бывает»** — транспортного
  exactly-once нет; Kafka-транзакции заканчиваются на границе Kafka;
  дальше — идемпотентность.
- **«FIFO-очередь гарантирует порядок обработки»** — конкуренция и
  повторы ломают; порядок — это партиция по ключу с последовательной
  обработкой.
- **Дедупликация «в памяти сервиса»** — рестарт стирает память, дубль
  проходит; набор обработанных — в хранилище, с транзакцией.
- **Ack до обработки** — «зато без дублей» — и с потерями; выбор
  плеча нужно уметь обосновать.
- **Не назвать окно дедупликации** — вечного хранения id не бывает.

## Как ответить за минуту

«На каждом плече выбор: at-most-once — возможна потеря, at-least-once
— возможен дубль; транспортного exactly-once не существует. Kafka
даёт exactly-once внутри себя — идемпотентный продюсер и транзакции,
— но любой внешний эффект достигает "ровно однажды" только формулой
at-least-once плюс идемпотентная обработка. Поэтому проектирую под
at-least-once: дубли обезвреживаются естественной идемпотентностью,
дедупликацией по id сообщения в одной транзакции с эффектом — с
ограниченным окном, — или версией сущности. Порядок — только внутри
партиции по ключу; глобальный не нужен, нужен порядок в рамках
сущности».
