# Практика: планировщик задач с приоритетом, задержкой и повторами

Финал модуля: миниатюра ядра BullMQ. Очередь задач, где у задачи есть
приоритет, отложенный запуск и лимит попыток с backoff, а воркер
берёт по одной готовой задаче за тик. Проверяется всё, что модуль
собирал: состояние задач, порядок выбора, повторы с задержкой.

## Модель

Время модельное, тики приходят снаружи. Экспортируй `runQueue(cmds)`:

```ts
type Cmd =
  | { cmd: "add"; at: number; id: string; priority?: number;  // default 0
      delayMs?: number;                                        // default 0
      attempts?: number }                                      // default 1 — всего попыток
  | { cmd: "tick"; at: number; result: "ok" | "fail" };
```

Правила:

- `add` ставит задачу: она **готова** с момента `at + delayMs`.
  Журнал: `"added:<id>"`.
- `tick` — воркер просыпается в момент `at` и берёт **одну** самую
  подходящую готовую задачу: из задач со временем готовности `<= at`
  — наибольший `priority`; при равенстве — более ранний момент
  постановки; при равенстве — порядок добавления. Если готовых нет —
  журнал `"idle"`.
- Взятая задача выполняется мгновенно с исходом `result` тика:
  - `ok` → `"done:<id>"`, задача завершена;
  - `fail` → попытка потрачена. Если попытки остались — задача
    уходит в отложенный повтор: готовность `at + backoff`, где
    backoff = `1000 * 2^(номер_завершившейся_попытки - 1)` мс
    (после первой неудачи 1000, после второй 2000, дальше 4000...);
    журнал `"retry:<id>:in:<backoff>"`. Если попыток больше нет —
    `"failed:<id>"`, задача завершена навсегда.
- В конце верни и сводку.

```ts
type Result = {
  log: string[];
  summary: { done: string[]; failed: string[]; pending: string[] };
  // pending — не завершённые к концу (в порядке добавления)
};

export function runQueue(cmds: Cmd[]): Result;
```

## Пример

```json
[
  { "cmd": "add",  "at": 0,   "id": "low",  "priority": 1 },
  { "cmd": "add",  "at": 5,   "id": "high", "priority": 9 },
  { "cmd": "add",  "at": 10,  "id": "later", "priority": 9, "delayMs": 5000 },
  { "cmd": "tick", "at": 20,  "result": "ok" },
  { "cmd": "tick", "at": 30,  "result": "ok" },
  { "cmd": "tick", "at": 40,  "result": "ok" }
]
```

Журнал: `["added:low", "added:high", "added:later", "done:high",
"done:low", "idle"]` — `later` готова только с 5010, до неё тики не
дотянулись; сводка: done `["high", "low"]`, failed `[]`, pending
`["later"]`.

## Ловушки, которые проверяют случаи

- Отложенная задача не берётся раньше времени готовности, каким бы
  ни был приоритет.
- Повтор после `fail` делает задачу неготовой на время backoff:
  следующий тик может взять другую задачу.
- Backoff растёт по попыткам одной задачи: 1000, 2000, 4000.
- `attempts: 1` (default) — единственная неудача сразу `failed`.
- Приоритет при равенстве решается временем постановки, затем
  порядком добавления.
