# Практика: идемпотентный консьюмер

Главная практика модуля: поток событий с дублями и нарушенным
порядком — а итоговое состояние должно быть таким, будто каждое
событие пришло ровно один раз и вовремя. Это формула
«at-least-once + идемпотентность» в коде, и её регулярно дают на
live-coding в самых разных обёртках.

## Постановка

`notifications` читает события об изменении карт из Kafka. Каждое
событие несёт ключ (id карты), **версию** сущности (монотонно растёт
с каждым изменением) и новое значение статуса:

```ts
type Event = {
  messageId: string;  // уникален у события; у дубля доставки — тот же
  cardId: number;
  version: number;
  status: string;
};
```

Брокер обещает только at-least-once: события могут **дублироваться**
(тот же `messageId`) и приходить **не по порядку** (version 3 раньше
version 2 — повтор после сбоя, ребалансировка).

## Задание

Экспортируй функцию `consume(events)`, которая обрабатывает поток по
порядку массива и возвращает:

```ts
type Result = {
  state: Record<number, { version: number; status: string }>; // по картам
  log: string[];   // решение по каждому событию, в порядке потока
  applied: number; // сколько событий реально применено
};
```

Правила обработки каждого события:

1. **Дубль по messageId** (уже видели) — пропустить, в журнал
   `"dup:<messageId>"`. Дубль не применяется повторно, даже если у него
   версия новее текущей (это тот же самый факт, доставленный дважды).
2. Иначе, если карта уже есть и `version <=` текущей — устаревшее или
   перепутанное — пропустить, в журнал
   `"stale:<messageId>:v<version>"`.
3. Иначе — применить: обновить статус и версию карты, в журнал
   `"apply:<messageId>:v<version>"`, `applied + 1`.
4. `messageId` запоминается в любом из исходов (увиденное — увидено).

Заготовка:

```ts
type Event = { messageId: string; cardId: number; version: number; status: string };
type Result = {
  state: Record<number, { version: number; status: string }>;
  log: string[];
  applied: number;
};

export function consume(events: Event[]): Result {
  // ...
  return { state: {}, log: [], applied: 0 };
}
```

## Пример

```json
[
  { "messageId": "m1", "cardId": 5, "version": 1, "status": "active" },
  { "messageId": "m2", "cardId": 5, "version": 2, "status": "blocked" },
  { "messageId": "m2", "cardId": 5, "version": 2, "status": "blocked" },
  { "messageId": "m3", "cardId": 5, "version": 1, "status": "active" }
]
```

Результат: состояние `{5: {version: 2, status: "blocked"}}`, журнал
`["apply:m1:v1", "apply:m2:v2", "dup:m2", "stale:m3:v1"]`,
применено 2. Дубль m2 отброшен по id, запоздавший m3 — по версии;
карта осталась заблокированной, как и была бы при идеальной доставке.

## Ловушки, которые проверяют случаи

- Дубль проверяется **раньше** версии: повторная доставка события с
  максимальной версией — это `dup`, а не `apply`.
- Равная версия — тоже `stale`: «не меньше» здесь означает «строго
  больше, чтобы применить».
- Разные карты независимы: версии не пересекаются между ключами.
- Первое событие карты применяется при любой версии (нет «текущей» —
  сравнивать не с чем).
- Пустой поток — пустое состояние, ноль применённых.
