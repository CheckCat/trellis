# Rate limiting и backpressure: token bucket, скользящее окно, ограниченные очереди

Уровень 1. Rate limiting уже мелькал трижды — защита входа, лимиты
провайдера, gateway. Пора разобрать сами алгоритмы и их свойства:
«какой лимитер выберете и почему» — стандартный вопрос, и у каждого
алгоритма есть подвох.

## Боль: без лимита ресурс достаётся самому жадному

Один интеграционный клиент с багом (цикл без задержки) выедает всю
ёмкость API — остальные ждут. Скрипт перебирает пароли со скоростью
сети. Массовая операция забивает базу так, что операторы не могут
работать. Лимит — это справедливость и защита: каждый получает свою
долю, перегрузка отбивается на границе (дёшево — это load shedding
из прошлого урока по ключу клиента).

## Алгоритмы

**Fixed window** — счётчик на интервал: «100 запросов на минуту
10:00–10:01». Просто (INCR с TTL в Redis), но граница окон дырявая:
100 запросов в 10:00:59 и ещё 100 в 10:01:00 — 200 за две секунды,
двойной лимит на стыке.

**Sliding window log** — журнал меток времени: считаем запросы за
последние 60 секунд честно, по каждому запросу вычищая старые метки.
Точен всегда; цена — память на каждую метку (ZSET в Redis на ключ) —
дорого при больших лимитах.

**Sliding window counter** — компромисс: счётчики текущего и
прошлого фиксированного окна, доля прошлого берётся
пропорционально перекрытию. Почти точен, дёшев — частый выбор для
API-лимитов.

**Token bucket** — ведро ёмкостью B, токены капают со скоростью R в
секунду; запрос забирает токен, нет токена — отказ (или ожидание).
Ключевое свойство: **позволяет всплески** до B при средней скорости
R — «можно 50 подряд, но не больше 10 в секунду в среднем». Именно
так формулируются лимиты для людей и интеграций; реализация — пара
(токены, время последнего пополнения) и ленивое пополнение при
запросе — O(1) памяти.

**Leaky bucket** — очередь фиксированной скорости вытекания:
сглаживает поток до идеально ровного (выход строго R). По сути —
ограниченная очередь + воркер с постоянным темпом; так удобно
**исполнять** исходящие вызовы под лимит провайдера (30 SMS/с из
модуля очередей).

Выбор одной строкой: **всплески разрешить — token bucket; поток
выровнять — leaky bucket; просто и почти точно на входе API —
sliding window counter**.

## Где и по какому ключу

- **Уровни**: граница (nginx/gateway — грубые лимиты по IP), сервис
  (по клиенту/токену — знает, кто это), операция (вход, отправка SMS
  — свои жёсткие лимиты).
- **Ключ**: по пользователю/клиенту — справедливость; по IP — защита
  до аутентификации (помня NAT: за одним IP — офис на тысячу
  человек); по паре (операция, аккаунт) — перебор паролей.
- **Распределённость**: инстансов восемь — счётчик общий в Redis
  (атомарный Lua-скрипт: проверка и списание разом — гонка из модуля
  Redis), либо каждый инстанс получает долю лимита (дёшево, но
  неточно при неравной балансировке).
- **Ответ**: 429 с `Retry-After` и заголовками остатка
  (`X-RateLimit-Remaining`) — клиент должен уметь притормозить, а не
  ретраить в лоб (иначе лимитер порождает retry storm — всё
  связано).

## Backpressure по всей цепочке

Вторая половина урока — та же идея изнутри: **не принимать работу,
которую некуда девать**. Ты видел это в стримах (write → false,
drain), в пуле соединений (очередь с таймаутом), в load shedding
(ограниченные очереди). Общий принцип: у каждой очереди в системе —
предел, при достижении — сигнал назад: отказ, замедление,
пауза чтения. Система без backpressure не «медленно работает», а
копит скрытый долг (буферы, память, латентность) и умирает внезапно.

Пример цепочки «Пульта»: наплыв обращений → gateway лимитирует вход
(429 самым частым) → BFF держит ограниченные пулы к сервисам
(bulkhead) → cases пишет в outbox, реле публикует с постоянным
темпом → воркеры уведомлений тянут из очереди сколько успевают
(prefetch), очередь растёт — метрика глубины зовёт дежурного →
исходящие SMS выравниваются leaky bucket-ом под лимит провайдера.
Давление на каждом стыке гасится, а не передаётся дальше.

## На чём валят

- **Fixed window без оговорки про стык окон** — двойной лимит на
  границе; назвать и предложить sliding counter.
- **Token bucket против leaky bucket** — путают: первый разрешает
  всплески на входе, второй выравнивает выход.
- **Лимитер в памяти инстанса** при восьми инстансах — лимит ×8 и
  зависит от балансировки; общий счётчик в Redis атомарным скриптом.
- **429 без Retry-After** — клиенты ретраят немедленно, лимитер
  создаёт шторм.
- **По IP как единственный ключ** — NAT: банковский офис за одним
  адресом.

## Как ответить за минуту

«Алгоритмы: fixed window прост, но дыряв на стыке окон; sliding log
точен, но память на метку; sliding counter — рабочий компромисс для
входа API; token bucket разрешает всплески при средней скорости —
язык лимитов для клиентов; leaky bucket выравнивает исходящий поток
под лимит провайдера. Ключи — пользователь, IP до аутентификации,
пара операция-аккаунт для входа; распределённо — общий счётчик в
Redis атомарным Lua. Ответ — 429 с Retry-After. И то же самое
изнутри — backpressure: предел у каждой очереди, сигнал назад вместо
скрытого долга — от write/drain в стримах до глубины очереди с
алёртом».
