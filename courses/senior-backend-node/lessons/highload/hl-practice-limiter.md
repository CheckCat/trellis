# Практика: лимитер со скользящим окном

Пишем точный лимитер — sliding window log: N запросов на ключ за
последние W миллисекунд, независимые ключи, ответ с временем, когда
можно вернуться. Это «напишите rate limiter» в его самой частой
постановке.

## Задание

Экспортируй функцию `runLimiter(limit, windowMs, requests)`:

```ts
type Request = { at: number; key: string };

type Decision = {
  at: number;
  key: string;
  allowed: boolean;
  remaining: number;    // сколько запросов ещё можно этому ключу прямо сейчас
                        // (после учёта текущего, если он допущен)
  retryAfterMs?: number; // только для отклонённых: через сколько мс появится слот
};

export function runLimiter(limit: number, windowMs: number, requests: Request[]): Decision[];
```

Правила:

- Запрос в момент `at` допускается, если за интервал
  `(at - windowMs, at]` у этого ключа **меньше** `limit` допущенных
  запросов. Отклонённые запросы в окне **не считаются**.
- `remaining` — свободные слоты после решения: для допущенного —
  `limit - использовано_в_окне` (включая текущий); для отклонённого —
  `0`.
- `retryAfterMs` — через сколько миллисекунд освободится слот: момент,
  когда самый старый допущенный запрос окна выйдет из окна, минус
  `at`. Формально: `oldest + windowMs - at`, где `oldest` — время
  самого старого допущенного в окне. Только у отклонённых.
- Ключи независимы. Запросы приходят в неубывающем порядке `at`.
- Запрос ровно на границе: допущенный в момент `t` покидает окно в
  момент `t + windowMs` (то есть в `at = t + windowMs` он уже **не**
  считается).

## Пример

`limit = 2`, `windowMs = 1000`:

```json
[
  { "at": 0,    "key": "a" },
  { "at": 100,  "key": "a" },
  { "at": 200,  "key": "a" },
  { "at": 999,  "key": "b" },
  { "at": 1000, "key": "a" },
  { "at": 1100, "key": "a" }
]
```

Решения:

```json
[
  { "at": 0,    "key": "a", "allowed": true,  "remaining": 1 },
  { "at": 100,  "key": "a", "allowed": true,  "remaining": 0 },
  { "at": 200,  "key": "a", "allowed": false, "remaining": 0, "retryAfterMs": 800 },
  { "at": 999,  "key": "b", "allowed": true,  "remaining": 1 },
  { "at": 1000, "key": "a", "allowed": true,  "remaining": 0 },
  { "at": 1100, "key": "a", "allowed": true,  "remaining": 0 }
]
```

В 200: старейший допущенный — 0, слот освободится в 1000 → retry
через 800. В 1000: запрос от 0 уже вне окна (граница!), в окне только
100 → допущен. В 1100: запрос от 100 вышел (1100 − 1000 = 100 — уже
не в окне), в окне только 1000 → допущен.

## Ловушки, которые проверяют случаи

- Отклонённые запросы не занимают слоты: шквал отказов не продлевает
  блокировку (это отличие от наивной реализации со счётчиком всех
  запросов).
- Граница окна: запрос ровно через windowMs после старейшего —
  допущен.
- retryAfterMs считается от старейшего **допущенного**, не от
  последнего.
- Ключи не влияют друг на друга.
- `limit = 1` — каждый допуск блокирует ключ на окно.
