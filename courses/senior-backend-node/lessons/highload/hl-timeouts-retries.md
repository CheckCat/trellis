# Таймауты, ретраи, jitter, retry storm и бюджет ретраев

Уровень 1. Близнец урока про повторы в очередях — теперь для
**синхронных** вызовов, где всё жёстче: ждёт живой запрос, и
неправильные ретраи не просто тратят ресурсы, а добивают лежащего.
Тема обязательная: «как настроите таймауты и ретраи» звучит в каждом
system design.

## Боль: один медленный сосед вешает всех

Сервис справочников начал отвечать за 30 секунд. BFF без таймаута
честно ждёт: его обработчики копятся (закон Литтла: латентность
выросла в сто раз — конкурентность тоже), пул соединений исчерпан,
память растёт — BFF падает целиком из-за **некритичного** сервиса.
Отказ пришёл не сверху, а сбоку — и распространился. Таймауты — это
изоляция отказов, а не «оптимизация».

## Таймауты: правила

- **Таймаут есть у всего**: connect (быстрый — сотни мс: живой сервис
  принимает соединение быстро), запрос целиком, запрос к базе
  (statement_timeout), захват соединения из пула, работа в очереди.
  Дефолты библиотек часто «бесконечность» — это проверяется руками.
- **Значение — из перцентилей вызываемого**: таймаут ≈ p99 плюс
  запас. Таймаут 5 с на сервис с p99 = 100 мс означает «в плохой
  день я готов ждать в 50 раз дольше обычного» — зачем?
- **Бюджет запроса (deadline)**: у входящего запроса общий лимит
  (наши 800 мс на экран), и внутренние вызовы должны укладываться в
  **остаток**. Дедлайн передаётся вниз по цепочке (в gRPC — встроено,
  в HTTP — заголовком), иначе внутренности продолжают трудиться над
  запросом, которого клиент уже не ждёт.
- Из модуля Node: клиент, ушедший сам, — это AbortController и отмена
  вглубь; таймаут — её частный случай.

## Ретраи: дисциплина

Всё из модуля очередей действует, плюс синхронная специфика:

- **Повторять только идемпотентное** (модуль API — таймаут не значит
  «не выполнилось»!) и **только транзиентное** (сетевые обрывы, 503,
  connect-таймауты; не 4xx).
- **Мало попыток**: обычно 1 повтор, максимум 2. Живой запрос ждёт;
  третья попытка в горящий сервис — уже соучастие в пожаре.
- **Экспоненциальный backoff с полным jitter** — как в очередях, но
  base короткий (десятки-сотни мс): времени нет.
- **Повтор — в другой инстанс** (балансировщик и так это сделает):
  повторять в тот же — спрашивать того же, кто уже не ответил.

## Retry storm: как ретраи убивают

Механика, которую нужно уметь рассказать: сервис деградировал до
50 % отказов → каждый отказ повторяется → нагрузка удваивается →
деградация глубже → отказов больше → ещё волна ретраев. Плюс этажи:
клиент ретраит BFF, BFF ретраит cases, cases ретраит базу — три
уровня по 3 попытки = **27-кратная** нагрузка на дно. Система,
которая слегка споткнулась, добивается собственной заботой о
надёжности.

Лечение:

- **Бюджет ретраев** (retry budget): повторов не больше N % от
  обычного трафика (типично 10–20 %); бюджет кончился — отказы идут
  наверх без повторов. Это переключатель «ретраи помогают при
  редких сбоях, выключаются при массовых».
- **Ретраи на одном уровне**, не на каждом: обычно у края (BFF или
  gateway), внутренние слои — без своих повторов.
- **Circuit breaker** — следующий урок: перестать ходить в лежащего
  вообще.
- И приправа из очередей: jitter, иначе повторы синхронизируются в
  волны.

## Hedged requests

Продвинутый приём для чтения: не дождался ответа за p95 — отправь
**вторую копию** запроса в другой инстанс, возьми первый ответ.
Срезает хвост латентности ценой +5 % трафика; только для
идемпотентных чтений и при свободной ёмкости. Назвать его — плюс в
разговоре про хвосты из прошлого урока.

## На чём валят

- **Таймаут «на всякий случай 30 секунд»** — это не таймаут, а
  согласие висеть; значение — из p99 вызываемого и бюджета запроса.
- **Ретрай POST-а без идемпотентности** — двойное списание из модуля
  API; сначала Idempotency-Key, потом ретраи.
- **Ретраи на каждом этаже** — умножение нагрузки 3×3×3; повторяет
  край, внутренние — нет.
- **Нет понятия retry budget** — ретраи без предохранителя при
  массовом сбое — это storm.
- **Дедлайн не передаётся вниз** — внутренности доделывают запросы,
  которых никто не ждёт; «зомби-работа» под нагрузкой ощутима.

## Как ответить за минуту

«Таймаут у всего: connect короткий, полный — из p99 вызываемого с
запасом, плюс общий дедлайн запроса, который передаётся вниз и
съедается по цепочке. Ретраи — только идемпотентное и транзиентное,
один-два повтора с backoff и полным jitter, в другой инстанс, и
только на одном уровне — у края. Против retry storm — бюджет
ретраев: повторы не больше десятой части трафика, при массовом сбое
отключаются, дальше работает circuit breaker. Для хвостов чтения —
hedged requests: вторая копия после p95, первый ответ побеждает».
