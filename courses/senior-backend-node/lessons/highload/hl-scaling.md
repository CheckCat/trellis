# Масштабирование: stateless, балансировка, sticky sessions, health checks

Уровень 1. Модуль про нагрузку начинается с базы: как из одного
инстанса сделать восемь и не сломать ничего. Половину кирпичей курс
уже дал — здесь они складываются в стену, и добавляется consistent
hashing, которого не хватало.

## Боль: второй инстанс ломает то, что работало

BFF работал на одном инстансе. Добавили второй за балансировщиком —
и посыпалось: операторы разлогиниваются (сессии жили в памяти
процесса), у половины не приходят уведомления (WebSocket-мост — из
модуля API), счётчики лимитов врут (каждый инстанс считал свои).
Всё это — одна ошибка: **состояние в процессе**.

## Stateless как условие

Правило: инстанс можно убить и создать в любой момент, и никто не
заметит. Всё, что должно пережить запрос, — наружу: сессии — в Redis
(модуль auth), кэш — слоями память+Redis с TTL (модуль кэша), файлы —
в объектное хранилище, счётчики и лимиты — в Redis, соединения
WebSocket — локальны, но события глобальны через pub/sub. Память
процесса остаётся для того, что не жалко потерять: локальный кэш,
буферы.

Из модуля Node сюда же: процессы не делят память — восемь реплик
контейнера это восемь изолированных миров, и оркестратор (а не
cluster) — современный способ занять восемь ядер.

## Вертикально или горизонтально

**Вертикально** — больше CPU и памяти тому же инстансу: просто, без
изменений кода, но упирается в потолок железа и не добавляет
отказоустойчивости (инстанс один — и точка отказа одна).
**Горизонтально** — больше инстансов: почти безграничо и даёт
переживание отказа инстанса, но требует stateless и балансировки.
Ответ сеньора: сначала вертикально до разумного (это дёшево), затем
горизонтально; и помнить, что 400 RPS «Пульта» держит и пара
инстансов — горизонтальность здесь ради **отказоустойчивости**, а не
пропускной способности.

## Балансировка

- **L4 (TCP)** — раскидывает соединения, не заглядывая в них: быстро,
  тупо; keep-alive-соединение целиком живёт на одном бэкенде.
- **L7 (HTTP)** — видит запросы: маршрутизация по путям, ретраи,
  заголовки, канареечные веса. Стандартный выбор для API.

Алгоритмы: round robin (по кругу), least connections (наименее
занятому — лучше при неравных запросах), по хешу (о нём ниже).

**Sticky sessions** — привязка клиента к инстансу (cookie, ip-hash).
Из модуля API ты уже знаешь: это костыль для нераспределённого
состояния и **не** решение доставки событий. Легитимные ниши — тёплый
локальный кэш и протоколы с рукопожатием; по умолчанию — stateless
без sticky.

**Health checks** — балансировщик шлёт трафик только живым: инстанс
отвечает на служебный эндпоинт; не ответил N раз — выведен из
ротации. Из модуля Node: при остановке инстанс **сам** начинает
отвечать «не готов», чтобы выйти из ротации до закрытия (graceful
shutdown); полный разбор проб — в модуле эксплуатации.

## Consistent hashing

Обещанный инструмент. Задача: распределить ключи (сессии, кэш,
партиции работы) по N узлам так, чтобы **изменение N не
перемешивало всё**.

Наивно: `узел = hash(key) % N`. Добавили узел — N сменилось, и
**почти каждый** ключ переехал: кэши всех узлов разом холодные,
partition-назначения все перетасованы. Это «стадо» на пустом месте.

Consistent hashing: узлы и ключи хешируются в одно **кольцо**
(0..2³²); ключ принадлежит первому узлу по часовой стрелке.
Добавление узла забирает **только** ключи между ним и предыдущим —
примерно 1/N от общего числа; удаление отдаёт только свои ключи
следующему. Чтобы дуга каждого узла была равномерной, каждый узел
кладут на кольцо **много раз** — виртуальные узлы (vnodes, обычно
100–200 на физический): сглаживают распределение и позволяют давать
узлам разный вес.

Где живёт: клиентское распределение по кэш-узлам, шардирование
(Cassandra, Dynamo-подобные), балансировка по хешу ключа (один клиент
— один бэкенд — тёплый кэш без sticky-cookie). Практика через два
урока — построить кольцо руками.

## На чём валят

- **Состояние в памяти при масштабировании** — «работает через раз
  после добавления инстанса» — диагноз с ходу.
- **«Sticky sessions решают состояние»** — прячут: умерший инстанс
  теряет свои «прилипшие» сессии; состояние — наружу.
- **hash % N** — не назвать, почему это больно при изменении N, и
  чем consistent hashing лучше (переезжает ~1/N ключей).
- **Виртуальные узлы** — без них кольцо из трёх узлов делится
  неравномерно; vnodes — часть правильного ответа.
- **«Горизонтальное масштабирование ради скорости»** при 400 RPS —
  главная выгода здесь отказоустойчивость; скорость — вопрос профиля
  нагрузки.

## Как ответить за минуту

«Условие масштабирования — stateless: сессии, счётчики, кэш и файлы —
во внешние хранилища, инстанс можно убить в любой момент. Балансировка
— обычно L7: least connections или round robin, health checks выводят
мёртвых, при остановке инстанс сам объявляет себя неготовым. Sticky
sessions — костыль, оставляю для тёплого кэша, не для состояния.
Распределение ключей по узлам — consistent hashing: кольцо с
виртуальными узлами, при изменении числа узлов переезжает лишь ~1/N
ключей против «почти всё» у hash % N. И честно: при наших 400 RPS
горизонтальность — про отказоустойчивость».
