# Кейс: массовые операции и регламентные выгрузки

Второй прогон метода — более узкая задача, из тех, что дают как
«спроектируйте подсистему»: фоновая обработка в банке. Она ближе
всего к твоему реальному опыту (массовые операции и выгрузки ты
делал с фронтовой стороны) — кейс достраивает серверную половину.

## Условие

«Супервизоры запускают массовые операции над обращениями и
документами (до 50 000 объектов): переназначение, смена статусов,
формирование реестров для внешних систем. Плюс регламентные
выгрузки по расписанию. Операция может идти десятки минут; нужен
прогресс, отмена, устойчивость к сбоям, отчёт о результате».

## Требования и оценки — быстро

Уточнить: одновременных операций — единицы; объект обрабатывается за
десятки миллисекунд (запись в базу) или секунды (вызов внешней
системы)? Это развилка всей архитектуры — считаем оба: 50k × 20 мс ≈
17 минут одним потоком, → параллелим; 50k × 1 с — уже 14 часов, →
параллелим обязательно и договариваемся об SLA. Пики — конец
месяца (регламентные). Критично: **не потерять и не задвоить**
эффекты; прогресс честный; отчёт — документ.

## Ядро дизайна

**Модель**: операция (`bulk_operation`) → разбивается на **пачки**
(chunks) по 100–1000 объектов → пачка — единица работы воркера.
Таблицы: операция (статус, параметры, счётчики, кто запустил),
пачки (диапазон, статус, попытки), результаты по объектам (успех/
причина отказа — для отчёта).

**Очередь**: BullMQ (Redis) — flow «родитель-дети»: дети-пачки,
родитель агрегирует. Либо — и это стоит проговорить как
альтернативу — **очередь в Postgres** через FOR UPDATE SKIP LOCKED
(наша практика из модуля Postgres): меньше инфраструктуры, тот же
паттерн; выбор по наличию Redis и объёмам.

**Идемпотентность — сердце ответа** (интервьюер будет копать сюда):

- пачка обрабатывается транзакционно: эффекты + отметка пачки в
  одной транзакции с блокировкой (или условием) от повторного
  выполнения;
- повтор упавшей пачки безопасен: объекты внутри — по условию
  («переназначить, если ещё на старом операторе» — атомарный UPDATE
  с WHERE);
- запуск операции идемпотентен: уникальный ключ (для регламентных —
  `выгрузка-2026-03-07`), дубль запуска схлопывается.

**Прогресс и отмена**: счётчики по завершению пачек (не по
«запланировано»); отмена кооперативная — флаг, пачки проверяют его
между собой; уже выполненное не откатывается (сказать явно — это
продуктовое решение, для отката — отдельная компенсирующая
операция).

**Выгрузки**: стриминг из базы (keyset-пагинацией или курсором) →
формирование файла потоково (модуль Node: константная память) →
объектное хранилище → ссылка в отчёте; передача во внешнюю систему —
отдельным шагом с ретраями и **сверкой** (количество/контрольные
суммы — банковская привычка из модуля миграций).

**Расписания**: одна запись расписания (BullMQ repeatable или
внешний cron) + уникальный ключ периода против двойного запуска +
явное решение о пропущенном окне (догонять или нет — спросить у
бизнеса вслух).

## Отказы — проход самостоятельно

Воркер умер на пачке → stalled, пачка вернулась, повтор безопасен
(идемпотентность); Redis умер → операции приостановились, состояние
в Postgres цело, после подъёма продолжение (вот зачем состояние не
только в очереди); внешняя система лежит → ретраи с backoff,
breaker, пачки в отложенный повтор, операция в статусе «частично,
ждёт»; **ядовитый объект** (один документ валит обработчик) — не
дать пачке зациклиться: лимит попыток пачки, деление пополам
(bisect) до изоляции объекта, объект — в отчёт с причиной.
Наблюдаемость: глубина очередей, возраст старейшей пачки, доля
отказов по типам — дашборд операции.

## Вопросы, которые зададут

- «Почему не одна транзакция на всё?» → блокировки на десятки минут,
  WAL, VACUUM — модуль Postgres; пачки с чекпоинтами.
- «Пользователь запустил дважды» → ключ идемпотентности запуска.
- «Как посчитать прогресс честно?» → по завершённым пачкам;
  «обработано объектов» — из результатов, не из планов.
- «50k синхронных вызовов внешней системы?» → лимит её RPS —
  выравнивание leaky bucket-ом, оценка времени, SLA и параллелизм —
  арифметика вслух.

## Что делает ответ сеньорским

Пачки как единица повторяемости; идемпотентность на трёх уровнях
(запуск, пачка, объект); состояние в базе, а не только в брокере;
ядовитый объект с bisect; сверка выгрузок. И постоянные отсылки «я
это делал с продуктовой стороны — знаю, что супервизору нужен
прогресс и понятный отчёт об отказах, а не только зелёная галка».
