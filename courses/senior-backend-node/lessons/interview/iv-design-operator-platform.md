# Кейс: спроектировать операторскую платформу

Первый полный прогон метода — на системе, которую ты знаешь лучше
интервьюера: рабочее место операторов банка. Кейс намеренно совпадает
с «Пультом»: читая, сверяй каждый шаг с тем, что курс строил
одиннадцать модулей, — это и есть твой эталонный ответ.

## Условие (как его дают)

«Спроектируйте бэкенд рабочего места операторов банка: операторы
принимают обращения клиентов, видят карточку клиента с продуктами,
ведут переписку, руководители смотрят отчёты. Компания крупная,
операторов несколько тысяч».

## Шаг 1. Требования

Функциональные (проговариваешь и записываешь): вход и роли
(оператор/супервизор/аудитор), карточка клиента со счетами и
картами, обращения с жизненным циклом и назначением, чат с клиентом
в реальном времени, уведомления операторам, массовые операции
супервизора, аудит всего (банк!). Отсекаешь вслух: телефонию,
базу знаний, WFM — «интегрируемся, не проектируем».

Нефункциональные — вытягиваешь вопросами: операторов в пик ~3000;
латентность экрана — сотни миллисекунд (инструмент работы!);
доступность высокая в рабочие часы; **аудит и невозможность потери
данных обращений — жёстче, чем скорость**; персональные данные —
регуляторика.

## Шаг 2. Оценки

3000 операторов × экран в 5–10 секунд ≈ 300–600 RPS на чтение к
BFF; записи — на порядок меньше (60k обращений/день ≈ 1–2 RPS
записи со всплесками). Вывод вслух: «нагрузка скромная — упор
на отказоустойчивость, корректность и аудит, не на пропускную
способность». Данные: миллионы обращений в год с событиями — десятки
ГБ в год — «один Postgres с партиционированием журналов тянет
годами».

## Шаги 3–4. API, данные, схема

Дальше — знакомая тебе картина, и в этом сила ответа:

- **BFF** для операторского фронта (агрегация экрана, WebSocket,
  сессии) за **gateway** (внешняя аутентификация, лимиты).
- Сервисы по bounded context-ам: **identity** (SSO, сессии в Redis с
  ротацией refresh, многосессионность, роли), **customers** (витрина
  счетов и карт из мастер-систем), **cases** (ядро: обращения,
  события, версия для оптимистичных обновлений), **chat**
  (WebSocket-плечи, история), **notifications** (очередь к внешним
  провайдерам), **bulk-ops** (BullMQ: чекпоинты, прогресс),
  **audit** (консьюмер Kafka, append-only хранилище).
- Данные: Postgres на сервис; события `case_events`; файлы вложений
  — объектное хранилище с presigned URL; кэш справочников — Redis +
  память с TTL.
- Асинхронка: доменные события через **outbox → Kafka** (ключ —
  caseId); команды «отправь SMS» — RabbitMQ с DLQ; чат-сообщения —
  событие в Kafka для аудита.
- API: REST у сервисов, ключ идемпотентности на создании обращения,
  keyset-пагинация журналов.

Каждый блок — с причиной из соответствующего модуля (проговаривай!):
почему outbox (нельзя терять события аудита), почему сессии, а не
голый JWT (мгновенный отзыв уволенного оператора — банковское
требование), почему BFF (пять сервисов на один экран, деградация
блоков).

## Шаг 5. Глубина: куда поведут

Три самых вероятных зонда интервьюера — и у тебя на каждый есть
целый модуль:

- **«Два оператора взяли одно обращение»** → оптимистичная версия в
  UPDATE, 409 и перечитать; почему не FOR UPDATE на человеческое
  время (модуль Postgres).
- **«Как доставите уведомление оператору на любом инстансе BFF»** →
  соединения локальны, события глобальны, pub/sub мост, нумерация и
  досылка при переподключении (модуль API).
- **«Что с аудитом при падении audit-сервиса»** → события ждут в
  Kafka, retention покрывает простой, консьюмер догоняет по
  offset-ам; сам аудит идемпотентен по event id (модули очередей).

## Шаг 6. Отказы и узкие места

Проход, который ты делаешь сам: SPOF — Redis сессий (→ Sentinel;
и деградация: короткий грейс на проверку сессий при его недоступности
— решение с ценой, проговорить), Kafka (→ кластер, но события
подождут в outbox — вот зачем он ещё), внешний SMS-провайдер (→
очередь, ретраи с backoff, breaker, DLQ с алёртом). Горячий ключ —
массовая рассылка банка порождает шторм обращений одной темы (→ ключ
партиционирования caseId, а не topic — урок из «инцидента» в модуле
нагрузки). Утренний пик входов — прогрев кэшей, jitter
переподключений.

## Шаг 7. Эволюция

×10 операторов: BFF и сервисы масштабируются репликами (stateless),
Postgres — сначала реплики на чтение отчётов, партиционирование
событий; шардирование — только если запись упрётся (по клиенту).
Чат — самый чувствительный к соединениям — выносится в отдельный
пул инстансов.

## Что делает этот ответ сеньорским

Не список технологий, а: числа, из которых следует «упор в
корректность»; каждый компонент с причиной; глубина в трёх местах по
приглашению; отказы, поднятые самостоятельно; и две-три фразы
«здесь я осознанно упрощаю». Прогони кейс вслух с таймером на 45
минут — квиз после этого урока проверит выбор решений в ключевых
точках.
