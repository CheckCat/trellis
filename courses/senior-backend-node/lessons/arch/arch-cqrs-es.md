# CQRS и Event Sourcing: когда нужно, когда вредно

Уровень 3: достаточно уверенной концепции — но именно здесь легко
выделиться, потому что большинство кандидатов пересказывают хайп, а
спрашивают обычно «когда НЕ надо».

## Боль: чтение и запись хотят разного

Запись в `cases` хочет нормализованную модель с инвариантами
(агрегат); чтение хочет плоские витрины: список обращений с именем
клиента, счётчики по отделам, полнотекст. Одна модель на оба
назначения — компромисс, который с ростом скрипит: JOIN-ы на каждый
экран против денормализации, ломающей запись.

## CQRS

Command Query Responsibility Segregation — **разные модели для команд
и запросов**. Спектр, а не выключатель:

- **Лайт (почти бесплатно):** разные пути в коде — команды идут через
  агрегат и репозиторий, запросы — отдельными read-хендлерами с
  голым SQL мимо доменной модели. Уже выигрыш: чтение не продирается
  через агрегаты, запись не обрастает полями «для списка». Этого
  уровня достаточно большинству систем, и это стоит сказать первым.
- **Средний:** отдельные **проекции** — денормализованные таблицы
  под экраны (`case_list_view` с именем клиента), обновляемые по
  доменным событиям. Читается мгновенно, пишется асинхронно —
  eventual между записью и витриной (знакомые слова).
- **Тяжёлый:** отдельное хранилище чтения (Elasticsearch для поиска,
  ClickHouse для аналитики) — модуль про выбор хранилищ это уже
  показывал: витрина не источник истины.

Цена растёт вправо: синхронизация проекций, отставание витрин,
двойной код. Двигаться вправо — по измеренной боли чтения, не по
моде.

## Event Sourcing

Радикальнее: **хранить не состояние, а события**. Текущее состояние
агрегата — свёртка его событий (`created`, `assigned`, `escalated`…);
запись — дозапись события в журнал (event store), чтение состояния —
replay событий агрегата (со **снапшотами** каждые N событий, чтобы
не крутить тысячи).

Что покупаем: полная история «почему так» (для аудита — идеально),
временные запросы («как выглядело обращение вчера»), новые проекции
из старых событий задним числом, естественная интеграция — события и
есть данные.

Чем платим — и это главная часть ответа:

- **версионирование событий**: события живут вечно, их схема
  меняется — нужны upcast-еры старых версий; это налог на каждое
  изменение модели;
- миграция «переписать историю» невозможна по определению;
- запросы «по текущему состоянию всех» — только через проекции
  (CQRS становится обязательным приложением);
- инструменты, экспертиза, обучение команды.

Трезвая рамка: ES — для **ядра с богатой историей и аудитом**
(проводки, лимиты, жизненный цикл обращения — кандидаты), остальному
достаточно журнала аудита рядом с обычным состоянием. И связка с
уже известным: аудит «Пульта» через события в Kafka — это
**event-driven** и журнал фактов, но НЕ event sourcing: источник
истины — таблицы Postgres, а не поток событий. Уметь провести это
различие — верный плюс.

## Проекции

Слово, которое уже встречалось: **проекция** — производное
представление, построенное из потока событий. Проектор слушает
события и обновляет витрину; упал — догоняет с своего offset-а;
испортилась — перестраивается replay-ем с нуля (суперсила Kafka из
модуля очередей). Требования знакомы до боли: проектор идемпотентен
(события приходят at-least-once), порядок — в рамках ключа. Следующая
практика — написать такой проектор.

## На чём валят

- **«CQRS — это два хранилища и шина»** — это разделение моделей;
  начинается с двух путей в коде и часто там заканчивается.
- **ES ради «полезно же иметь историю»** — историю даёт и журнал
  аудита; ES оправдывается временными запросами и перестроением
  проекций, а оплачивается версионированием событий навсегда.
- **Спутать event-driven с event-sourced** — события как интеграция
  против событий как источник истины.
- **Не назвать снапшоты** — replay тысяч событий на каждое чтение.
- **Проекция как источник истины** — она перестраиваемая витрина.

## Как ответить за минуту

«CQRS — разные модели чтения и записи, спектром: сначала просто
разные пути в коде — команды через агрегат, запросы голым SQL; потом
проекции под экраны, обновляемые по событиям; в пределе — отдельные
хранилища чтения. Двигаюсь вправо по измеренной боли. Event Sourcing
— события как источник истины: полная история, временные запросы,
перестроение проекций, но вечное версионирование событий и
обязательный CQRS в нагрузку — беру для ядра с богатым аудитом, не
для CRUD. И различаю event-driven интеграцию — события поверх
обычного состояния, как наш аудит через Kafka, — и event-sourced
хранение».
