# Монолит, модульный монолит, микросервисы: границы и цена

Уровень 1. «Монолит или микросервисы?» — вопрос-ловушка: правильный
ответ — не название, а понимание, **что покупаешь и чем платишь**, и
умение провести границы. Ты работал в микросервисном банке со
стороны потребителя — теперь взгляд изнутри.

## Боль, которую решают микросервисы (и это не «масштабируемость»)

Главная боль большого монолита — **организационная**: тридцать
человек в одной кодовой базе с одним релизным поездом. Релиз раз в
неделю, потому что регрессия всего; команда А ждёт команду Б; сломать
чужое — легко, найти виноватого — квест. Микросервисы решают именно
это: **независимые релизы независимых команд** (закон Конвея:
архитектура повторяет структуру коммуникаций — и наоборот, сервисы
режут по командам). Техническая независимость — масштабировать
горячее отдельно, изолировать сбой, разные стеки — приятный бонус,
а не главная причина.

## Цена

Каждый вызов функции стал сетевым: латентность, таймауты, ретраи,
circuit breaker-ы (модуль нагрузки — весь про это). Транзакция стала
распределённой: вместо `BEGIN/COMMIT` — саги и eventual consistency
(следующие уроки). Отладка стала трейсингом по десяти сервисам.
Появились контракты между командами, версионирование, брокер,
service discovery, инфраструктурная команда. Джойн двух таблиц стал
невозможен — данные в разных базах.

Формула: **микросервисы меняют сложность кода на сложность
операций**. Плата фиксированная и высокая; окупается, когда команд
много. Стартап из пяти человек с восемью сервисами платит цену
корпорации без её причин.

## Лестница: монолит → модульный монолит → сервисы

**Монолит** — один деплой, одна база. Для старта и маленькой команды
— правильный выбор: рефакторинг границ дёшев (переместить файл, а не
переписать контракт), транзакции настоящие, отладка локальная.

**Модульный монолит** — один деплой, но внутри — модули с жёсткими
границами: свой публичный API (интерфейсы), свои таблицы (чужие
модули не трогают их даже JOIN-ом), общение через интерфейсы или
внутреннюю шину событий. Это bounded context-ы из прошлого урока,
живущие в одном процессе. Даёт большую часть порядка микросервисов
без сетевой цены — и главный трамплин: модуль с чистой границей
выносится в сервис, когда (и если) появится причина.

**Микросервисы** — модули стали процессами со своими базами и
релизами. Причина перехода — организационная (команды толкаются) или
техническая с доказательствами (несовместимые профили нагрузки,
изоляция сбоев критична).

Ответ на «когда переходить»: **не по моде, а по боли** — релизный
поезд тормозит команды; и переходить **вырезанием модулей по одному**
(strangler — через два урока), а не переписыванием всего.

## Границы: как резать

Самое содержательное место вопроса. Правила:

- **По bounded context-ам** — по бизнес-способностям: обращения,
  клиенты, уведомления, аудит — как «Пульт» и нарезан. Не по слоям
  («сервис контроллеров, сервис базы») и не по CRUD-сущностям
  («сервис таблицы users»).
- **Данные принадлежат сервису.** У каждого — своя база (или схема);
  чужие данные — только через API или события владельца. Общая база
  на три сервиса — это монолит с сетевыми вызовами: связывание через
  схему, миграции бьют всех.
- **Критерий хорошей границы** — знакомая пара: высокая связность
  внутри, низкое зацепление между. Проверка: типичная фича трогает
  один сервис? Если каждая фича — правки в трёх сервисах и
  синхронный релиз — границы проведены не там.

**Распределённый монолит** — главный анти-исход, который нужно уметь
описать: сервисов много, но общая база, синхронные цепочки вызовов,
общие библиотеки с бизнес-логикой, релизы всё равно согласованные.
Все цены микросервисов, ни одной выгоды. Проверочный вопрос себе:
«можем ли мы задеплоить один сервис в пятницу, не спрашивая никого?»

## Как рассказывать про свой опыт

Твоя позиция честна и сильна: «работал в микросервисной платформе
банка со стороны BFF и контрактов: видел и выгоды — команды
релизились независимо, мой BFF изолировал фронт от их изменений, — и
цены: сквозные сценарии через несколько сервисов, версионирование
контрактов, инциденты на стыках. Сам бы начинал с модульного
монолита и выносил сервисы по доказанной боли».

## На чём валят

- **«Микросервисы — это про масштабируемость»** — главное про
  независимость команд и релизов; масштабируется и монолит
  (репликами).
- **Общая база между сервисами** — не узнать распределённый монолит.
- **Резка по слоям или по таблицам** — границы — по бизнес-способностям.
- **«Начнём сразу с микросервисов, чтобы потом не переделывать»** —
  границы неизвестны в начале; дешевле ошибиться границей модуля,
  чем контрактом сервиса.
- **Нет ответа про переход** — strangler и вынос по одному, не
  большой переписыватель.

## Как ответить за минуту

«Микросервисы покупают независимость команд и релизов — закон Конвея,
— платя сетью вместо вызовов функций, сагами вместо транзакций,
контрактами, трейсингом и инфраструктурой. Потому лестница: монолит
для старта, модульный монолит — жёсткие границы модулей со своими
таблицами в одном деплое — как дефолт для средней команды, сервисы —
по доказанной боли, вырезанием модулей. Границы — по
bounded context-ам, данные принадлежат сервису, фича в норме трогает
один сервис. Худший исход — распределённый монолит: сервисы с общей
базой и согласованными релизами — все цены, ноль выгод».
