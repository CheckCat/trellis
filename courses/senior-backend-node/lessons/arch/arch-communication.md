# Связь сервисов: синхронно и асинхронно, API gateway, service discovery, service mesh

Уровень 2. Сервисы нарезаны — теперь как им разговаривать. Урок
собирает решения, половину которых курс уже дал, в одну карту — и
добавляет инфраструктурный слой, о котором спрашивают словами
«gateway, discovery, mesh».

## Боль: каждый вызов — это выбор

`cases` создал обращение. Уведомить клиента — позвать `notifications`
синхронно или событием? Ответ определяет связанность судеб: синхронный
вызов — «мне нужен результат сейчас, и я завишу от твоей
доступности»; асинхронный — «я сообщаю факт и живу дальше».

## Синхронно против асинхронно

**Синхронно (REST/gRPC)** — когда ответ нужен для продолжения:
проверить права, прочитать карточку клиента для экрана, зарезервировать
средства перед подтверждением. Цена — **временнáя связанность**:
вызываемый должен быть жив и быстр прямо сейчас; цепочка синхронных
вызовов перемножает доступности (пять сервисов по 99,9 % — уже
99,5 %) и складывает латентности. Дисциплина: таймауты, ретраи
идемпотентного, circuit breaker — модуль нагрузки посвящён этому
целиком.

**Асинхронно (события/команды через брокер)** — когда нужен факт или
поручение, а не немедленный результат: уведомления, аудит,
пересчёты. Всё из модуля очередей: развязка доступности, at-least-once,
идемпотентный потребитель, outbox.

**Оркестрация против хореографии** — кто ведёт сквозной сценарий:
оркестратор (один сервис командует шагами — явный процесс, видно
состояние) против хореографии (каждый реагирует на события
предыдущего — нет центральной точки, но процесс «размазан», и понять
«где сейчас заказ» сложнее). Подробно — в уроке про саги; здесь
достаточно пары определений.

Практическое правило распределения: **запросы данных — синхронно;
факты и поручения — асинхронно; длинные процессы — сага**.

## API gateway

Единая входная дверь снаружи: маршрутизация по сервисам, терминация
TLS, аутентификация внешнего токена, rate limiting, иногда —
агрегация. Отличие от BFF (модуль API): gateway — **общий и тупой**
(без знания экранов), BFF — **свой у каждого фронта и умный**
(агрегация под экран). Они сосуществуют: браузер → BFF → gateway →
сервисы, либо gateway снаружи и BFF как один из его маршрутов.
Ошибка — тащить бизнес-логику в gateway: он инфраструктура, его
меняет платформенная команда.

## Service discovery

Инстансы приходят и уходят (деплой, автоскейл) — адреса нельзя
зашивать. Варианты по нарастанию:

- **DNS оркестратора** — в Kubernetes у сервиса стабильное имя
  (`cases.svc`), балансировка за ним; для большинства систем этого
  достаточно, и это правильный первый ответ;
- **реестр сервисов** (Consul, Eureka) — инстансы регистрируются,
  клиенты спрашивают реестр: нужен вне оркестратора или для умной
  клиентской балансировки.

## Service mesh

Когда сервисов десятки, сквозные заботы синхронных вызовов —
таймауты, ретраи, mTLS, метрики, канареечная маршрутизация —
повторяются в каждом. **Mesh** (Istio, Linkerd) выносит их из кода в
инфраструктуру: рядом с каждым инстансом — **sidecar**-прокси, весь
трафик идёт через него, и политики («таймаут 2 с, две попытки, mTLS
всюду») задаются конфигурацией, единообразно для сервисов на любом
языке. Из урока про межсервисную аутентификацию: mTLS «приносит
mesh» — вот откуда.

Цена: заметная инфраструктура и экспертиза, прокси в каждом поде,
ещё один слой отладки. Честная позиция: «mesh — когда сервисов
десятки и заботы реально дублируются; до того — библиотека
HTTP-клиента с таймаутами и ретраями на всю платформу». Не
переоценивай: mesh управляет **синхронным** трафиком — очередей и
брокеров он не заменяет.

## Контракты между командами

Связь сервисов — это прежде всего связь **команд**: контракт (OpenAPI,
proto, схема события) — граница ответственности. Всё из модуля API
работает и здесь: совместимые изменения, версии, deprecation по
метрикам; для событий — реестр схем (schema registry) с проверкой
совместимости при публикации новой версии. Двусторонняя проверка —
контрактные тесты (модуль тестирования). Твой опыт проектирования
контрактов с бэк-командами — ровно эта работа, называй её.

## На чём валят

- **Синхронная цепочка там, где нужен факт** — уведомления
  синхронным вызовом: связал доступности без причины.
- **Перемножение доступностей не назвать** — «а что будет с SLA при
  пяти сервисах в цепочке?»
- **Gateway с бизнес-логикой** — «умная труба» — антипаттерн: логика
  принадлежит сервисам.
- **«Mesh заменит очереди»** — он про синхронный трафик.
- **Контракт «понял из кода соседа»** — контракты явные,
  версионируемые, с проверкой совместимости.

## Как ответить за минуту

«Запросы данных — синхронно с таймаутами, ретраями идемпотентного и
circuit breaker-ом, помня, что цепочка перемножает доступности; факты
и поручения — асинхронно через брокер с outbox и идемпотентным
потребителем; длинные процессы — сага с оркестрацией или
хореографией. Снаружи — API gateway: общий, тупой, с
аутентификацией и лимитами; BFF — отдельно, он умный и принадлежит
фронту. Адреса — service discovery, в Kubernetes хватает DNS.
Десятки сервисов — service mesh: sidecar-прокси выносят таймауты,
mTLS и метрики в конфигурацию. И всё это держится на явных
версионируемых контрактах между командами — работа, которую я делал
руками».
