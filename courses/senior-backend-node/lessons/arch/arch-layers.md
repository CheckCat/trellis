# Слои, чистая и гексагональная архитектура, порты и адаптеры

Уровень 1. «Как устроен типичный сервис» — вопрос, с которого
начинается архитектурная часть почти любого собеседования. Хорошая
новость: слоистая, чистая, гексагональная и луковая архитектуры —
это **одна идея** с разной подачей, и понять нужно её, а не четыре
картинки.

## Боль: бизнес-правила размазаны по транспорту

Сервис, где расчёт комиссии живёт в обработчике HTTP, проверка прав —
в SQL-запросе, а отправка события — прямо в контроллере. Следствия:
правило нельзя протестировать без HTTP и базы; нельзя вызвать из
фоновой задачи (копипаст в воркер); смена библиотеки очередей — правка
пятидесяти файлов. Диагноз в терминах прошлых уроков: высокое
зацепление домена с инфраструктурой.

## Слои: базовая форма

```
Controller  — принять HTTP: распарсить, вызвать, оформить ответ
    ↓
Service     — бизнес-логика: правила, сценарии; не знает про HTTP
    ↓
Repository  — доступ к данным: SQL здесь; не знает про бизнес
    ↓
БД
```

Правило одно: **зависимости направлены вниз, и каждый слой знает
только соседа**. Контроллер не пишет SQL; репозиторий не проверяет
права; сервис не знает, что его вызвали по HTTP (значит — его можно
вызвать из воркера очереди без изменений). Это и есть структура
Nest-модуля из модуля HTTP, и аналогия с FSD-слоями фронта у тебя
уже в руках: однонаправленные зависимости, публичные API слоёв.

Тесты ложатся на слои: сервис тестируется с фейковым репозиторием
(быстро, без базы), репозиторий — интеграционно с настоящей базой,
контроллер — тонкий, ему почти нечего тестировать.

## Инверсия: домен в центре

У слоистой схемы есть изъян: сервис зависит от репозитория, то есть
**бизнес-логика зависит от инфраструктуры**. Чистая/гексагональная/
луковая архитектуры делают один ход — переворачивают стрелку (DIP из
урока про SOLID):

- домен объявляет **порты** — интерфейсы того, что ему нужно от мира:
  `CasesRepository`, `EventPublisher`, `Clock`;
- инфраструктура реализует их **адаптерами**: PostgresCasesRepository,
  KafkaEventPublisher — и подключается к домену, а не наоборот;
- направление зависимостей: **всё смотрит внутрь, домен не смотрит
  наружу** — в нём нет импортов pg, kafkajs, fastify.

«Гексагон» — просто картинка: у домена много граней-портов, к каждой
подключаются адаптеры (HTTP-адаптер и воркер очереди — оба входные
адаптеры одного порта «создать обращение»). Луковица — те же кольца.
Слова разные, идея одна: **домен в центре, инфраструктура — сменные
детали по краям**.

Что это даёт практически:

- домен тестируется в памяти фейками портов — быстрые тесты правил;
- вход не важен: HTTP, очередь, cron зовут один и тот же сценарий;
- инфраструктура заменяема по-настоящему: «Kafka вместо RabbitMQ» —
  новый адаптер, домен не тронут.

## Сколько слоёв — не перебор?

Обратная крайность реальна: интерфейс над каждым классом, DTO ↔
Entity ↔ Model маппинги в четыре прыжка, «луковица» в CRUD-сервисе из
трёх экранов. Зрелые ориентиры:

- **толщина церемоний пропорциональна сложности домена**: у сервиса
  справочников хватит контроллер+запросы; у `cases` с инвариантами и
  событиями — полный набор;
- порты — на **границах** (база, брокер, внешние API, время,
  случайность), а не над каждым классом;
- один сценарий не обязан прыгать через пять файлов, чтобы прочитать
  строку из таблицы.

На собеседовании фраза «архитектура — на самых сложных 20 % домена,
остальное проще» звучит как опыт, а не как лень.

## На чём валят

- **SQL в контроллере / HTTP-статусы в сервисе** — не узнать
  нарушение слоёв в показанном коде.
- **«Гексагональная — это про шесть слоёв»** — это про направление
  зависимостей: домен не импортирует инфраструктуру.
- **Не назвать выгоду инверсии** — тестируемость домена в памяти и
  много входов к одному сценарию.
- **Церемонии везде** — луковица над CRUD-справочником; толщина — по
  сложности.
- **«Мы можем сменить базу»** как главный аргумент — базу не меняют;
  аргумент — тесты и независимость домена от деталей.

## Как ответить за минуту

«База — слои: контроллер принимает HTTP, сервис держит правила и не
знает про транспорт, репозиторий — про данные; зависимости вниз,
благодаря чему сервис зовётся и из HTTP, и из воркера, а тестируется
с фейковым репозиторием. Следующий шаг — инверсия: домен объявляет
порты (репозиторий, публикация событий, часы), инфраструктура
реализует их адаптерами; всё смотрит внутрь, в домене нет импортов
pg и kafkajs. Чистая, гексагональная, луковая — одна эта идея.
Церемонии дозирую по сложности: полный набор — вокруг настоящих
инвариантов, справочникам хватает простого».
