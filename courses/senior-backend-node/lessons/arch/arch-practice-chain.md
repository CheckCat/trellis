# Практика: конвейер проверок поручения

Массовая операция «Пульта» прогоняет каждое поручение через конвейер
проверок перед исполнением: валидация формы, права, лимиты,
дубликаты. Наборы проверок различаются по типу поручения, проверки
переиспользуются, у каждой есть приоритет, а режим ошибок зависит от
сценария: интерактивному пользователю нужен первый отказ быстро,
пакетной загрузке — полный список проблем. Это Chain of
Responsibility + Strategy в одном флаконе — постоянный сюжет
live-coding «спроектируйте расширяемый конвейер».

## Модель

Проверки описаны данными (движок не передаёт функции):

```ts
type Check = {
  name: string;
  priority: number;         // больше — раньше
  appliesTo: string[];      // типы поручений, к которым применима
  failsFor: string[];       // id поручений, на которых проверка не проходит
};

type Order = { id: string; type: string };
```

`failsFor` — модель результата: реальная проверка смотрела бы в
данные, наша «падает» на перечисленных id.

## Задание

Экспортируй функцию `runPipeline(checks, orders, mode)`:

- Для каждого поручения собери его конвейер: проверки, у которых
  `appliesTo` содержит тип поручения, в порядке убывания `priority`;
  при равенстве — в порядке объявления в массиве `checks`.
- Прогони поручение по конвейеру:
  - `mode: "fail-fast"` — до первого отказа: прошедшие проверки
    попадают в `passed`, отказавшая — в `failed`, остальные не
    выполняются;
  - `mode: "collect-all"` — все проверки выполняются, отказы
    собираются списком.
- Верни по каждому поручению вердикт:

```ts
type Verdict = {
  id: string;
  ok: boolean;              // ни одного отказа
  passed: string[];         // имена прошедших, в порядке выполнения
  failed: string[];         // имена отказавших, в порядке выполнения
};

export function runPipeline(checks: Check[], orders: Order[], mode: "fail-fast" | "collect-all"): Verdict[];
```

Порядок вердиктов — порядок поручений на входе. Поручение, к типу
которого не применима ни одна проверка, проходит (`ok: true`, пустые
списки) — но подумай на собеседовании вслух, что в реальной системе
«ни одной проверки» скорее повод для ошибки конфигурации.

## Пример

```json
checks: [
  { "name": "form",   "priority": 10, "appliesTo": ["payment", "transfer"], "failsFor": [] },
  { "name": "rights", "priority": 9,  "appliesTo": ["payment", "transfer"], "failsFor": ["p2"] },
  { "name": "limits", "priority": 5,  "appliesTo": ["payment"],             "failsFor": ["p2", "p3"] }
],
orders: [
  { "id": "p1", "type": "payment" },
  { "id": "p2", "type": "payment" },
  { "id": "p3", "type": "transfer" }
],
mode: "fail-fast"
```

Результат:

```json
[
  { "id": "p1", "ok": true,  "passed": ["form", "rights", "limits"], "failed": [] },
  { "id": "p2", "ok": false, "passed": ["form"], "failed": ["rights"] },
  { "id": "p3", "ok": true,  "passed": ["form", "rights"], "failed": [] }
]
```

`p2` остановился на правах — до лимитов не дошло; `p3` — перевод,
проверка лимитов к нему не применяется, и его `failsFor` у `limits`
не сыграл.

## Ловушки, которые проверяют случаи

- `failsFor` срабатывает только если проверка вообще применима к
  типу поручения.
- В `collect-all` порядок выполнения тот же, меняется только
  остановка.
- Приоритет при равенстве — порядок объявления.
- Поручение без применимых проверок — ok с пустыми списками.
