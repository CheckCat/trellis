# DDD без фанатизма: агрегаты, инварианты, репозитории, доменные события

Уровень 1. Domain-Driven Design оброс сектантством, но на
собеседовании из него нужны четыре рабочих понятия: единый язык,
ограниченный контекст, агрегат, доменное событие. Урок — про них и
про то, где остановиться.

## Боль: модель, в которой можно всё

`UPDATE cases SET status = 'closed'` доступен из любого места кода —
и однажды массовая операция закрывает обращения без резолюции, а
отчёт комплаенса ловит «закрыто без решения». Правило «закрыть можно
только с резолюцией» существовало — в головах и в одном из трёх
обработчиков. Домен, чьи правила не собраны в одном месте, охраняется
только дисциплиной — то есть никак.

## Единый язык и ограниченный контекст

**Ubiquitous language** — слова бизнеса в коде: `Case`,
`assign`, `escalate`, `resolution` — не `data`, `update`, `flag2`.
Смысл практический: перевод между «языком бизнеса» и «языком кода» —
место, где рождаются баги.

**Bounded context** — граница, внутри которой слова значат одно.
«Клиент» для `cases` — обратившийся с проблемой; для `customers` —
владелец продуктов; для аналитики — строка агрегата. Это **разные
модели**, и попытка сделать «единую модель Клиента на всю компанию» —
известное болото: модель толстеет, все контексты тянут её в разные
стороны. Правильный ход — свои модели в своих контекстах и явные
трансляции между ними. Bounded context — главный кандидат в границу
микросервиса (следующий урок), и у тебя есть живой пример: в твоей
платформе «поручение» для модуля создания и для модуля выгрузок —
разные проекции одной сущности.

## Агрегат: единица согласованности

**Агрегат** — группа объектов, меняющихся **вместе и согласованно**;
**корень агрегата** — единственная точка входа. `Case` с его
событиями — агрегат: снаружи нельзя дописать событие в историю мимо
корня, все изменения — методы корня, и они охраняют **инварианты**:

```ts
class Case {
  close(operatorId: OperatorId, resolution: string) {
    if (this.status === "closed") throw new DomainError("already_closed");
    if (!resolution.trim()) throw new DomainError("resolution_required");
    this.status = "closed";
    this.record(new CaseClosed(this.id, operatorId));
  }
}
```

Инвариант «закрытое — с резолюцией» теперь **не может** быть нарушен:
другого пути к статусу нет (инкапсуляция из урока про ООП, доведённая
до конца).

Два правила проектирования агрегатов, о которых спрашивают:

- **Агрегат = граница транзакции.** Одна транзакция меняет один
  агрегат. Между агрегатами — согласованность через события
  (eventual), не через мегатранзакцию на три агрегата. Отсюда правило
  размера: агрегат — **минимальный** кластер, который должен быть
  согласован немедленно. «Клиент со всеми обращениями» — не агрегат:
  два оператора не могут конфликтовать на всём клиенте из-за разных
  обращений.
- **Ссылки между агрегатами — по id**, не объектами: `Case` хранит
  `customerId`, а не объект клиента, — иначе агрегаты слипаются в
  один граф.

**Репозиторий** в DDD-смысле — сохранение и загрузка агрегата
**целиком**, по одному на агрегат: `CasesRepository.load(id)` /
`save(case)`. Это порт из прошлого урока; ORM-репозитории «по таблице
на класс» — другой, более низкий уровень.

## Доменные события

Факт, случившийся в домене: `CaseClosed`, `CardBlocked`. Агрегат
**записывает** события при изменении, инфраструктура **публикует**
после сохранения — и тут всё сходится с модулем очередей: publish
через outbox в той же транзакции, что и save. События — способ
реагировать на изменение, не зашивая реакцию в агрегат: уведомления
и аудит подписаны, `Case.close` о них не знает (Observer, низкое
зацепление).

## Анемичная модель: всегда ли это плохо

**Анемичная модель** — данные отдельно (структуры), логика отдельно
(сервисы-процедуры). DDD-ортодоксия называет её антипаттерном, но
честный ответ тоньше: для CRUD без инвариантов анемичная модель +
валидация на границе — **нормальна и проще** (справочники, витрины).
Богатая модель с агрегатами окупается там, где есть настоящие
инварианты и переходы состояний — обращения, платежи, лимиты. Это
та же формула «церемонии по сложности», и она отличает практика от
начитавшегося.

## На чём валят

- **Агрегат «Клиент со всем»** — не назвать правило минимальности и
  границу транзакции.
- **Транзакция на два агрегата** — «а как же согласованность?» —
  события и eventual, сага для цепочек (через урок).
- **Инварианты в сервисе при публичных сеттерах** — правило, которое
  можно обойти, — не правило.
- **«Анемичная модель — всегда зло»** — догма; ответ — по наличию
  инвариантов.
- **Единая модель на все контексты** — «Клиент» один на компанию —
  болото, которое сеньор обязан узнать.

## Как ответить за минуту

«Из DDD беру рабочее ядро: единый язык — слова бизнеса в коде;
bounded context — границы, внутри которых модель одна, и разные
контексты имеют разные модели одной сущности; агрегат — кластер
немедленной согласованности с корнем как единственной точкой входа,
инварианты в методах корня, одна транзакция — один агрегат, между
агрегатами — доменные события через outbox; ссылки между агрегатами
— по id; репозиторий — на агрегат. Богатую модель строю там, где
есть инварианты и переходы состояний; для CRUD-справочников честная
анемичная модель проще и лучше».
