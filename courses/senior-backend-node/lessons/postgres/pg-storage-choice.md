# Выбор хранилища: PostgreSQL, MongoDB, Redis, ClickHouse, S3

Уровень 3 по глубине, но вопрос «почему Postgres, а не Mongo» (и
наоборот) звучит постоянно — нужен уверенный каркас ответа.

## Каркас: хранилище выбирается под форму данных и доступ

Не «какая база лучше», а четыре вопроса: какова форма данных
(реляционная, документная, ключ-значение, временной ряд, файлы),
какие запросы (точечные, аналитические, полнотекст), какие гарантии
(транзакции? строгая согласованность?) и какой объём/рост.

## PostgreSQL — по умолчанию

Реляционная модель, настоящие транзакции, богатые запросы — плюс
`jsonb` закрывает большинство «нам нужна гибкая схема». Правило
сеньора: **начинай с Postgres и уходи из него по доказанной причине**.
Это не догма, а экономика: одна технология в проде — это бэкапы,
мониторинг, экспертиза.

## MongoDB — документы

Когда оправдана: данные — естественные документы с вложенностью,
читаемые целиком по ключу (профили, каталоги с разными атрибутами),
схема реально разная у записей, горизонтальный рост встроен
(шардирование из коробки, оно проще постгресового).

Что нужно знать, чтобы не поплыть на уточнениях:

- транзакции есть (многодокументные, с 4.0), но идиома Mongo — так
  спроектировать документ, чтобы **атомарности одного документа
  хватало**;
- индексы, агрегационный pipeline — есть и мощные; «Mongo не умеет
  запросы» — устаревший ответ;
- согласованность настраивается (`readConcern`/`writeConcern` —
  сколько узлов подтверждают);
- денормализация — норма проектирования: копии данных в документе и
  их обновление — твоя забота;
- JOIN-ов в привычном виде нет (`$lookup` ограничен) — данные с
  плотными связями и отчёты «через всё» — не сюда.

Ответ на «почему не Mongo» для «Пульта»: обращения, счета, клиенты —
плотно связанная реляционная модель с транзакциями через несколько
таблиц (обращение + событие + outbox), отчёты с JOIN — профиль
Postgres. Ответ на «почему не Postgres» для чьего-то каталога
товаров с миллионом разных атрибутов — зеркальный.

## Redis — ключ-значение в памяти

Сессии, кэш, счётчики, блокировки, pub/sub. Скорость — сотни тысяч
операций в секунду; цена — данные в памяти (дорого за гигабайт),
персистентность настраиваемо-ослабленная. Redis как **основное**
хранилище — почти всегда ошибка; как вспомогательное — стандарт.
Подробно — следующий модуль.

## ClickHouse — аналитика

Колоночная база: миллиарды строк событий, агрегации за секунды.
Профиль: аналитика по журналу действий операторов, метрики,
клик-стримы. Обратная сторона: точечные обновления и удаления —
не её жанр (append-only мышление), транзакций в OLTP-смысле нет.
Формула: **OLTP в Postgres, OLAP в ClickHouse**, данные едут из
первого во второй через Kafka/ETL. Для аудита «Пульта» на годы —
естественный кандидат.

## S3-совместимое объектное хранилище — файлы

Сканы документов, выгрузки, вложения чата. В базе файлам не место
(раздувают таблицы, бэкапы, WAL); в S3 — байты, в Postgres —
метаданные и ссылка. Доступ клиенту — presigned URL: сервис выдаёт
подписанную ссылку на скачивание/загрузку, байты идут мимо сервиса.

## Elasticsearch/OpenSearch — поиск

Полнотекст с релевантностью, фасеты, «искать как Google» по
обращениям и чатам. Postgres умеет полнотекст (tsvector) — для
скромных нужд его хватает, и это хороший первый ответ; отдельный
поисковый движок — когда релевантность и объёмы становятся продуктом.
Данные в него **дублируются** из основной базы (индексация по
событиям) — это витрина, не источник истины.

## На чём валят

- **«Mongo не держит транзакции»** — держит; устаревшие ответы минусуют.
- **«Возьмём Mongo, потому что схема будет меняться»** — jsonb в
  Postgres закрывает «немного гибкости»; выбор Mongo обосновывается
  документной моделью доступа, а не страхом миграций.
- **Файлы в базе** — раздутые бэкапы и WAL; S3 + метаданные.
- **«Одна база на всё»** и **«под каждую задачу своя база»** — обе
  крайности; каждая дополнительная технология — операционная цена, и
  она называется вслух.
- **Поиск как источник истины** — Elasticsearch теряет данные при
  переиндексации; он витрина.

## Как ответить за минуту

«По умолчанию Postgres: реляционная модель, транзакции, jsonb для
гибких кусков. Mongo — когда данные документные и читаются целиком,
рост горизонтальный, а атомарность документа покрывает нужды. Redis —
кэш, сессии, счётчики, не основное хранилище. ClickHouse — аналитика
по событиям: OLTP в Postgres, OLAP отдельно. Файлы — в S3 с
presigned URL, в базе — метаданные. Поиск — tsvector, пока хватает,
дальше Elasticsearch как витрина. Каждая новая технология —
операционная цена: бэкапы, мониторинг, экспертиза».
