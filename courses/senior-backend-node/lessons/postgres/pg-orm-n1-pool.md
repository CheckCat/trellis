# ORM, N+1 и пул соединений: Prisma, TypeORM, Knex, Drizzle

Уровень 1. Три практических вопроса в одном уроке: чем брать данные из
базы в Node, как не наступить на N+1 уже в ORM и как настроить пул
соединений — тема, которая всплывает на каждом инциденте «база
держит, а сервис лежит».

## Слои абстракции: от драйвера до ORM

- **Драйвер** (`pg`, `postgres.js`) — SQL руками,
  параметризованные запросы, максимум контроля. Параметры — только
  плейсхолдерами (`$1`), никогда конкатенацией: это и есть защита от
  SQL-инъекций (подробнее — в модуле про безопасность).
- **Query builder** (Knex, и на новом витке Drizzle) — SQL,
  собираемый кодом: композиция условий, переиспользование кусков,
  типы. Ты видишь, какой SQL уедет.
- **ORM** (Prisma, TypeORM, Sequelize) — модели и связи вместо SQL:
  быстрые CRUD, миграции, типобезопасность (у Prisma — лучшая в
  экосистеме). Цена — расстояние до реального SQL: ORM может
  сгенерировать то, что ты бы никогда не написал.

Зрелая позиция для собеседования: **это не религия, а спектр** — CRUD
и типовые выборки удобно писать ORM-ом, отчёты, оконные функции и
горячие запросы — сырым SQL или билдером; любой уважающий себя ORM
даёт `$queryRaw`-выход. Красный флаг — команда, которая «не знает,
какой SQL генерирует ORM».

## N+1 в ORM

Модуль API показал N+1 в GraphQL-резолверах; ORM порождает его же
другим путём — **ленивыми связями**:

```ts
const cases = await caseRepo.find();          // 1 запрос
for (const c of cases) {
  console.log((await c.customer).fullName);   // + N запросов
}
```

Каждое обращение к ленивой связи — отдельный SELECT. Сто обращений —
сто одна поездка в базу. Лечения три, по ситуации:

- **eager-загрузка связей одним** запросом с JOIN-ом:
  `find({ relations: ["customer"] })`, `include: { customer: true }`
  у Prisma — один запрос с соединением;
- **два запроса**: выбрать обращения, затем всех клиентов одним
  `WHERE id IN (...)` и склеить в коде — так под капотом делает
  Prisma, и это часто дешевле JOIN-а с дублированием широких строк;
- **батчинг DataLoader-ом** — когда точки доступа разбросаны (GraphQL).

Как N+1 **замечают**: в логах запросов (у любого ORM включается
логирование) — пачки одинаковых SELECT с разными id; в APM — сотни
обращений к базе на один HTTP-запрос. Привычка сеньора — смотреть
количество запросов на запрос API, а не только их длительность.

Вторая классика ORM — **широкие выборки**: `SELECT *` с пятью JOIN,
когда нужно три поля. явный выбор нужных столбцов решает.

## Пул соединений

Соединение с Postgres — это **процесс** на стороне базы: форк,
память, стоимость установления. Открывать соединение на запрос —
самоубийство; держать по соединению на «пользователя» — тоже. Пул —
N живых соединений, которые по очереди обслуживают запросы.

Что нужно понимать:

- **Транзакция живёт на одном соединении.** `BEGIN` через пул, а
  `COMMIT` — на другом соединении — не транзакция. В `pg`:
  `pool.connect()` → все запросы транзакции через этого клиента →
  `release()`. Забытый `release` — утечка соединений: пул пустеет,
  сервис виснет на «ожидании свободного соединения».
- **Размер пула** — не «побольше». У базы предел
  (`max_connections`, по умолчанию 100, и часть занята служебным);
  инстансов сервиса — восемь, у каждого пул 20 — уже 160. Больше
  соединений ≠ больше пропускной способности: ядер у базы конечное
  число, лишние соединения конкурируют и замедляют всех. Ориентир —
  небольшой пул (10–20 на инстанс) и **очередь ожидания с таймаутом**
  в пуле.
- **Симптом исчерпания**: latency растёт ступенькой, база при этом
  скучает. Смотреть метрики пула (занято/ждёт), а не только базы.
- Когда инстансов и сервисов много, между ними и базой ставят
  **внешний пулер** — о нём в уроке про масштабирование Postgres.

## Мелочи, которые спрашивают

- **Prepared statements** — план запроса кэшируется на соединении;
  драйверы делают это сами для параметризованных запросов.
- **Таймаут запроса** — `statement_timeout` на сессии/роли: запрос
  дольше N секунд убивается. Обязателен: один аналитический запрос
  без лимита способен занять соединение на час.
- **Миграции и ORM** — Prisma Migrate/TypeORM migrations удобны, но
  на проде миграции применяются как SQL с ревью — следующий урок
  объяснит почему.

## На чём валят

- **«ORM медленный, поэтому мы пишем всё на сыром SQL»** и **«SQL не
  нужен, есть Prisma»** — обе крайности выдают отсутствие опыта;
  правильный ответ — спектр и выходы на raw.
- **N+1 через ленивые связи** — не увидеть его в описанном коде на
  ревью — минус.
- **Транзакция через пул** (каждый запрос сам берёт соединение) — не
  транзакция.
- **«Поставим пул 200, чтобы не ждать»** — упрётесь в
  max_connections и ядра базы; маленький пул с очередью быстрее.
- **Забытый release клиента** — сервис зависает без ошибок в логах
  базы.

## Как ответить за минуту

«Спектр: драйвер с параметризованным SQL, билдер, ORM — CRUD пишу
ORM-ом, горячее и отчёты — SQL-ом через raw-выход. N+1 в ORM рождают
ленивые связи: лечится include/relations, двумя запросами с IN или
DataLoader-ом; замечается по логу запросов и числу обращений к базе
на один запрос API. Пул: транзакция целиком на одном клиенте с
release в finally, размер — десятки, не сотни, с учётом
max_connections на все инстансы; исчерпание пула видно как рост
latency при скучающей базе. statement_timeout обязателен».
