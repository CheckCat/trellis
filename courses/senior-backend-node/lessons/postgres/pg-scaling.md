# Репликация, лаг реплики, партиционирование, шардирование, pgbouncer

Уровень 2. Один Postgres на хорошем железе тянет больше, чем принято
думать, — и первый правильный ответ на «как масштабировать базу» —
«сначала индексы, запросы и кэш». Но сеньор обязан знать следующие
ступени и их цену.

## Репликация

**Streaming replication**: реплика проигрывает WAL праймери почти в
реальном времени. Режимы:

- **асинхронная** (по умолчанию): праймери отвечает «commit ok», не
  дожидаясь реплик. Быстро; цена — при гибели праймери последние
  транзакции могут не доехать до реплики;
- **синхронная**: коммит ждёт подтверждения реплики
  (`synchronous_commit`, `synchronous_standby_names`). Не теряем
  зафиксированное; цена — латентность каждой записи и зависимость от
  здоровья реплики.

Зачем реплики: **чтение с реплик** (отчёты, списки, аналитика — прочь
с праймери), **failover** (реплика повышается при гибели праймери —
руками или оркестратором вроде Patroni), горячий резерв.

**Лаг реплики** — главный практический вопрос. Реплика отстаёт на
секунды (сеть, тяжёлый WAL, долгий запрос на реплике конфликтует с
проигрыванием). Классический баг: сервис записал обращение в
праймери, тут же прочитал список с реплики — записи нет, оператор в
недоумении. Это read-your-writes проблема, решения:

- критичные к свежести чтения — с праймери (простое правило: «после
  своей записи читай праймери» хотя бы N секунд);
- маршрутизация по типу запроса в слое доступа к данным, а не
  случайно;
- следить за лагом как за метрикой с алёртом.

На собеседовании фраза «чтение с реплик — это eventual consistency
внутри одной системы, и код обязан это учитывать» звучит как опыт.

## Партиционирование

Одна логическая таблица — много физических секций. Декларативно:
`PARTITION BY RANGE (created_at)` — секция на месяц. Зачем:

- **удаление старого — мгновенное**: `DROP TABLE` секции вместо
  `DELETE` миллионов строк с вакуумом после;
- запросы с условием по ключу секционирования читают только свои
  секции (partition pruning);
- обслуживание (вакуум, индексы) — посекционно.

Естественные кандидаты в «Пульте»: `case_events` и журнал аудита —
время-ориентированные, растут бесконечно, старое читается редко и
удаляется по регламенту. Цена: ключ секционирования должен входить в
уникальные ограничения, запросы без условия по ключу читают все
секции, секции надо создавать заранее (автоматизируется).

## Шардирование

Партиционирование — внутри одного сервера; **шардирование** — данные
режутся между независимыми серверами (по клиенту, по диапазону, по
хешу ключа). Это последняя ступень, и цена у неё архитектурная:

- запросы через шарды (`JOIN` по всем клиентам) — больно или никак;
- транзакции через шарды — распределённые (модуль архитектуры
  расскажет, почему их избегают);
- решардинг при росте — отдельный проект; выбор ключа шардирования —
  решение, которое почти нельзя поменять.

Честный ответ на собеседовании: «до шардирования — реплики на чтение,
кэш, партиционирование, вынос холодного; шардирование — когда запись
не помещается в один праймери, и тогда по ключу арендатора/клиента,
либо готовым решением (Citus)». Для «Пульта» с 60 000 обращений в
день шардирование не нужно — уметь сказать «не нужно» тоже
проверяется.

## pgbouncer

Из урока про пул: соединение Postgres — дорогой процесс. Когда
сервисов и инстансов много, их суммарные пулы превышают
`max_connections`. **pgbouncer** — лёгкий пулер между сервисами и
базой: тысячи клиентских соединений мультиплексируются в десятки
серверных.

Режимы — и это спрашивают:

- **session** — клиент держит серверное соединение всю сессию;
  совместимо со всем, экономии мало;
- **transaction** — серверное соединение выдаётся на время
  транзакции. Главный режим; **ломает** всё сессионное: prepared
  statements уровня сессии, `SET` без `LOCAL`, advisory locks
  session-уровня, LISTEN/NOTIFY — следующая транзакция уедет по
  другому соединению;
- **statement** — на один оператор; почти никому.

Формула: «pgbouncer в transaction mode + дисциплина: никакого
сессионного состояния, SET LOCAL внутри транзакций».

## На чём валят

- **«Реплики масштабируют запись»** — только чтение; запись
  масштабирует шардирование.
- **Read-your-writes с реплики** — «записал и не увидел» — надо знать
  и называть решение.
- **«Синхронная репликация просто надёжнее»** — без упоминания цены
  (латентность каждой записи, доступность при смерти реплики) ответ
  неполон.
- **«Партиционирование ускорит все запросы»** — только с условием по
  ключу секционирования; главная выгода — дешёвое удаление старого.
- **pgbouncer transaction mode + prepared statements сессии** —
  классические загадочные ошибки; режим и ограничения идут парой.

## Как ответить за минуту

«Сначала — запросы, индексы, кэш; затем реплики: streaming, обычно
асинхронная — чтение отчётов и списков уходит с праймери, но
появляется лаг и read-your-writes — критичные чтения с праймери,
лаг под алёртом. Время-ориентированные таблицы — декларативное
партиционирование по диапазону: pruning и мгновенный DROP старых
секций. Шардирование — последняя ступень, когда запись не влезает в
праймери: ключ почти не поменять, кросс-шардовые запросы и
транзакции — боль. Соединения при множестве сервисов — pgbouncer в
transaction mode, помня, что он ломает сессионное состояние».
