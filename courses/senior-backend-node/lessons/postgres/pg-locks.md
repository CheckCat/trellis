# Блокировки: FOR UPDATE, SKIP LOCKED, deadlock, оптимистичная блокировка

Уровень 1. Продолжение предыдущего урока: изоляция отвечает «что я
вижу», блокировки — «кто кого ждёт». Вопросы «как взять задачу из
очереди без гонки» и «пессимистичная против оптимистичной» — из
обязательной программы.

## Боль: два оператора берут одно обращение

Обращение видно в общем списке двум операторам. Оба нажимают «взять в
работу» одновременно: оба прочитали `assignee_id IS NULL`, оба
записали себя. Выжила одна запись — второй оператор работает с
обращением, которое ему уже не принадлежит. Это lost update из
прошлого урока, теперь решаем.

## Пессимистично: FOR UPDATE

`SELECT ... FOR UPDATE` читает строки и **блокирует их до конца
транзакции**: второй такой же SELECT встанет и подождёт.

```sql
BEGIN;
SELECT * FROM cases WHERE id = 7 FOR UPDATE;  -- строка наша
-- проверили, что assignee_id IS NULL, решили
UPDATE cases SET assignee_id = 3, status = 'in_progress' WHERE id = 7;
COMMIT;
```

Второй оператор дождётся коммита, прочитает уже занятую строку и
получит честное «уже взято». Модификаторы, которые нужно знать:

- `FOR NO KEY UPDATE` — мягче: не конфликтует со вставкой ссылающихся
  строк (FK); для «обновлю не-ключевые поля» правильнее он;
- `FOR SHARE` — «не меняйте, пока читаю», разделяемая;
- `NOWAIT` — не ждать, а сразу ошибку;
- `SKIP LOCKED` — **пропустить занятые строки**. Из этого модификатора
  сделаны очереди задач в Postgres: десять воркеров делают
  `SELECT ... WHERE status = 'queued' ORDER BY priority DESC, id
  LIMIT 5 FOR UPDATE SKIP LOCKED` — каждый получает **свои** пять
  задач, не ожидая соседей и не беря чужие. Практика после этого
  урока — ровно про это.

Блокировки строк живут до конца транзакции — ещё одна причина держать
транзакции короткими. Табличные блокировки (их берёт DDL) — тема
урока про миграции.

## Deadlock

Транзакция A заблокировала строку 1 и хочет строку 2; транзакция B —
наоборот. Обе ждут вечно. Postgres обнаруживает цикл ожидания
(deadlock detector, срабатывает через `deadlock_timeout`, по
умолчанию 1 с) и убивает одну из транзакций с ошибкой 40P01 — её
нужно **повторить** (снова ретрай в коде, как с сериализацией).

Профилактика лучше лечения: **захватывать строки в одном и том же
порядке**. Перевод между счетами блокирует счета в порядке
возрастания id — тогда циклов не бывает. Массовые операции сортируют
свои цели; два разных пути кода к одним строкам согласуют порядок.

## Оптимистично: версия

Пессимистичная блокировка честна, но держит других в ожидании и
требует открытой транзакции вокруг «прочитал-решил-записал». Когда
между чтением и записью — **человек** (оператор открыл карточку,
думал минуту, нажал «Сохранить»), транзакцию на минуту не откроешь.

Оптимистичная блокировка: конфликт не предотвращаем, а **обнаруживаем**.
В строке — счётчик `version`; читаем строку вместе с версией, при
записи проверяем, что версия не изменилась, и увеличиваем её:

```sql
UPDATE cases
SET assignee_id = 3, status = 'in_progress', version = version + 1
WHERE id = 7 AND version = 4;
```

Ноль обновлённых строк — кто-то успел раньше: отвечаем 409, клиент
перечитывает и решает заново. Ни ожиданий, ни открытых транзакций;
цена — конфликтующий проигравший переделывает работу. Тот же приём в
HTTP-обличье — `ETag` + `If-Match` из модуля API.

Выбор формулой: **конкуренция редкая или между чтением и записью
человек — оптимистичная; конкуренция плотная и всё в одной транзакции
— пессимистичная; раздача работы воркерам — FOR UPDATE SKIP LOCKED.**

## Advisory locks

Блокировки не строк, а **чисел, которые значат то, что ты решил**:
`pg_advisory_lock(42)` / `pg_try_advisory_lock(42)`. База ничего не
знает про смысл — это распределённый мьютекс на произвольный ресурс:
«регламентная выгрузка №42 уже запущена одним из инстансов».
Session-уровень требует не забыть unlock (или разорвать соединение);
transaction-уровень (`pg_advisory_xact_lock`) отпускается сам.
Альтернатива Redis-блокировкам, когда Postgres уже есть, — сравним их
в модуле про кэширование.

## Атомарные обновления без блокировок вовсе

Самый недооценённый ответ: часто блокировка не нужна — нужен
**атомарный UPDATE**. «Уменьшить лимит на 10000, но не ниже нуля»:

```sql
UPDATE cards SET daily_limit = daily_limit - 10000
WHERE id = 5 AND daily_limit >= 10000;
```

Проверка и изменение — один оператор, гонки нет по построению. Ноль
строк — не хватило лимита. Это же правило из урока про
идемпотентность: абсолютные и условные операции вместо
«прочитал-посчитал-записал».

## На чём валят

- **«Проверю SELECT-ом, потом UPDATE-ну»** — между ними гонка; либо
  FOR UPDATE, либо версия, либо условие прямо в UPDATE.
- **SKIP LOCKED не знают** — а это стандартный ответ на «очередь в
  Postgres» и вопрос «как воркеры не подерутся».
- **«Deadlock — это баг Postgres»** — это цикл ожидания в твоём
  порядке захвата; лечится порядком, обнаруживается детектором,
  повторяется кодом.
- **Оптимистичная версия без обработки нуля строк** — конфликт молча
  теряется; ноль обновлённых строк — это ответ 409, а не успех.
- **Advisory lock session-уровня без unlock** — ресурс заперт до
  разрыва соединения, которое живёт в пуле вечно.

## Как ответить за минуту

«Гонка "прочитал-изменил" решается тремя способами: пессимистично —
SELECT FOR UPDATE в транзакции, второй ждёт и видит уже занятую
строку; оптимистично — поле version в WHERE и +1 в SET, ноль строк —
конфликт, 409 и перечитать, — правильно, когда между чтением и
записью человек; или атомарным UPDATE с условием, когда проверку
можно выразить в WHERE. Раздача задач воркерам — FOR UPDATE SKIP
LOCKED: каждый берёт незанятые. Deadlock — цикл ожидания: Postgres
убьёт одну транзакцию, код повторит, профилактика — единый порядок
захвата. Advisory locks — мьютекс на смысл, вроде "выгрузка уже
запущена"».
