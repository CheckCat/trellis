# Практика: частичный индекс под горячий запрос

Экран «мои открытые обращения» выполняет запрос:

```sql
SELECT id, topic, priority, created_at
FROM cases
WHERE assignee_id = $1 AND status IN ('open', 'in_progress')
ORDER BY created_at DESC
LIMIT 50;
```

Закрытые обращения — большинство таблицы, экрану они не нужны.

## Задание

Создай **частичный** индекс с именем `cases_open_by_assignee`, который
обслуживает этот запрос целиком:

- таблица `cases`;
- ключевые столбцы: `assignee_id`, затем `created_at DESC` — равенство
  слева, сортировка последней;
- условие индекса: `status in ('open', 'in_progress')` — ровно то
  подмножество, по которому ходит запрос.

Имя индекса — часть задания: проверка ищет индекс по имени.

Как убедиться, что получилось: выполни в песочнице свой
`CREATE INDEX`, а затем тем же запуском —

```sql
EXPLAIN SELECT id, topic, priority, created_at
FROM cases
WHERE assignee_id = 1 AND status IN ('open', 'in_progress')
ORDER BY created_at DESC LIMIT 50;
```

(песочница пересевается перед каждой попыткой, поэтому индекс и
EXPLAIN должны идти в одной отправке; показывается результат
последнего оператора). На маленькой таблице песочницы планировщик
может предпочесть Seq Scan — это нормально и само по себе не ошибка:
проверка смотрит на определение индекса, а не на план.
