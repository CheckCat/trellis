# Миграции без даунтайма: expand/contract и блокировки DDL

Уровень 1. «Как добавить колонку в таблицу на 50 миллионов строк, не
останавливая сервис?» — вопрос, по которому мгновенно видно, ловил ли
человек прод за руку. Правильный ответ состоит из знания блокировок
DDL и дисциплины expand/contract.

## Боль: ALTER TABLE положил «Пульт» на 40 секунд

Миграция `ALTER TABLE cases ADD COLUMN sla_deadline timestamptz` на
большой таблице — и все запросы к обращениям встали. Почему: DDL
берёт **ACCESS EXCLUSIVE** — самую тяжёлую табличную блокировку,
несовместимую даже с SELECT. Сама она нужна на миллисекунды, но есть
два усилителя катастрофы:

- **очередь блокировок**: если ALTER ждёт, пока закончится чей-то
  длинный SELECT, то **все** запросы после ALTER выстраиваются за
  ним — короткое ожидание превращается в остановку таблицы. Лечение:
  `lock_timeout` (например, 2 секунды) на сессии миграции — не
  дождался блокировки, упал, повторим позже; это правило номер один
  любой прод-миграции;
- **работа под блокировкой**: некоторые ALTER не отпускают её
  мгновенно, а переписывают таблицу.

Что быстро, а что переписывает таблицу — это спрашивают прямо:

- **быстро (только метаданные)**: `ADD COLUMN` без default;
  `ADD COLUMN ... DEFAULT <константа>` — быстро начиная с Postgres 11;
  `DROP COLUMN`; расширение `varchar`;
- **медленно (перепись или полное сканирование под блокировкой)**:
  `ALTER COLUMN TYPE` (кроме совместимых), `ADD COLUMN` с volatile
  default, `SET NOT NULL` без подготовки (сканирует всю таблицу;
  обход: `ADD CONSTRAINT ... CHECK (col IS NOT NULL) NOT VALID` →
  `VALIDATE CONSTRAINT` — валидация идёт уже без тяжёлой блокировки);
- **индексы** — только `CREATE INDEX CONCURRENTLY` (урок про
  индексы), и он не работает внутри транзакции — значит, такая
  миграция помечается «без транзакции» в инструменте миграций.

## Expand/contract: совместимость версий кода

Даже мгновенный DDL не решает главного: во время деплоя **живут две
версии кода одновременно** (rolling-деплой), и обе ходят в одну базу.
Значит, каждая миграция обязана быть совместима и со старым, и с
новым кодом. Отсюда трёхтактный паттерн:

1. **Expand** — расширить: добавить новое (колонку, таблицу),
   ничего не ломая. Старый код нового не видит и живёт как жил.
2. **Migrate** — переехать: новый код пишет в оба места и читает
   по-новому; фоновая задача переливает старые данные пачками (не
   одним UPDATE на 50 млн строк — он возьмёт блокировки и раздует
   WAL, а пачками по 10–50 тысяч со сном между ними).
3. **Contract** — сжать: когда метрики показывают, что старое не
   читается, — убрать двойную запись, затем отдельным релизом
   удалить старую колонку.

Переименование колонки в этой дисциплине — не `RENAME` (он ломает
старый код мгновенно), а «добавить новую → двойная запись → перелить
→ переключить чтение → удалить старую». Скучно, зато без даунтайма —
и это ровно тот ответ, которого ждут.

Правила процесса вокруг:

- миграции — **код в репозитории**, применяются CI/CD, а не руками;
  у каждой есть откат (или явная пометка, что откат — вперёд);
- порядок в деплое: сначала миграция (expand), потом код; contract —
  только после подтверждения метриками;
- **не смешивать** DDL и массовое обновление данных в одной миграции:
  DDL быстрый и транзакционный (в Postgres DDL транзакционен — это
  его сила), перелив данных — долгий и пачками.

## На чём валят

- **«ADD COLUMN заблокирует таблицу надолго»** — нет: блокировка
  тяжёлая, но мгновенная; страшна очередь за ней — поэтому
  lock_timeout и ретраи.
- **«Добавлю NOT NULL колонку сразу»** — SET NOT NULL сканирует
  таблицу; через CHECK NOT VALID → VALIDATE.
- **`UPDATE table SET new_col = old_col` одним махом** — блокировки,
  WAL, реплики захлебнутся; пачками.
- **RENAME COLUMN в rolling-деплое** — старая версия кода падает в ту
  же секунду.
- **«Откатим миграцию, если что»** — данные, записанные новой формой,
  откат не вернёт; план отката продумывается до, а часто честный
  ответ — «откат вперёд» (roll forward).

## Как ответить за минуту

«DDL берёт ACCESS EXCLUSIVE; сам по себе ADD COLUMN мгновенен, но
очередь за блокировкой останавливает таблицу — поэтому lock_timeout и
повтор. Знаю, что переписывает таблицу: смена типа, volatile default;
SET NOT NULL — через CHECK NOT VALID и VALIDATE; индексы — только
CONCURRENTLY, вне транзакции. Деплой держит две версии кода, поэтому
expand/contract: добавить новое → двойная запись и перелив пачками →
переключить чтение → удалить старое отдельным релизом; переименование
— тем же путём, никогда RENAME. Миграции — код с ревью, применяются
конвейером, большие обновления данных отделены от DDL».
