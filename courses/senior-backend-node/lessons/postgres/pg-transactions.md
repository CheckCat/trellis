# Транзакции, уровни изоляции, аномалии и MVCC

Уровень 1. «Расскажите про уровни изоляции» — вопрос, который звучит
на каждом собеседовании бэкендера. Слабый ответ — перечислить четыре
названия; сильный — объяснить, какие аномалии какой уровень
пропускает, что из этого правда в Postgres и почему читатели не
блокируют писателей.

## Боль: перевод между счетами

Списать с одного счёта и зачислить на другой — два UPDATE. Упади
процесс между ними — деньги исчезли. Транзакция делает из двух
операций одну: либо обе, либо ни одной.

ACID по-честному, а не по заучке:

- **Atomicity** — всё или ничего: откат отменяет все изменения
  транзакции.
- **Consistency** — транзакция переводит базу из одного согласованного
  состояния в другое; сторожат это ограничения (CHECK, FK) и твоя
  логика.
- **Isolation** — параллельные транзакции не видят промежуточных
  состояний друг друга. Насколько «не видят» — и есть уровни
  изоляции.
- **Durability** — зафиксированное переживает сбой: WAL пишется на
  диск до ответа «commit ok».

## Аномалии и уровни

Аномалии, через которые определяются уровни:

- **dirty read** — увидеть незафиксированное чужое;
- **non-repeatable read** — прочитать строку дважды и получить разное
  (между чтениями кто-то закоммитил UPDATE);
- **phantom read** — повторный запрос по условию возвращает новые
  строки;
- **lost update** — два «прочитал-изменил-записал» поверх друг друга:
  выжила только одна правка;
- **write skew** — две транзакции читают пересекающиеся данные и
  пишут в разные места, вместе нарушая инвариант (классика: два
  врача одновременно снимают с себя дежурство, каждый проверил «есть
  второй дежурный»).

Уровни в Postgres:

| Уровень | Что даёт | Чего не ловит |
|---|---|---|
| Read Committed (по умолчанию) | видишь только зафиксированное; каждый **оператор** — свежий снимок | non-repeatable, phantom, lost update, write skew |
| Repeatable Read | один снимок на всю **транзакцию**; апдейт поверх изменённой другим строки — ошибка сериализации | write skew |
| Serializable | как если бы транзакции шли по одной: ловит и write skew (SSI — отслеживание зависимостей) | ничего, но платишь ошибками сериализации и накладными |

Тонкости, которые отличают знание Postgres от знания учебника:

- **Read Uncommitted в Postgres не существует** как поведение: попросишь
  — получишь Read Committed. Dirty read невозможен в принципе.
- В Postgres **phantom read не случается уже на Repeatable Read**
  (снимок на транзакцию), хотя стандарт SQL его там допускает.
- Repeatable Read и Serializable отвечают ошибкой
  `serialization failure` (40001) — и код обязан **повторять**
  транзакцию. Уровень изоляции без ретрая в коде — недоделка.
- Уровень задаётся на транзакцию: `BEGIN ISOLATION LEVEL REPEATABLE
  READ`. Повышать глобально — платить за всё подряд.

Lost update на Read Committed — главный практический риск: два
оператора одновременно редактируют лимит карты через
«прочитал-показал-записал». Решается не уровнем изоляции, а явно:
атомарным UPDATE (`SET daily_limit = 50000 WHERE id = ...` без чтения),
`SELECT FOR UPDATE` или оптимистичной версией — следующий урок.

## MVCC: почему читатели не блокируют писателей

Postgres не правит строку на месте. UPDATE создаёт **новую версию**
строки; у каждой версии — отметки «с какой транзакции видна» (xmin) и
«с какой невидна» (xmax). Каждая транзакция смотрит на базу через
**снимок**: множество транзакций, которые для неё «уже случились».
Отсюда:

- читатель читает свою версию строки, даже если писатель прямо сейчас
  делает UPDATE, — **чтение не ждёт запись, запись не ждёт чтение**;
- ждут друг друга только **две записи одной строки**;
- откат дёшев: новые версии просто остаются невидимыми.

Цена MVCC — **мёртвые версии**. Их убирает VACUUM (autovacuum):
помечает место переиспользуемым, обновляет карту видимости (без неё
нет Index Only Scan) и защищает от переполнения счётчика транзакций
(wraparound — редкий, но фатальный сценарий, о котором стоит знать
слово). Таблица, которую часто обновляют и редко вакуумят, пухнет —
это называют **bloat**: место не возвращается ОС, сканы дорожают.

Отсюда же вред **длинных транзакций**: пока жива транзакция со старым
снимком, VACUUM не может убрать версии, которые ей ещё видны, — bloat
растёт по всей базе. Открытая «на подумать» транзакция аналитика или
забытый `BEGIN` в коде — реальный источник инцидентов. Правила:
транзакции короткие; **никаких внешних вызовов внутри транзакции**
(HTTP-запрос на 30 секунд держит соединение, блокировки и снимок);
`idle_in_transaction_session_timeout` включён.

## Как это выглядит в коде сервиса

Транзакция привязана к **соединению**: взять клиента из пула, `BEGIN`,
выполнить всё на этом клиенте, `COMMIT`/`ROLLBACK`, вернуть клиента.
Типичная ошибка в Node — выполнять запросы транзакции через пул
(каждый запрос — другое соединение, транзакции нет). Об этом ещё раз
в уроке про пул.

## На чём валят

- **«Postgres по умолчанию Serializable»** — Read Committed.
- **«Repeatable Read защитит от двойного списания лимита»** — от lost
  update поверх изменённой строки — да, ошибкой сериализации, но без
  ретрая в коде это просто 500. А write skew не ловится и там.
- **«Читатели блокируют писателей, поэтому отчёты тормозят OLTP»** — в
  Postgres не блокируют (MVCC); отчёты вредят иначе: длинный снимок
  мешает VACUUM.
- **«VACUUM — это дефрагментация, можно отключить»** — это уборка
  мёртвых версий, карта видимости и защита от wraparound; отключение
  автовакуума — путь к инциденту.
- **HTTP-вызов внутри транзакции** — держит соединение и блокировки на
  всё время чужого таймаута.

## Как ответить за минуту

«Postgres по умолчанию Read Committed: каждый оператор видит свежий
снимок — возможны non-repeatable read и lost update; Repeatable Read
даёт снимок на транзакцию и ошибку сериализации при конфликте записи,
Serializable ловит ещё и write skew — оба требуют ретрая в коде.
Dirty read в Postgres невозможен. Под капотом MVCC: UPDATE создаёт
новую версию строки, читатели и писатели не блокируют друг друга,
ждут только две записи одной строки. Цена — мёртвые версии: VACUUM,
bloat, и вред длинных транзакций, которые держат снимок. Транзакции
короткие, внешних вызовов внутри нет, lost update решаю атомарным
UPDATE, FOR UPDATE или версией».
