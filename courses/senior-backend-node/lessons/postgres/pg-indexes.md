# Индексы: B-tree, составные, частичные, покрывающие и EXPLAIN

Уровень 1. Самая спрашиваемая тема по базам. Проверяют не «что такое
индекс», а умеешь ли ты подобрать индекс под конкретный запрос и
прочитать план, когда база его не использует.

## Боль: список обращений за 4 секунды

Экран «мои открытые обращения» делает:

```sql
SELECT * FROM cases
WHERE assignee_id = $1 AND status IN ('open', 'in_progress')
ORDER BY created_at DESC LIMIT 50;
```

На миллионе обращений без индекса это последовательное чтение всей
таблицы — Seq Scan — на каждый экран каждого оператора. База занята
перелопачиванием, все остальные запросы ждут.

## B-tree: что он умеет

Индекс по умолчанию — B-tree: сбалансированное дерево отсортированных
значений со ссылками на строки. Отсюда всё, что он умеет:

- **равенство** (`= $1`) — спуск по дереву;
- **диапазон** (`>`, `<`, `BETWEEN`, `LIKE 'abc%'` — но не
  `LIKE '%abc'`: по суффиксу дерево не спускается);
- **сортировку** — данные в индексе уже упорядочены; `ORDER BY` по
  индексному порядку не сортирует вовсе.

**Составной индекс** `(a, b, c)` работает слева направо — как
телефонная книга «фамилия, имя»: найти по фамилии — да, по имени без
фамилии — нет. Правило: **равенства слева, диапазон или сортировка —
последним**. Под запрос выше:

```sql
CREATE INDEX ON cases (assignee_id, status, created_at DESC);
```

`assignee_id` — равенство, `status` — равенство по списку,
`created_at` — сортировка. Индекс `(created_at, assignee_id)` этому
запросу почти бесполезен: по первому столбцу нет условия равенства.

**Частичный индекс** — с условием WHERE:

```sql
CREATE INDEX ON cases (assignee_id, created_at DESC)
WHERE status IN ('open', 'in_progress');
```

Закрытых обращений — 95 % таблицы, и они этому экрану не нужны.
Частичный индекс в разы меньше, быстрее и дешевле в поддержке;
условие запроса должно **включать** условие индекса, иначе планировщик
его не возьмёт. Это любимый приём для «горячего подмножества»:
открытые обращения, неопубликованный outbox, задачи в статусе queued.

**Покрывающий индекс** — `INCLUDE (столбцы)`: данные, нужные ответу,
лежат прямо в индексе, и база не ходит в таблицу вовсе — Index Only
Scan. Работает, пока страницы «видимы всем» (карта видимости
обновляется VACUUM-ом) — поэтому Index Only Scan на свежеизменённых
данных всё равно заглядывает в таблицу.

**Не-B-tree, о которых спрашивают:** GIN — для «содержит»: `jsonb`
(`payload @> '{"channel":"chat"}'`), массивы, полнотекстовый поиск;
GiST/SP-GiST — геометрия и диапазоны; BRIN — огромные таблицы,
упорядоченные физически (журналы по времени): индекс в тысячи раз
меньше B-tree. Хеш-индекс почти никогда: только равенство, и B-tree
не хуже.

## EXPLAIN: читать план

`EXPLAIN` показывает план, `EXPLAIN ANALYZE` — выполняет и показывает
факты. Узлы, которые нужно узнавать:

- **Seq Scan** — чтение всей таблицы. Не всегда зло: для маленькой
  таблицы или выборки в половину строк это дешевле индекса.
- **Index Scan** — спуск по индексу + походы в таблицу за строками.
- **Index Only Scan** — всё из индекса (см. выше про видимость).
- **Bitmap Index Scan + Bitmap Heap Scan** — индекс собирает битовую
  карту страниц, затем страницы читаются пачкой: середина между
  точечным Index Scan и Seq Scan, характерно для условий с многими
  совпадениями или объединения двух индексов.
- **Nested Loop / Hash Join / Merge Join** — соединения: вложенный
  цикл хорош при маленькой внешней стороне и индексе на внутренней;
  hash — общий случай; merge — обе стороны отсортированы.

На что смотреть в ANALYZE: **rows ожидаемые против фактических**
(расхождение на порядки — устаревшая статистика: `ANALYZE table`),
**loops** (Nested Loop с loops=100000 — вот твой N+1 внутри одного
запроса), Buffers (`EXPLAIN (ANALYZE, BUFFERS)`) — сколько страниц
прочитано.

**Почему индекс не используется** — стандартный вопрос:

- по столбцу применена функция: `WHERE lower(email) = $1` не берёт
  индекс по `email` — нужен функциональный индекс по `lower(email)`;
- несоответствие типов (`text` против `varchar` — ок, но `int` в
  строке — приведение отключает индекс);
- ведущий столбец составного индекса не в условии;
- выборка слишком большая — Seq Scan честно дешевле;
- статистика устарела после массовой загрузки.

## Цена индекса

Индекс — не бесплатный кэш. Каждая запись в таблицу обновляет **все**
её индексы: десять индексов — десятикратная цена вставки, плюс место,
плюс WAL при репликации. Отсюда дисциплина: индексы создаются под
реальные запросы, а неиспользуемые находятся через
`pg_stat_user_indexes` (idx_scan = 0) и удаляются.

Создание индекса на живой таблице — `CREATE INDEX CONCURRENTLY`:
обычный `CREATE INDEX` держит блокировку записи на всё время
построения, и на большой таблице это простой сервиса. CONCURRENTLY
строит в два прохода без блокировки записи; цена — дольше, нельзя в
транзакции, при обрыве остаётся invalid-индекс, который нужно
удалить. Это слово обязано прозвучать в любом ответе про индексы на
проде.

## На чём валят

- **«Повешу индекс на каждый столбец»** — цена записи и место; индексы
  — под запросы, составные — по правилу «равенства слева».
- **«Index Scan всегда лучше Seq Scan»** — для половины таблицы
  последовательное чтение дешевле; планировщик не глуп, он считает
  стоимость.
- **`WHERE lower(email) = ...`** не использует индекс по email —
  нужен функциональный.
- **CREATE INDEX без CONCURRENTLY на проде** — блокировка записи на
  время построения.
- **«ORDER BY требует сортировки»** — не требует, если порядок даёт
  индекс; это половина смысла составного индекса с DESC.

## Как ответить за минуту

«B-tree умеет равенство, диапазон, префикс и сортировку; составной —
слева направо: равенства в начало, сортировка последней. Частичный
индекс — под горячее подмножество вроде открытых обращений;
покрывающий с INCLUDE — Index Only Scan, пока карта видимости свежая.
GIN — для jsonb и полнотекста, BRIN — для огромных журналов по
времени. Диагностика — EXPLAIN ANALYZE: смотрю тип скана, ожидаемые
против фактических rows, loops; индекс не берётся из-за функции по
столбцу, чужого ведущего столбца или большой выборки. Каждая запись
платит за все индексы, на проде — только CREATE INDEX CONCURRENTLY».
