# Streams и backpressure: почему pipe без pipeline течёт

Уровень 1. Потоки — второй по популярности вопрос про Node после
цикла событий, и единственная тема, где даже опытные бэкендеры
регулярно ошибаются в проде. Вопрос «что такое backpressure» —
проверка, эксплуатировал ли ты что-то с большими данными.

## Боль: 2 ГБ в память

Сервис `bulk-ops` отдаёт оператору выгрузку реестра — CSV на два
гигабайта. Наивный код:

```js
const data = await fs.promises.readFile(path);
res.send(data);
```

Два гигабайта в куче на каждый такой запрос. Три оператора запросили
выгрузку одновременно — шесть гигабайт, процесс убит по лимиту памяти
контейнера, и вместе с выгрузками умерли все остальные запросы этого
инстанса. Та же история с загрузкой: собрать тело запроса в буфер,
потом разобрать.

Потоки решают это одним принципом: **обрабатывать данные кусками, не
загружая всё в память**. Файл на два гигабайта читается кусками по 64
КБ; память — константа, не зависящая от размера файла.

## Четыре вида потоков

- **Readable** — источник: файл на чтение, входящий HTTP-запрос
  (`req`), сокет, ответ базы построчно.
- **Writable** — приёмник: файл на запись, исходящий HTTP-ответ
  (`res`), сокет, `process.stdout`.
- **Duplex** — и то и другое, независимо: TCP-сокет.
- **Transform** — Duplex, где выход вычисляется из входа: `gzip`,
  шифрование, парсер CSV, любой «прочитал — преобразовал — отдал».

`req` и `res` в `http` — тоже потоки, и это ключ к пониманию, как
фреймворки читают тело: они подписываются на `data` и собирают куски.
Именно поэтому у тела есть лимит размера — иначе один клиент собирает
тебе в памяти гигабайт.

**objectMode** — поток передаёт не байты, а объекты: строки таблицы из
базы, записи из CSV. `highWaterMark` тогда считается в объектах (16 по
умолчанию), а не в байтах (64 КБ для обычных, 16 КБ для
`fs`-потоков).

## Backpressure

Производитель пишет быстрее, чем потребитель читает. Файл читается со
скоростью диска — сотни мегабайт в секунду; клиент по сети принимает
десять. Куда деваются разница? В буфер потока-приёмника. Без
ограничения буфер растёт, пока не кончится память — то есть тот же
инцидент, что и с `readFile`, только медленнее.

Механизм: `writable.write(chunk)` возвращает **`false`**, когда
внутренний буфер превысил `highWaterMark`. Это не ошибка и не запрет:
писать можно дальше, буфер продолжит расти. Это **сигнал** —
«притормози». Правильная реакция: перестать читать источник и ждать
событие `drain`, которое приходит, когда буфер опустел. Потом
продолжить.

```js
function writeAll(readable, writable) {
  readable.on("data", (chunk) => {
    if (!writable.write(chunk)) {
      readable.pause();
      writable.once("drain", () => readable.resume());
    }
  });
  readable.on("end", () => writable.end());
}
```

Так руками почти никто не пишет — за это отвечают `pipe` и `pipeline`.
Но понимать, что внутри, обязательно: вопрос «что вернёт write и что
с этим делать» — стандартный.

## pipe против pipeline

`readable.pipe(writable)` — делает backpressure автоматически, но **не
пробрасывает ошибки**. Ошибка в одном потоке не закрывает остальные:
файл открыт, сокет висит, память не освобождена. На каждый поток
приходится вешать свой `on('error')` и вручную уничтожать соседей. В
проде так не делают.

`stream.pipeline(a, b, c, callback)` — или промисная версия из
`node:stream/promises` — прокидывает ошибки в одно место и при ошибке
любого потока **уничтожает все** потоки цепочки. Это правильный
инструмент; `pipe` остался для обратной совместимости.

```js
import { pipeline } from "node:stream/promises";
import { createGzip } from "node:zlib";

await pipeline(
  fs.createReadStream("registry.csv"),
  createGzip(),
  res,
);
```

Три строки — и файл любого размера уходит клиенту сжатым, с
backpressure по сети и с корректной уборкой при обрыве соединения.
Заголовки `Content-Type` и `Content-Encoding` — отдельно;
`Content-Length` неизвестен, ответ уйдёт chunked.

## Async-итерация

Современный способ читать поток — `for await`:

```js
for await (const chunk of fs.createReadStream(path)) {
  // chunk — Buffer
}
```

Backpressure здесь встроенный: следующий кусок не читается, пока тело
цикла не отработало. Для построчного чтения — `node:readline`:

```js
import { createInterface } from "node:readline";
for await (const line of createInterface({ input: stream })) { /* ... */ }
```

Но помни: `chunk` — это кусок **байтов**, а не кусок текста. Граница
куска проходит где угодно: посреди строки, посреди многобайтового
символа UTF-8. Разбить кусок по `\n` и обработать — ошибка, которую
делают все в первый раз: последняя «строка» куска на самом деле
начало строки, продолжение которой в следующем куске. Следующая
практика ровно про это. А разрезать UTF-8 по байтам нельзя — для
текста между кусками используют `string_decoder` или `setEncoding`.

## События, которые нужно знать

- `data` — пришёл кусок (переводит Readable в flowing-режим).
- `end` — Readable закончился: данных больше не будет.
- `finish` — Writable записал всё, что ему дали через `end()`.
- `close` — ресурсы освобождены (дескриптор закрыт).
- `error` — везде; без слушателя — падение процесса.
- `drain` — буфер Writable опустел, можно писать снова.

Мнемоника: **end — про чтение, finish — про запись**. На собеседовании
их путают.

## Где потоки в «Пульте»

- Выгрузка реестра: `pipeline(запрос к базе построчно, форматтер CSV,
  gzip, res)`. Память константна, старт ответа — мгновенный.
- Загрузка реестра оператором: `pipeline(req, парсер строк, валидатор,
  писатель в базу пачками)`. Тело не собирается целиком.
- Проксирование файлов из хранилища через BFF: `pipeline(ответ
  хранилища, res)` — BFF не держит файл в памяти.
- Логи: `pino` пишет в `process.stdout` — тоже поток, и если stdout
  медленный (терминал, медленный сборщик логов), backpressure
  замедлит сервис. Поэтому в проде логи отправляют асинхронно.

## На чём валят

- **«write вернул false — значит запись не удалась».** Нет, это сигнал
  притормозить. Запись в буфер произошла.
- **«pipe и pipeline — одно и то же».** pipe не пробрасывает ошибки и
  не убирает за собой; pipeline — пробрасывает и уничтожает всю
  цепочку.
- **«Разобью chunk по переводу строки».** Граница куска не совпадает с
  границей строки; последний фрагмент нужно нести в следующий кусок.
- **«end и finish — синонимы».** end — Readable кончился, finish —
  Writable дописал.
- **«Стримы нужны только для файлов».** req, res, сокеты, ответ базы,
  stdout — всё потоки; тело запроса читается потоком любым
  фреймворком.

## Как ответить за минуту

«Поток — обработка данных кусками с константной памятью. Четыре вида:
Readable, Writable, Duplex, Transform; req и res — тоже потоки.
Backpressure: write возвращает false, когда буфер превысил
highWaterMark, — сигнал перестать читать источник до события drain.
pipe делает это автоматически, но не пробрасывает ошибки; в проде
только pipeline — он закрывает всю цепочку при ошибке. Читать удобно
через for await; кусок — это байты, граница проходит где угодно,
поэтому строки собираются с переносом хвоста».
