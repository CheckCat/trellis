# Что такое Node.js: V8, libuv и один поток

Уровень 1. Это первый вопрос почти любого собеседования по Node, и
задают его не ради определения. Интервьюер хочет услышать, понимаешь ли
ты, **где** в Node один поток, а где их много, и что из этого следует
для сервера под нагрузкой.

## Боль: почему сервер на одном потоке вообще работает

Классический сервер — Apache старой школы, Java-сервлеты до реактивной
эры — на каждое соединение выделяет поток. Поток ждёт ответа базы,
ждёт диска, ждёт сети — и всё это время занимает память и время
планировщика ОС. Десять тысяч соединений — десять тысяч потоков, и
большинство из них спят.

Наблюдение, на котором построен Node: сервер почти всё время **ждёт**
ввода-вывода, а не считает. Если вместо «поток ждёт» сделать «поток
подписался на завершение и пошёл обслуживать другого», один поток
обслужит тысячи соединений. Цена — код должен быть написан так, чтобы
никогда не ждать синхронно. Именно поэтому в Node всё асинхронно: не из
любви к колбэкам, а потому что синхронное ожидание убивает единственный
поток.

## Из чего состоит Node

Три части, и на собеседовании их нужно уметь разделить.

**V8** — движок JavaScript от Chrome. Компилирует JS в машинный код,
управляет памятью (куча, сборщик мусора). V8 ничего не знает о файлах,
сокетах и таймерах: в браузере это даёт Web API, в Node — следующие два
слоя.

**libuv** — библиотека на C, которая даёт Node цикл событий и
асинхронный ввод-вывод. Она умеет два принципиально разных способа не
ждать:

- **Сетевой ввод-вывод** идёт через механизмы ОС — `epoll` в Linux,
  `kqueue` в macOS, IOCP в Windows. Поток говорит ОС «разбуди, когда на
  любом из этих десяти тысяч сокетов появятся данные», и ОС будит. Ни
  одного дополнительного потока.
- **Файловый ввод-вывод, DNS-резолв через `getaddrinfo`, часть crypto
  (`pbkdf2`, `scrypt`, `randomBytes`), zlib** — операции, для которых у
  ОС нет удобного асинхронного интерфейса. libuv выполняет их в
  **thread pool** — пуле из четырёх потоков по умолчанию (переменная
  `UV_THREADPOOL_SIZE`, до 1024). JS-поток ставит задачу в пул и
  получает колбэк, когда пул закончил.

**Node API и биндинги** — слой на C++ и JS, который связывает V8 с
libuv и даёт знакомые модули: `fs`, `net`, `http`, `crypto`, `stream`.

Отсюда ответ на классический вопрос «однопоточный ли Node». JS
выполняется в одном потоке — да. Но процесс Node — многопоточный:
четыре потока пула libuv, потоки V8 для сборки мусора и компиляции,
плюс `worker_threads`, если ты их создал. Ответ «Node однопоточный» без
этой оговорки на собеседовании сеньора — минус.

## Что из этого следует для сервера

**Один поток обслуживает всех, поэтому один медленный синхронный кусок
кода останавливает всех.** `JSON.parse` на десятимегабайтном теле
запроса, синхронное чтение файла, тяжёлая регулярка — пока это
выполняется, ни один другой запрос не обрабатывается. В «Пульте» это
выглядело бы так: один оператор загрузил реестр на 50 МБ, и три тысячи
операторов увидели зависший интерфейс. Следующие уроки — про то, как это
измерять и куда выносить.

**Файловые операции конкурируют за четыре потока.** Если сервис читает
много файлов или считает много хешей паролей (`pbkdf2` — тоже пул),
пятая операция ждёт освобождения потока. Это не блокирует JS, но
задерживает ответы, и в метриках выглядит как «база тормозит», хотя
база ни при чём. Лечение — увеличить `UV_THREADPOOL_SIZE` или вынести
работу.

**Сетевой ввод-вывод почти бесплатен.** Десять тысяч открытых
WebSocket-соединений с операторами — это десять тысяч дескрипторов и
немного памяти, а не десять тысяч потоков. Поэтому Node хорош именно
там, где много соединений и мало вычислений: BFF, шлюзы, реалтайм.

**Использовать восемь ядер один процесс не может.** JS-поток один.
Чтобы задействовать ядра, запускают несколько процессов — модулем
`cluster`, менеджером процессов вроде PM2 или, чаще всего сегодня,
репликами контейнеров за балансировщиком. Следствие, о котором
забывают: процессы не делят память, и всё, что лежало «в переменной»
— сессии, кэш, счётчики, — после масштабирования начинает работать
через раз. Состояние выносится наружу: в Redis, в базу.

## Модули: CommonJS и ESM

Второй по частоте вопрос про рантайм. CommonJS — `require` и
`module.exports`, синхронная загрузка, `require` можно вызвать внутри
условия, есть `__dirname`. ESM — `import`/`export`, статическая
структура (можно анализировать до выполнения), top-level `await`,
`import.meta.url` вместо `__dirname`. ESM включается полем
`"type": "module"` в `package.json` или расширением `.mjs`.

Нюанс для собеседования: в ESM код модуля верхнего уровня выполняется
внутри микрозадачи, поэтому порядок `Promise.then` и `process.nextTick`
на верхнем уровне модуля отличается от CommonJS. К этому вернёмся в
следующем уроке.

Про TypeScript: начиная с Node 22.6 есть флаг
`--experimental-strip-types` (в Node 23+ включён по умолчанию): Node
выполняет `.ts`, стирая типы без проверки. Работает только «стираемый»
синтаксис — без `enum`, `namespace` и параметров-свойств конструктора.
В проде по-прежнему принято собирать `tsc` или `esbuild`, но знать про
флаг стоит: задания этого курса выполняются именно так.

## Версии и LTS

Чётные мажорные версии Node становятся LTS и поддерживаются 30 месяцев;
нечётные — экспериментальные, живут полгода. В проде — только LTS. На
собеседовании могут спросить, что появилось в последних версиях:
встроенный `fetch` и `AbortController`, встроенный test runner
(`node --test`), `--watch`, `--env-file`, стабильные `worker_threads`,
разрешения (`--permission`). Не обязательно помнить всё, но «слежу за
платформой» — сигнал, который считывают.

## На чём валят

- **«Node однопоточный, значит `fs.readFile` выполняется в главном
  потоке».** Нет: файловые операции идут в пул libuv. В главном потоке
  выполняется только колбэк.
- **«Сетевые запросы тоже идут через thread pool».** Нет: сеть — через
  `epoll`/`kqueue`, без потоков. Это принципиально, потому что именно
  поэтому Node держит десятки тысяч соединений.
- **«Async-функция выполняется в другом потоке».** Нет: `async/await` —
  синтаксис поверх промисов, всё в том же потоке. Асинхронность — про
  ожидание, а не про параллельность. `await heavyComputation()` не
  освобождает поток, если `heavyComputation` синхронно считает.
- **«Чтобы использовать все ядра, нужно включить многопоточность в
  Node».** Ядра используют процессами (cluster, реплики), а
  `worker_threads` — для конкретной CPU-работы, не для HTTP-сервера в
  целом.

## Как ответить за минуту

«Node — это V8 плюс libuv. V8 выполняет JavaScript в одном потоке,
libuv даёт цикл событий и асинхронный ввод-вывод: сеть через механизмы
ОС без потоков, файлы, DNS и часть crypto — через пул из четырёх
потоков. Поэтому один процесс держит тысячи соединений, но любой
синхронный тяжёлый код останавливает всех. Ядра используются
несколькими процессами, которые не делят память, — отсюда требование
выносить состояние в Redis или базу».
