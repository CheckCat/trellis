# Ошибки процесса и graceful shutdown

Уровень 1. Два вопроса, которые проверяют, доводил ли ты сервис до
прода: «что делать с uncaughtException» и «как правильно остановить
сервис при деплое». У обоих есть популярный неправильный ответ, и
интервьюер ждёт, что ты его не дашь.

## Боль: два вида ошибок

Ошибки в сервере делятся на два класса, и обращаться с ними нужно
по-разному.

**Операционные ошибки** — то, что происходит в нормально работающей
системе: база не ответила, внешний провайдер вернул 503, клиент прислал
невалидное тело, файл не найден, соединение оборвалось. Это не баги.
Их ожидают, обрабатывают на месте — ответить 4xx/5xx, повторить,
записать в лог — и продолжают работать.

**Программные ошибки** — баги: обращение к свойству `undefined`, неверный
тип, забытый `await`, ошибка в логике. После такой ошибки состояние
процесса **не определено**: что-то могло остаться недописанным,
блокировка — незахваченной, счётчик — сбитым. Единственный честный ответ
— записать всё, что можно, и **выйти**, чтобы оркестратор перезапустил
процесс в чистом состоянии.

Попытка «поймать и жить дальше» — популярный неправильный ответ. Он
превращает один упавший запрос в тысячу запросов, обработанных в
непредсказуемом состоянии.

## uncaughtException и unhandledRejection

```js
process.on("uncaughtException", (err, origin) => {
  logger.fatal({ err, origin }, "uncaught exception");
  shutdown(1);
});

process.on("unhandledRejection", (reason) => {
  logger.fatal({ reason }, "unhandled rejection");
  shutdown(1);
});
```

`uncaughtException` — синхронное исключение, которое никто не поймал.
`unhandledRejection` — промис отклонён, и никто не подписался на
отклонение. Начиная с Node 15 второе по умолчанию **роняет процесс**,
как и первое, — раньше только печатало предупреждение, и это была
причина множества тихих багов.

Правильное содержание обработчика: залогировать с полным контекстом,
попытаться корректно закрыться (об этом ниже), выйти с ненулевым
кодом. Не «залогировать и продолжить».

Что ловит `try/catch`: только синхронный код и то, что под `await`.
Ошибка внутри колбэка `setTimeout` или слушателя события до внешнего
`try/catch` не долетит. Ошибка в `async`-функции, вызванной без `await`
и без `.catch`, — это `unhandledRejection`. Отсюда правило: у каждого
промиса должен быть хозяин, который его ждёт или ловит.

## Где ошибки должны оставаться операционными

В «Пульте» внешний провайдер SMS иногда отвечает 500. Это не повод
падать: сообщение должно уйти на повтор, а сервис — продолжить
обрабатывать остальные. Граница между «обработать на месте» и
«упасть» проходит по **ожидаемости**: всё, что может случиться с
внешним миром, обрабатывается; всё, что означает баг в нашем коде, —
падение и перезапуск.

Практическое следствие для кода: доменные и инфраструктурные ошибки —
свои классы (`NotFoundError`, `ConflictError`, `UpstreamUnavailable`),
их ловят на границе и превращают в ответ. Всё остальное — не ловят,
дают долететь до обработчика процесса. Об этом ещё будет урок про формат
ошибок в HTTP-модуле.

## Graceful shutdown

Деплой: оркестратор шлёт процессу `SIGTERM`, ждёт N секунд, потом
`SIGKILL`. Балансировщик перестаёт слать трафик на этот инстанс — но не
мгновенно. Если процесс на `SIGTERM` просто выходит, все запросы,
которые были в обработке, обрываются: оператор получает ошибку на
ровном месте, а если запрос уже что-то записал в базу и не успел
опубликовать событие — данные расходятся.

Правильная остановка — последовательность:

1. **Перестать принимать новые соединения.** `server.close()` закрывает
   слушающий сокет; активные соединения при этом продолжают работать.
2. **Сказать оркестратору, что мы уходим.** Readiness-эндпоинт начинает
   отвечать ошибкой, чтобы балансировщик снял инстанс раньше, чем он
   закроется. Об этом — модуль про эксплуатацию.
3. **Дождаться завершения запросов в обработке** — с таймаутом.
   Запрос, который не завершился за 10–30 секунд, всё равно будет
   оборван.
4. **Закрыть ресурсы в порядке, обратном открытию:** отписаться от
   очереди (перестать брать новые сообщения, дообработать взятые),
   закрыть пул соединений с базой, остановить таймеры, сбросить логи.
5. **Выйти** с кодом 0.

И на всё это — **общий таймаут**: если через 30 секунд мы всё ещё
закрываемся, выходим принудительно. Иначе зависший хук остановки
превращает деплой в вечное ожидание, и оркестратор всё равно пришлёт
`SIGKILL` — только уже без нашего участия.

```js
process.on("SIGTERM", async () => {
  const forceExit = setTimeout(() => process.exit(1), 30_000).unref();
  await server.close();          // 1. новые соединения не принимаем
  await queue.close();           // 4. дообрабатываем взятые сообщения
  await db.end();                // 4. пул закрыт
  clearTimeout(forceExit);
  process.exit(0);
});
```

`unref()` на таймере — чтобы сам таймер не держал процесс живым, если
всё закрылось раньше.

## Ловушка keep-alive

`server.close()` перестаёт принимать **новые соединения**, но
HTTP-соединения с keep-alive — а это почти все соединения от
балансировщика — остаются открытыми и **продолжают приносить
запросы**, пока клиент их не закроет. Сервер честно ждёт их
завершения, а они не завершаются, потому что балансировщик шлёт
следующий запрос по тому же соединению. В итоге процесс живёт до
`SIGKILL`, и запросы всё равно обрываются.

Лечение: при остановке отвечать `Connection: close` на каждый
запрос по keep-alive-соединению, чтобы клиент его закрыл. Node 18.2+
делает это сам в `server.close()` для простаивающих соединений, а
для активных есть `server.closeIdleConnections()` и
`server.closeAllConnections()`. Что такое keep-alive и как его
настраивать относительно балансировщика — следующий модуль.

## На чём валят

- **«В uncaughtException логирую и продолжаю работать».** После бага
  состояние процесса не определено; правильно — залогировать, закрыть
  ресурсы, выйти.
- **«unhandledRejection — это предупреждение».** С Node 15 — падение
  процесса, как uncaughtException.
- **«На SIGTERM вызываю process.exit()».** Обрываются запросы в
  обработке; правильно — перестать принимать, дождаться, закрыть
  ресурсы, выйти с таймаутом на всё.
- **«server.close() дождётся всех запросов».** Не дождётся конца
  keep-alive-соединений; их нужно закрывать явно.
- **«try/catch вокруг всего сервера поймает всё».** Не поймает колбэки
  и промисы без await.

## Как ответить за минуту

«Ошибки делю на операционные — обрабатываю на месте — и программные:
после них состояние не определено, поэтому логирую и выхожу, чтобы
оркестратор перезапустил. unhandledRejection с Node 15 роняет процесс.
Остановка по SIGTERM: перестать принимать соединения, снять инстанс с
балансировки через readiness, дождаться запросов в обработке, закрыть
очередь, пул, таймеры в обратном порядке, выйти — с общим таймаутом,
после которого выходим принудительно. Отдельно закрываю
keep-alive-соединения, иначе close их не дождётся».
