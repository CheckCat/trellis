# Event loop сервера: фазы, микрозадачи, nextTick и setImmediate

Уровень 1. Ты знаешь event loop браузера: синхронный код, потом
микрозадачи, потом одна макрозадача, потом рендер. В Node база та же, но
цикл устроен из **фаз**, есть две очереди с приоритетом над всем
остальным, и есть вопрос с подвохом, который задают почти всем. У тебя
здесь фора: понимание браузерного цикла переносится почти целиком, нужно
добавить детали.

## Боль: зачем вообще знать фазы

Потому что на сервере от порядка зависит поведение под нагрузкой. Код,
который «просто откладывает» работу через `process.nextTick`, может
заморозить обработку всех входящих соединений. Код, который ставит
таймер на ноль, чтобы «дать другим поработать», не даёт. А вопрос «что
выведется первым» на собеседовании — не проверка памяти, а проверка,
понимаешь ли ты, где в цикле находится твой код в момент вызова.

## Фазы цикла

Одна итерация цикла libuv проходит фазы по кругу:

```
   ┌──────────────────────────┐
┌─▶│  timers                  │  колбэки setTimeout / setInterval, чьё время пришло
│  ├──────────────────────────┤
│  │  pending callbacks       │  отложенные системные колбэки (ошибки TCP и т. п.)
│  ├──────────────────────────┤
│  │  idle, prepare           │  внутренние
│  ├──────────────────────────┤
│  │  poll                    │  ожидание и обработка I/O: сокеты, файлы (из пула)
│  ├──────────────────────────┤
│  │  check                   │  колбэки setImmediate
│  ├──────────────────────────┤
└──│  close callbacks         │  socket.on('close') и подобные
   └──────────────────────────┘
```

Ключевая фаза — **poll**. Здесь цикл спрашивает ОС «есть ли готовые
события», выполняет их колбэки и, если больше нечего делать, **блокируется
в ожидании** — до ближайшего таймера или до появления события. Именно
поэтому пустой сервер не жрёт CPU: он спит внутри poll.

Между фазами — и это главное отличие от простой модели «макро/микро» —
после **каждого** колбэка любой фазы Node опустошает две очереди:

1. **очередь `process.nextTick`** — целиком;
2. **очередь микрозадач** (промисы, `queueMicrotask`) — целиком.

Причём в таком порядке: сначала все nextTick, потом все микрозадачи, и
если микрозадача добавила nextTick — снова nextTick, и так до пустых
очередей. Только потом цикл идёт к следующему колбэку.

## Классический вопрос: порядок вывода

```js
setTimeout(() => console.log("timeout"), 0);
setImmediate(() => console.log("immediate"));
process.nextTick(() => console.log("nextTick"));
Promise.resolve().then(() => console.log("promise"));
console.log("sync");
```

Ответ: `sync`, `nextTick`, `promise`, затем `timeout` и `immediate` — и
вот здесь подвох. Из главного модуля порядок `timeout`/`immediate` **не
гарантирован**. `setTimeout(fn, 0)` — на самом деле `setTimeout(fn, 1)`,
и когда цикл входит в фазу timers, одна миллисекунда могла как пройти,
так и нет: зависит от того, сколько заняла загрузка модуля. Запусти
десять раз — увидишь оба варианта.

А теперь то же самое внутри колбэка ввода-вывода:

```js
import fs from "node:fs";
fs.readFile("file.txt", () => {
  setTimeout(() => console.log("timeout"), 0);
  setImmediate(() => console.log("immediate"));
});
```

Здесь порядок **гарантирован**: `immediate`, потом `timeout`. Колбэк
`readFile` выполняется в фазе poll; следующая фаза — check, где живёт
`setImmediate`; а до timers цикл дойдёт только на следующей итерации.
Это и есть вопрос, на который отвечают уверенно только те, кто понял
фазы, а не выучил список.

## nextTick против setImmediate

Названия перепутаны местами — это признают сами разработчики Node.
`process.nextTick` срабатывает **немедленно** после текущей операции,
раньше любой микрозадачи. `setImmediate` — в фазе check, то есть в
конце текущей итерации цикла, после ввода-вывода.

Когда что:

- `nextTick` — когда нужно выполнить что-то «после того, как текущая
  функция вернётся, но до всего остального». Классика: эмиттер, который
  создают и на который подписываются в той же функции, должен выдать
  первое событие уже после подписки. Внутри Node так сделан `EventEmitter`
  и стримы.
- `setImmediate` — когда нужно «дать циклу сделать оборот»: отпустить
  ввод-вывод, а потом продолжить. Например, разбить длинную синхронную
  обработку на куски.

И опасность, о которой спрашивают: **рекурсивный `nextTick` замораживает
ввод-вывод**. Очередь nextTick опустошается до конца, и если каждый
nextTick ставит следующий, цикл никогда не дойдёт до poll. Ни один
входящий запрос не будет обработан, хотя CPU занят на сто процентов и
процесс «жив». Рекурсивный `setImmediate` так себя не ведёт: между
вызовами цикл проходит poll. Поэтому «отложить и повторить» делают через
`setImmediate`, никогда через `nextTick`.

## Голодание цикла и как его измерить

Всё то же самое в терминах эксплуатации: если один колбэк выполняется
долго, цикл не крутится, и все соединения ждут. Это называют **лагом
цикла событий** — разницей между тем, когда таймер должен был сработать,
и тем, когда он сработал реально. Node даёт готовый инструмент:

```js
import { monitorEventLoopDelay } from "node:perf_hooks";
const h = monitorEventLoopDelay({ resolution: 20 });
h.enable();
// ... позже: h.mean, h.percentile(99) — в наносекундах
```

Лаг цикла — одна из первых метрик, которую выводят на дашборд
Node-сервиса, наравне с потреблением памяти. Если лаг растёт под
нагрузкой — где-то синхронная работа, и следующий урок про то, куда её
вынести.

## ESM и порядок на верхнем уровне

Нюанс из прошлого урока: в ESM код модуля выполняется внутри
микрозадачи. Поэтому на верхнем уровне `.mjs`-файла `Promise.then`
сработает **раньше** `process.nextTick` — мы уже внутри опустошения
микрозадач, и nextTick дождётся его конца. В CommonJS — наоборот. На
собеседовании такой вопрос встречается редко, но если встретится, это
ровно то место, где «знаю модель» отличается от «выучил порядок».

## На чём валят

- **«setTimeout(fn, 0) выполнится раньше setImmediate».** Из главного
  модуля — не гарантировано; внутри колбэка ввода-вывода — всегда
  наоборот.
- **«nextTick — это следующая итерация цикла».** Нет, это до конца
  текущей операции; следующая итерация — как раз setImmediate.
- **«Микрозадачи выполняются после всех макрозадач фазы».** Нет: после
  **каждого** колбэка. Это отличие от старых версий Node (до 11), и
  сейчас поведение совпадает с браузером.
- **«Долгий async-код блокирует цикл».** Не блокирует, если он
  действительно ждёт ввода-вывода. Блокирует синхронная работа между
  `await`. Вопрос «что блокирует» — следующий урок.

## Как ответить за минуту

«Цикл libuv идёт по фазам: timers, pending, poll, check, close. Poll —
основная, там ждём и обрабатываем ввод-вывод. После каждого колбэка
любой фазы опустошаются очередь nextTick, потом микрозадачи. setImmediate
— это фаза check, поэтому внутри колбэка ввода-вывода он всегда раньше
таймера на ноль, а из главного модуля порядок не гарантирован.
Рекурсивный nextTick замораживает ввод-вывод, setImmediate — нет. Лаг
цикла измеряют через perf_hooks и выводят на дашборд».
