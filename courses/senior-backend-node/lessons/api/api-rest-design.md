# REST по-взрослому: ресурсы, методы, статус-коды

Уровень 1. Ты проектировал контракты с бэк-командами годами — у тебя
есть насмотренность. Этот урок переводит её в систему: что именно
проверяют вопросами про REST и какими словами отвечать. Спрашивают
это всегда, потому что дизайн API — ежедневная работа бэкендера и
дешёвый способ увидеть, как человек думает.

## Боль: API без соглашений

Сервис, где `/getClientCards`, `/blockCard`, `/cards_unblock_v2` и
ответ 200 с `{"error": true}` внутри. Каждый вызов — поход в
документацию, каждый клиент — своя обработка ошибок, кэширование
невозможно, ретраи опасны. REST — не догма, а набор соглашений,
которые делают API предсказуемым: увидел URL и метод — понял
поведение.

## Ресурсы и методы

Правила, которые стоит проговаривать как аксиомы:

- **В URL — существительные, иерархия — принадлежность:**
  `/customers/42/accounts`, `/cases/7/events`. Глаголы выражаются
  методами, а не словами в пути.
- **Методы и их семантика по спецификации:**

| Метод | Смысл | Безопасный | Идемпотентный |
|---|---|---|---|
| GET | прочитать | да | да |
| HEAD | как GET без тела | да | да |
| POST | создать / выполнить действие | нет | **нет** |
| PUT | заменить целиком | нет | да |
| PATCH | изменить частично | нет | не обязан |
| DELETE | удалить | нет | да |

  «Безопасный» — не меняет состояние; «идемпотентный» — повтор даёт
  тот же результат, что один вызов. Почему вторая колонка — самое
  важное слово таблицы, разберём в следующем уроке; здесь достаточно
  определения.
- **Действия, не ложащиеся в CRUD,** оформляются подресурсом:
  заблокировать карту — `POST /cards/123/block` (или создание ресурса
  `block-requests`). Это честнее, чем растягивать PATCH со
  «статусами» на всё подряд.
- **Stateless:** сервер не хранит состояние диалога между запросами —
  каждый запрос несёт всё нужное (токен, параметры). Следствие: любой
  инстанс обработает любой запрос — это фундамент масштабирования.

## Статус-коды, по которым проверяют

Не нужно помнить все — нужно без запинки объяснять эти:

- **200** — ок; **201** — создано (с заголовком `Location`);
  **202** — принято, выполняется асинхронно (массовая операция:
  ответ сразу, статус — по ссылке); **204** — ок без тела (DELETE).
- **301/308** — переехало; **304** — не изменилось (условный GET).
- **400** — запрос непонятен (битый JSON); **422** — понятен, но
  невалиден по содержанию. Разделение условно, важно быть
  последовательным на платформе.
- **401 против 403** — вопрос-фильтр на каждом собеседовании: 401 «я
  не знаю, кто ты» (нет или протух токен — попробуй войти), 403 «я
  знаю, кто ты, и тебе нельзя» (оператор без роли супервизора). И
  помни оговорку прошлого урока: на чужой приватный ресурс банковской
  системы честнее отвечать 404, чем подтверждать его существование
  через 403.
- **404** — нет ресурса; **405** — нет метода; **409** — конфликт
  состояния (обращение уже закрыто); **429** — превышен лимит
  запросов (с `Retry-After`).
- **500** — наша ошибка; **502** — за нами кто-то ответил мусором;
  **503** — мы перегружены или закрываемся (с `Retry-After`);
  **504** — за нами кто-то не ответил вовремя.

Правило, которое отличает практика: **код — часть контракта, по нему
ветвится чужой код и алёрты**. 200 с ошибкой в теле ломает и то и
другое; 500 на невалидный ввод будит дежурного из-за чужого бага.

## Мелочи дизайна, о которых спрашивают

- **Согласованность имён:** `camelCase` или `snake_case` — любой, но
  один на платформу.
- **Даты** — ISO 8601 с таймзоной (`2026-09-24T10:00:00Z`); деньги —
  строкой или в минорных единицах, никогда float. Для банка это не
  стилистика: `0.1 + 0.2` в балансе — инцидент.
- **Частичные ответы и вложенность:** сколько уровней раскрывать
  (`/cases?expand=customer`) — решение контракта, а не привычки.
- **Единый формат ошибок** — прошлый модуль; он тоже часть REST-дизайна.

## HATEOAS и «уровни зрелости»

Могут спросить про модель зрелости Ричардсона: уровень 0 — RPC поверх
POST, 1 — ресурсы, 2 — методы и коды (здесь живёт вся индустрия), 3 —
HATEOAS: ответы несут ссылки на возможные действия. Честный ответ
сеньора: «уровень 2 осознанно; HATEOAS красив, но клиенты всё равно
пишутся по документации, и на практике он редко окупается». Это
лучше, чем делать вид, что HATEOAS у вас есть.

## На чём валят

- **401 против 403** — см. выше; путаница здесь почти
  дисквалифицирующая.
- **«POST /cases/7/close — это не REST, нужен PATCH статуса»**.
  Действие-подресурс — легитимный приём; важно, чтобы семантика и
  коды были честными, а не буква стиля.
- **«DELETE вернул 404 при повторе — значит, DELETE не идемпотентен»**.
  Идемпотентность — про состояние сервера, а не про одинаковость
  ответов: ресурс удалён в обоих случаях.
- **200 с {"success": false}** — ломает ветвление клиентов, кэши и
  мониторинг; коды существуют ровно для этого.

## Как ответить за минуту

«REST — соглашения: ресурсы-существительные в URL, семантика —
методами, GET безопасен и кэшируем, PUT и DELETE идемпотентны, POST —
нет; действия вне CRUD — подресурсом. Сервер stateless — любой инстанс
обрабатывает любой запрос. Коды — часть контракта: 401 — не знаю кто,
403 — знаю и нельзя, 404 — на чужое приватное, 409 — конфликт
состояния, 422 — невалидно по содержанию, 429 — лимит, 503 с
Retry-After — перегрузка. Деньги — не float, даты — ISO 8601, формат
ошибок един».
