# Пункт 1. Соло-проект: «построил платформу целиком»

Что значит «сделал образовательную платформу с нуля в одиночку» на
языке, за который не стыдно перед бэкендером? Разложим твой Crowdwiz
на части и посмотрим, что в каждой из них рассказывать и о чём спросят.

Фраза для скрининга — одно предложение:

> «Построил и запустил платформу онлайн-школы целиком: схема данных в
> MongoDB, REST API на Express, приём платежей, авторизация, деплой и
> сопровождение в проде».

Теперь — что стоит за каждым словом.

## Схема данных в MongoDB

MongoDB — документная база: вместо таблиц со строками она хранит
JSON-подобные документы. Курс с его модулями и уроками ложится в один
документ со вложенной структурой — читается одним запросом, без
склейки нескольких таблиц.

На вопрос «почему MongoDB, а не реляционная база?» отвечай честно и
без обороны: «Для раннего продукта в одиночку — скорость разработки:
структура курса — естественный документ, схему легко менять. Сегодня
я бы взвешивал внимательнее: как только появляются связи и отчётность,
реляционная база выигрывает — поэтому я и добирал PostgreSQL всерьёз».
Такой ответ показывает рост, а не оправдывается за прошлое.

## REST API на Express

REST — стиль устройства HTTP-API: у каждой сущности свой адрес
(`/courses/42`), действия выражаются методами HTTP (GET — прочитать,
POST — создать, DELETE — удалить), сервер отвечает статус-кодами.
Express — минималистичный веб-фреймворк Node.js, много лет бывший
выбором по умолчанию.

Что важно уметь сказать: API — это **контракт**, договорённость о
формате между клиентом и сервером. Ты проектировал его сам и сам же
был его потребителем со стороны фронтенда — это редкий угол зрения,
называй его прямо: «я знаю, как выглядит неудобный API, потому что
сам ел свои контракты с другой стороны».

## Приём платежей: самая взрослая часть соло-проекта

Интеграция с платёжной системой устроена так: пользователь уходит на
страницу оплаты платёжного провайдера, а результат тебе прилетает
**вебхуком** — HTTP-запросом от платёжной системы на твой сервер:
«платёж такой-то прошёл».

Здесь живут две настоящие бэкенд-проблемы, и они украшают рассказ:

- **Вебхук может прийти дважды.** Платёжная система работает по
  принципу «доставить хотя бы раз»: не получила от тебя ответ 200 —
  пришлёт снова, даже если первый раз ты всё обработал, а потерялся
  только ответ. Обработчик обязан быть **идемпотентным**: повторная
  обработка того же события не даёт повторного эффекта. Реализация —
  проверка по уникальному идентификатору платежа: уже видел и
  обработал — отвечаем 200 и ничего не делаем второй раз. Без этого —
  двойное зачисление доступа или двойное списание.
- **Вебхуку нельзя верить на слово.** Запрос «платёж прошёл» может
  прислать кто угодно. Подлинность проверяется подписью: платёжная
  система подписывает тело запроса секретом, сервер проверяет подпись.

## Авторизация, деплой, прод

- **Авторизация**: вход по паролю, пароль в базе — только в виде
  хеша (никогда открытым текстом), сессия пользователя — токен или
  cookie. На скрининге достаточно «сделал авторизацию сам»; механику
  сессий разберём в модуле про аутентификацию и его уроке-пункте про
  фундамент — там у тебя есть чем блеснуть посерьёзнее.
- **Деплой**: приложение живёт на сервере, перед ним — обратный
  прокси (nginx: принимает HTTPS, отдаёт статику, проксирует API),
  процесс Node перезапускается менеджером процессов при падении.
- **Прод**: логи, бэкапы базы, разбор ошибок живых пользователей.
  Слово «сопровождал в проде» означает именно это — ты был один на
  все роли, включая дежурного.

## Как говорить о нагрузке

Вопрос «какие были нагрузки?» про соло-проект — ловушка тщеславия.
Ответ по правилу честности: «Ранний продукт, нагрузки скромные — но
весь цикл мой: от схемы данных до приёма денег и ночных аварий».
Ценность этого пункта биографии — не масштаб, а **полнота цикла**:
людей, которые в одиночку довели продукт до живых платежей, мало.

## Вопросы вдогонку

- «Сколько пользователей?» — честная цифра + перевод разговора на
  полноту цикла (см. выше).
- «Почему Express?» — «Стандарт де-факто на тот момент, максимум
  материалов и библиотек. Сегодня для нового сервиса взял бы Fastify
  или NestJS — и могу объяснить почему» (если спросят почему: Fastify
  быстрее и строже со схемами данных, Nest даёт структуру для
  команды; глубже на скрининге не понадобится).
- «Платежи — какая система? Как тестировали?» — назови провайдера как
  есть; тестирование — песочница провайдера с тестовыми картами.
