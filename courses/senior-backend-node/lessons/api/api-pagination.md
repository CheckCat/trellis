# Пагинация, фильтрация, сортировка: offset против cursor

Уровень 1. История операций по счёту, лента обращений, журнал аудита —
всё это списки на десятки тысяч строк, и вопрос «как сделаешь
пагинацию» на собеседовании обязателен. Правильный ответ — не название
способа, а сравнение двух и выбор под задачу.

## Боль: страница 500

Оператор открывает историю операций по счёту:
`GET /accounts/42/operations?page=500&perPage=20`. Сервер делает
`OFFSET 9980 LIMIT 20` — и база **читает и выбрасывает** 9980 строк,
чтобы отдать 20. Чем глубже страница, тем дороже запрос: OFFSET не
«перепрыгивает», он проходит. На больших журналах глубокие страницы —
это секунды и деградация всей базы.

Вторая беда offset — **нестабильность**. Пока оператор читал страницу
1, пришли три новые операции. Страница 2 теперь начинается на три
строки раньше: оператор видит три операции повторно (или, при
удалении, теряет строки). Для банковского журнала «видел дважды или не
видел вовсе» — это не мелочь.

## Keyset: курсор по значениям, а не по номеру

Идея курсорной (keyset) пагинации: вместо «пропусти N строк» — «дай
строки **после вот этой**». Сортируем по стабильной паре — например,
`(created_at, id)` — и передаём границу последней увиденной строки:

```sql
SELECT * FROM operations
WHERE account_id = $1
  AND (created_at, id) < ($2, $3)   -- граница из курсора
ORDER BY created_at DESC, id DESC
LIMIT 21;
```

- **Дёшево на любой глубине:** по индексу
  `(account_id, created_at DESC, id DESC)` база встаёт сразу на
  границу — миллисекунды хоть на первой странице, хоть на тысячной.
- **Стабильно при вставках:** новые строки выше границы не сдвигают
  то, что ниже неё, — дублей и пропусков нет.
- **`id` в паре обязателен:** `created_at` не уникален (две операции в
  одну миллисекунду), а курсор должен указывать на строку однозначно.
  Забытый tiebreaker — классический баг: строки с одинаковым временем
  то дублируются, то пропадают.
- **LIMIT 21 при странице 20** — дешёвый способ узнать `hasMore`: если
  пришла 21-я строка, есть следующая страница, а строка отбрасывается.

Курсор наружу отдают **непрозрачным**: JSON с границей, закодированный
в base64. Не потому, что секрет, а чтобы клиент не начал собирать его
сам и не завязался на внутренности; поменяем сортировку — старые
курсоры просто перестанут декодироваться, и это управляемая поломка.

Что keyset не умеет — и это честная цена: **прыжок на страницу 37** и
«всего страниц: 214». Нужны номера страниц — это offset; нужен счётчик
— отдельный `COUNT(*)` (дорогой на больших таблицах; часто заменяется
приблизительным или «более 1000»).

## Выбор

| | offset | keyset |
|---|---|---|
| Глубокие страницы | деградирует | дёшево |
| Вставки во время листания | дубли/пропуски | стабильно |
| Прыжок на страницу N | да | нет |
| Реализация | тривиальна | курсор + индекс под сортировку |

Правило выбора: **бесконечная лента, журналы, API для машин — keyset;
маленькие админочные списки с номерами страниц — offset**. Гибрид
тоже легален: первые 100 страниц offset (пользователи глубже не
ходят), API — только keyset.

## Фильтры и сортировка — в связке

- Фильтры (`?status=open&topic=card-blocked`) — белым списком: имена
  полей и операторы перечислены контрактом, а не «что пришло, то и в
  WHERE» (иначе клиент фильтрует по внутренним полям и кладёт базу
  нечитаемым запросом).
- Сортировка — тоже белым списком, и **курсор привязан к сортировке**:
  граница по `(created_at, id)` бессмысленна при сортировке по сумме.
  Меняется сортировка — курсор строится по новой паре
  (`amount, id`).
- Значения по умолчанию и предел: `limit` по умолчанию 20–50, максимум
  100–200 — иначе кто-нибудь запросит `limit=1000000`, и это будет
  ваш OOM.

## На чём валят

- **«OFFSET пропускает строки»**. Читает и выбрасывает; в этом вся
  проблема глубоких страниц.
- **Курсор по одному `created_at`**. Без уникального tiebreaker
  курсор неоднозначен — дубли и пропуски на границах.
- **«Отдам в курсоре просто id последней строки»**. Работает только
  при сортировке по id; для любой другой сортировки границей служит
  пара «значение сортировки + id».
- **`COUNT(*)` на каждый запрос списка**. На больших таблицах это
  полноценное сканирование; счётчик — отдельное решение, а не
  бесплатное поле ответа.

## Как ответить за минуту

«Offset прост и даёт номера страниц, но глубокие страницы читают и
выбрасывают всё до себя, а вставки сдвигают границы — дубли и
пропуски. Keyset: сортировка по стабильной паре значение+id, в курсоре
— граница последней строки, запрос через WHERE больше границы по
индексу — дёшево на любой глубине и стабильно; курсор отдаю
непрозрачным base64, hasMore — запросом на строку больше. Цена —
нет прыжка на страницу N. Журналы и ленты — keyset, админка с
номерами — offset. Фильтры и сортировки — белым списком, limit —
с потолком».
