# Идемпотентность и ключ идемпотентности

Уровень 1. Если из всего курса выбрать одно слово, которое сеньор
обязан уметь раскрыть с любого места, — это идемпотентность. Она
всплывает в REST, в ретраях, в очередях, в платежах — и на
собеседовании к ней возвращаются трижды под разными углами.

## Боль: таймаут — это не «нет»

Клиент «Лавки» нажимает «Оплатить». Запрос ушёл, сервер списал деньги
— а ответ потерялся: сеть моргнула, балансировщик оборвал соединение,
клиент увидел таймаут. Что знает клиент? **Ничего.** Операция могла
выполниться, могла не выполниться, могла выполняться прямо сейчас.
Таймаут — это не отказ, это отсутствие информации.

Что делает клиент? Повторяет. Что получает «Лавка»? Второе списание.
То же самое в «Пульте»: фронтенд повторил создание обращения после
таймаута — у клиента два одинаковых обращения, два оператора звонят
одному человеку.

Вывод, который надо произносить дословно: **сеть ненадёжна, ретраи
неизбежны, значит каждая операция должна быть безопасна для повтора**.
Идемпотентность — не теоретическое свойство из таблицы методов, а
условие выживания в реальной сети.

## Определение и границы

Операция идемпотентна, если повторное выполнение оставляет систему в
том же состоянии, что однократное. `UPDATE cards SET status =
'blocked' WHERE id = 7` — идемпотентен. `UPDATE accounts SET balance =
balance - 100` — нет. GET/PUT/DELETE идемпотентны по спецификации,
POST — нет, и именно POST-операции — создание, списание, отправка —
нужно делать идемпотентными руками.

## Ключ идемпотентности

Механика, ставшая стандартом (её API называют заголовком
`Idempotency-Key`):

1. **Клиент** генерирует уникальный ключ на операцию (UUID) — не на
   запрос: повтор той же операции идёт с тем же ключом.
2. **Сервер** при первом запросе сохраняет ключ и выполняет операцию,
   записывая результат рядом с ключом.
3. **Повтор с тем же ключом** не выполняет операцию, а возвращает
   сохранённый результат — тот же статус и тело, что получил бы
   первый запрос.

Дьявол в деталях, и именно их спрашивают:

- **Ключ и операция — атомарно.** Сохранить ключ и выполнить операцию
  нужно в одной транзакции (или ключ — уникальным ограничением в той
  же базе). Иначе окно: ключ записан, операция упала — повтор получит
  «уже выполнено» за невыполненную операцию.
- **Конкурентный повтор.** Два запроса с одним ключом пришли
  одновременно (двойной клик). Первый выполняет, второй должен либо
  дождаться результата первого, либо ответить 409/425 «в обработке» —
  но не выполнить операцию второй раз. Реализация — уникальный индекс
  по ключу: второй INSERT упадёт, и это сигнал ждать.
- **Тот же ключ, другое тело** — ошибка клиента: 422, а не
  выполнение. Для этого рядом с ключом хранят хеш тела.
- **Срок жизни.** Ключи хранят ограниченно (сутки–недели), это
  оговаривается контрактом: повтор через месяц — новая операция.
- **Область.** Ключ уникален в рамках операции и пользователя, а не
  глобально: чужой ключ не должен отдавать чужой результат.

## Идемпотентность без ключа

Ключ — не единственный инструмент, и сеньор называет альтернативы:

- **Естественный ключ.** «Одно обращение на клиента и тему в день» —
  уникальное ограничение в базе; повторная вставка упирается в него, и
  сервер отвечает существующим обращением. Надёжнее любого заголовка,
  когда бизнес даёт естественную уникальность.
- **Перевод состояния, а не приращение.** «Заблокировать карту» вместо
  «переключить статус», «установить лимит 50 000» вместо «увеличить на
  10 000». Абсолютные операции идемпотентны сами по себе; дельты — нет.
- **Версия/условие.** `If-Match` с ETag или поле версии: повтор со
  старой версией отклоняется. Об этом подробнее в уроке про блокировки
  Postgres.

А для операций через очередь идемпотентность обязана жить **на
потребителе** — брокер честно доставляет «как минимум один раз».
Это тема модуля про очереди, и она стоит на сегодняшнем уроке.

## Внешние платежи: две стороны ключа

В «Лавке» оплата идёт через внешнего провайдера, и картина
симметрична: наш API принимает `Idempotency-Key` от фронтенда, а сам,
вызывая провайдера, передаёт ему **свой** ключ (все серьёзные
платёжные API его принимают). Наш таймаут при вызове провайдера — та
же неопределённость: списание могло пройти. Повтор с тем же ключом
провайдера безопасен; без ключа единственный честный путь — запросить
у провайдера статус операции, прежде чем повторять.

## На чём валят

- **«Таймаут — значит не выполнилось, можно повторять»**. Таймаут —
  отсутствие информации; повторять можно только идемпотентное.
- **«Сгенерирую ключ на сервере»**. Тогда повтор клиента получит новый
  ключ и создаст дубль; ключ обязан родиться у инициатора операции.
- **«Проверю existsом: если ключ есть — не выполняю»**. Проверка и
  вставка отдельно — гонка; нужен уникальный индекс и одна транзакция.
- **«Идемпотентность — забота клиента, пусть не повторяет»**. Ретраит
  не только человек: балансировщики, SDK, очереди. Сервер обязан быть
  готов.

## Как ответить за минуту

«Таймаут — это не отказ, а отсутствие информации, поэтому клиенты
повторяют, и каждая небезопасная операция должна быть готова к
повтору. Стандарт — Idempotency-Key: клиент генерирует ключ операции,
сервер атомарно с операцией сохраняет его с результатом, повтор
получает сохранённый ответ, конкурентный повтор отсекается уникальным
индексом, другое тело с тем же ключом — 422. Где можно, лучше
естественная идемпотентность: уникальное ограничение бизнес-ключа или
абсолютная операция вместо дельты. С внешним платёжным провайдером —
его же механика ключей с нашей стороны».
