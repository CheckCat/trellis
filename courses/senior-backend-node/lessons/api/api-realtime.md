# WebSocket, SSE, long polling: реалтайм со стороны сервера и его масштабирование

Уровень 2, но с постоянным вопросом уровня 1 внутри: «как
масштабировать WebSocket на несколько инстансов». Ты работал с
вебсокетами со стороны клиента и BFF — здесь серверная механика и её
следствия.

## Боль: сервер должен позвонить первым

Оператору назначили обращение — он должен узнать об этом сейчас, а не
когда обновит страницу. Клиент написал в чат — сообщение должно
появиться у оператора мгновенно. HTTP устроен «клиент спрашивает —
сервер отвечает»; реалтайм — это способы обойти это ограничение.

## Три транспорта

**Long polling.** Клиент делает запрос, сервер держит его открытым до
события или таймаута, отвечает, клиент немедленно спрашивает снова.
Работает через любые прокси, но: задержка на переустановку, висящие
запросы занимают ресурсы, упорядочивание и пропуски — забота
приложения. Сегодня это fallback, а не выбор.

**SSE (Server-Sent Events).** Один долгоживущий HTTP-ответ
`text/event-stream`, по которому сервер льёт события; браузерный
`EventSource` сам переподключается и присылает `Last-Event-ID` —
встроенное восстановление с места обрыва. Ограничения: только
сервер→клиент, только текст. Идеален для «сервер уведомляет»: лента
статусов, прогресс массовой операции.

**WebSocket.** Полноценный двусторонний канал поверх апгрейда
HTTP-соединения. Всё, что нужно для чата: клиент и оператор пишут в
обе стороны. Цена — это уже не HTTP: свой жизненный цикл, свои
проблемы доставки, и всё ниже — про них.

Правило выбора: **только пуш от сервера — SSE; двусторонний диалог —
WebSocket; long polling — когда среда не пропускает ни то, ни то**.

## WebSocket в проде: что спрашивают

- **Обрывы и ping/pong.** Мёртвое соединение не отличимо от молчащего:
  NAT и балансировщики режут простаивающие соединения тихо. Сервер
  шлёт ping и закрывает соединения без pong; клиент переподключается с
  экспоненциальной задержкой. Без этого списки «онлайн-операторов»
  всегда врут.
- **Состояние на сервере.** Каждое соединение — память и дескриптор;
  Node с этим хорош (см. модуль про рантайм), но 5 000 операторов ×
  два соединения — это уже цифры для мониторинга.
- **Аутентификация.** Апгрейд происходит один раз: токен проверяется
  на рукопожатии (cookie или параметр запроса), а **срок жизни
  соединения может превысить срок жизни токена** — нужна политика:
  перепроверять по таймеру или закрывать по истечении. Об этом ещё
  раз в модуле auth.
- **Backpressure.** Медленный клиент не читает — буфер соединения
  растёт (bufferedAmount). Медленных отключают или прореживают им
  поток; безлимитный буфер — та же утечка памяти, что в уроке про
  стримы.

## Главный вопрос: несколько инстансов

Один инстанс BFF — все соединения в его памяти: «отправь оператору
7» — нашёл сокет в Map, отправил. Теперь инстансов три, соединение
оператора 7 живёт на инстансе B, а событие «обращение назначено»
пришло из Kafka на инстанс A. Как доставить?

Два семейства решений:

- **Sticky sessions** — балансировщик привязывает клиента к инстансу
  (по cookie или ip-хешу). Соединение и правда живёт на одном
  инстансе, но проблему это не решает: событие-то родилось на другом.
  Sticky нужен для рукопожатия некоторых транспортов, но доставку не
  обеспечивает.
- **Pub/sub между инстансами** — правильный ответ. Каждый инстанс
  подписан на общий канал (Redis pub/sub, или консюмер-группы у
  общего брокера): событие публикуется в канал, получают его **все**
  инстансы, а отправляет в сокет тот, у кого живёт соединение
  оператора 7. Реестр «оператор → инстанс» либо не нужен (все
  получают всё и фильтруют), либо живёт в Redis для адресной
  доставки при больших объёмах.

Формула для собеседования: **соединения локальны, события глобальны;
мост между ними — pub/sub**.

И две смежные проблемы, которые отличают продуманный ответ:

- **Порядок и пропуски.** Между обрывом и переподключением события
  потерялись. Лечение как в SSE: события нумеруются, клиент присылает
  последний увиденный номер, сервер досылает из короткой истории
  (буфер в Redis) — или честно говорит «обнови состояние целиком».
  Чат «Пульта» живёт именно так: номер сообщения в диалоге +
  дозагрузка истории по переподключению.
- **Graceful shutdown.** Деплой BFF рвёт тысячи соединений разом —
  и все клиенты переподключаются одновременно к оставшимся инстансам.
  Сервер при остановке закрывает соединения постепенно с кодом
  «переподключись», клиент — с рандомизированной задержкой. Слово для
  этого эффекта будет в модуле про отказоустойчивость.

## На чём валят

- **«Sticky sessions решают масштабирование WebSocket»**. Они
  привязывают клиента к инстансу, но событие рождается где угодно;
  доставку решает pub/sub между инстансами.
- **«SSE — это урезанный WebSocket, зачем он»**. Обычный HTTP (кэши,
  прокси, HTTP/2), автопереподключение с Last-Event-ID из коробки.
  Для одностороннего пуша он проще и надёжнее.
- **«Обрыв виден по событию close»**. Мёртвый NAT не шлёт close;
  без ping/pong сервер хранит зомби-соединения.
- **«События по WebSocket доходят по порядку и всегда»**. В пределах
  живого соединения — да; через переподключение — нет, нужна
  нумерация и досылка.

## Как ответить за минуту

«Только пуш — SSE: обычный HTTP, автопереподключение, Last-Event-ID.
Диалог — WebSocket: ping/pong против мёртвых соединений, проверка
токена на апгрейде и политика на его истечение, лимит буфера
медленным. Масштабирование: соединения локальны инстансу, события
глобальны — мостом служит pub/sub через Redis или брокер: публикуешь
событие, доставляет тот инстанс, где живёт соединение. Потери на
переподключении закрываются нумерацией событий и досылкой истории.
Sticky sessions доставку не решают».
