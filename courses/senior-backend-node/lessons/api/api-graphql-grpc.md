# GraphQL и gRPC против REST: схемы, N+1, стриминг

Уровень 2 — но с одним фрагментом уровня 1: проблему N+1 в GraphQL
спрашивают у всех, кто упомянул GraphQL в резюме. А ты его упомянул.

## Боль, которую решает каждый

- REST отдаёт фиксированные срезы: экрану нужно три поля — приедут
  сорок; нужны данные трёх ресурсов — три запроса.
- **GraphQL**: клиент декларативно описывает, что ему нужно, сервер
  собирает ровно это. Одна конечная точка, типизированная схема.
- **gRPC**: сервисам между собой не нужен человекочитаемый JSON —
  нужны скорость, типы и стриминг. Бинарный protobuf поверх HTTP/2 с
  генерацией клиентов.

Треугольник выбора: **GraphQL — для разнообразных клиентов наружу,
gRPC — между сервисами внутрь, REST — универсальный по умолчанию**.

## GraphQL со стороны сервера

Ты работал с GraphQL как потребитель и соавтор схем; собеседующий
спросит серверную сторону.

**Устройство.** Схема (типы, запросы, мутации) + **резолверы** —
функции, вычисляющие каждое поле. Запрос исполняется обходом дерева:
резолвер `case` вернул обращение, резолверы полей `customer`,
`events` дособирают своё.

**N+1 — главный вопрос.** Запрос:

```graphql
{ cases(first: 50) { id, customer { name } } }
```

Резолвер `cases` сделал один запрос к базе и вернул 50 обращений.
Дальше GraphQL вызывает резолвер `customer` **для каждого** обращения
— 50 запросов `SELECT * FROM customers WHERE id = $1`. Итого 51
запрос вместо двух. Это и есть N+1: один запрос за списком, по одному
за каждым элементом.

Решение — **батчинг**: резолверы не ходят в базу сразу, а складывают
id в накопитель; в конце тика событий накопитель одним запросом
забирает всех (`WHERE id = ANY($1)`) и раздаёт результаты ожидающим.
Эталонная реализация — DataLoader; она же кэширует повторные ключи в
рамках запроса. Как это устроено на промисах и тике цикла событий —
следующая практика, ты напишешь свой.

**Чем ещё стреляет GraphQL-сервер:**

- **Сложность запроса.** Клиент может запросить дерево глубины 15 и
  положить базу. Защита: лимиты глубины и стоимости запроса,
  персистированные запросы (клиент шлёт id заранее одобренного
  запроса — стандарт для мобильных приложений банка).
- **Кэширование.** Всё летит POST-ом на одну точку — HTTP-кэш не
  работает; кэшируют на уровне резолверов и клиентских библиотек.
- **Ошибки.** 200 с массивом `errors` рядом с частичными `data` —
  клиент обязан проверять оба; это осознанное расхождение с REST.
- **Версионирование** — его нет: поля добавляются, старые помечаются
  `@deprecated` и живут по метрикам использования. Та же дисциплина
  вывода, что в прошлом уроке.

## gRPC

- **Контракт** — `.proto`-файл: сообщения и сервисы; из него
  генерируются клиент и сервер для любого языка. Contract-first по
  построению.
- **Транспорт** — HTTP/2: мультиплексирование, бинарные кадры. Отсюда
  **стриминг** трёх видов: серверный (сервер льёт поток ответов),
  клиентский, двунаправленный — то, чего в REST нет вовсе.
- **Скорость** — protobuf компактнее и дешевле JSON в разы на
  сериализации; на внутренних вызовах с тысячами RPS это реальные
  проценты CPU.
- **Ограничения:** из браузера напрямую нельзя (нужен grpc-web и
  прокси); человекочитаемость нулевая — отладка через grpcurl;
  балансировка L7 требует умного балансировщика (долгоживущие
  HTTP/2-соединения).
- **Идиоматика ошибок** — свои коды (`NOT_FOUND`,
  `DEADLINE_EXCEEDED`…), и главное слово — **deadline**: клиент
  передаёт предельное время, оно распространяется по цепочке вызовов.
  Запомни слово — оно вернётся в модуле про отказоустойчивость.

Где gRPC в «Пульте»: между BFF и сервисами — кандидат (типизация +
скорость), но честный ответ: «выиграем проценты, заплатим
инфраструктурой и порогом входа; я бы начал с REST + OpenAPI и
переводил на gRPC горячие внутренние пары сервисов по мере надобности».

## Сравнение одним взглядом

| | REST | GraphQL | gRPC |
|---|---|---|---|
| Контракт | OpenAPI (опционально) | схема (обязательна) | proto (обязателен) |
| Клиент выбирает поля | нет | да | нет |
| Кэш HTTP | да | нет | нет |
| Стриминг | нет (SSE отдельно) | подписки | да, три вида |
| Из браузера | да | да | через прокси |
| Типичное место | всё по умолчанию | разнообразные клиенты | сервис-сервис |

## На чём валят

- **N+1**: не сможешь объяснить механику и решение батчингом — GraphQL
  в резюме сыграет против тебя.
- **«GraphQL быстрее REST»**. Он не про скорость, а про гибкость
  выборки; сервер работает больше, а не меньше.
- **«gRPC — это JSON по HTTP/2»**. Бинарный protobuf; в этом половина
  смысла.
- **«Возьмём GraphQL для связи микросервисов»**. Между сервисами
  запросы фиксированы — гибкость выборки не нужна, а цена есть; там
  живут REST и gRPC.

## Как ответить за минуту

«REST — по умолчанию; GraphQL — когда клиентов много и им нужны
разные срезы: клиент декларирует выборку, сервер исполняет резолверами
— отсюда N+1, лечится батчингом а-ля DataLoader: накопить id за тик,
забрать одним запросом, раздать; плюс лимиты сложности и
персистированные запросы. gRPC — между сервисами: protobuf-контракт с
кодогенерацией, HTTP/2, стриминг, deadline по цепочке; из браузера —
только через прокси. Выбор — по потребителям, а не по моде».
