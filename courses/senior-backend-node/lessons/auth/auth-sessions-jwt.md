# Сессии против JWT: где хранить, как отзывать, CSRF

Уровень 1. «Сессии или JWT?» — вопрос, на котором проверяют умение
взвешивать, а не заучивать. У тебя есть фронтовая половина (где
хранить токен, CORS, cookie) — достраиваем серверную и собираем
критерий выбора.

## Боль: сервер должен помнить, кто вошёл

HTTP — без состояния; вход случился один раз, а запросов потом тысячи.
Два фундаментально разных способа «помнить»:

**Серверная сессия** — состояние на сервере. При входе создаётся
запись сессии (кто, когда, с какого устройства), клиенту уходит
только её случайный id в cookie. Каждый запрос — поиск сессии по id.

**JWT** — состояние у клиента. Сервер при входе подписывает пакет
утверждений (claims): кто, роли, срок — и отдаёт клиенту целиком.
Каждый запрос — проверка подписи, поход в хранилище не нужен.

## Серверная сессия: механика

- id — криптослучайный, длинный; ищется в хранилище. На одном
  инстансе можно в памяти, но инстансов больше одного — хранилище
  общее: Redis с TTL — стандарт (быстро, TTL из коробки), Postgres —
  когда сессий немного и хочется одной технологией меньше.
- Cookie: `HttpOnly` (JS не читает — краденый XSS-ом скрипт не
  утащит), `Secure`, `SameSite=Lax` или `Strict`, `Path`, срок.
- **Отзыв мгновенный**: удалил запись — сессии нет. «Выйти со всех
  устройств», «уволили оператора» — решается удалением записей.
- Цена: поход в хранилище на каждый запрос (Redis — доли
  миллисекунды, это дёшево) и само хранилище как зависимость.

## JWT: механика и обещания

Три части `header.payload.signature`, base64url. Подпись:

- **HS256** — симметричная: один секрет и подписывает, и проверяет.
  Просто, но каждый проверяющий сервис может и подделывать.
- **RS256/ES256** — асимметричная: подписывает приватный ключ
  identity, проверяет любой сервис публичным. Публичные ключи
  раздаются через **JWKS** (стандартный URL с ключами), в токене
  `kid` говорит, каким ключом подписан, — так работает **ротация
  ключей** без передоговорённостей.

Что нужно говорить про подводные камни самого формата:

- `alg: none` и подмена RS256→HS256 — исторические атаки; лечение:
  библиотека настроена на **белый список алгоритмов**, никогда «что
  пришло в заголовке».
- Payload **читается всеми** (это кодирование, не шифрование) —
  внутри никаких секретов и персональных данных сверх необходимого.
- Проверять всегда: подпись, `exp`, `iss`, `aud`. Токен «для другого
  сервиса» (чужой aud) — невалиден.
- Часы серверов расходятся — небольшой `clockTolerance`.

**Главная слабость — отзыв.** Подпись валидна до `exp`, сервер по
построению не помнит токенов. Уволенный оператор с токеном на сутки —
сутки ходит в систему. Смягчения: короткий срок жизни access-токена
(минуты) + refresh (следующий урок), чёрный список jti в Redis (но
это возвращает состояние — и тогда честно спросить себя, чем это
лучше сессии), версия «выхода» в записи пользователя.

## Выбор: критерий, а не вера

| | Сессия | JWT |
|---|---|---|
| Отзыв | мгновенный | до exp; нужны обходные пути |
| Проверка | поход в Redis | локальная (подпись) |
| Межсервисно | каждому сервису нужен доступ к хранилищу | проверяется везде по публичному ключу |
| Состояние | на сервере | у клиента |

Рабочая формула: **интерактивные пользователи одного продукта —
сессии** (отзыв и контроль дороже, чем экономия похода в Redis);
**межсервисные вызовы и федерация многих сервисов — JWT** с коротким
сроком. Частый гибрид — как в «Пульте»: браузер ↔ BFF живёт на
cookie-сессии, BFF ↔ сервисы — короткоживущие JWT (модуль
продолжит это уроком про межсервисную аутентификацию). Ответ «и то и
то, по месту» с этим обоснованием — сильный.

## Где хранить токен на клиенте и CSRF

Ты это знаешь с фронта — проговорим серверными словами:

- localStorage — читается любым XSS; httpOnly cookie — не читается,
  и потому предпочтительна для браузера.
- Но cookie браузер шлёт **сам** — отсюда **CSRF**: чужой сайт
  отправляет форму на наш домен, и cookie поедет с ней. Защита:
  `SameSite=Lax/Strict` (закрывает большинство сценариев), плюс для
  строгости CSRF-токен (double submit или синхронизатор) на
  небезопасных методах; CORS сам по себе от CSRF-форм **не** защищает
  — форма не подчиняется CORS.
- Bearer из заголовка CSRF не подвержен (заголовок чужой сайт не
  поставит) — но токен для этого лежит в читаемом JS месте: обмен
  одной угрозы на другую, и это стоит проговаривать как trade-off.

## На чём валят

- **«JWT безопаснее сессий»** — это не про безопасность, а про
  распределение состояния; безопасность определяется реализацией.
- **«JWT можно отозвать»** — из коробки нельзя; любой механизм отзыва
  — возврат состояния на сервер, и это нужно признавать.
- **«Положим роли и ФИО в JWT — удобно же»** — payload публичен, а
  роли протухают: роль отозвали, токен ещё жив.
- **«CORS защищает от CSRF»** — нет; SameSite и CSRF-токены.
- **Белый список алгоритмов** — не назвать его, рассказывая про JWT,
  — минус: атаки на alg — классика.

## Как ответить за минуту

«Сессия — состояние на сервере: id в httpOnly cookie, записи в Redis
с TTL, отзыв мгновенный; цена — поход в хранилище и общая зависимость.
JWT — состояние у клиента: подпись RS256 с ротацией через JWKS,
проверка локальна везде; цена — отзыв только через короткий exp,
refresh или чёрный список, что возвращает состояние. Формула: люди в
браузере — сессии, межсервисное и федерация — короткие JWT; в нашей
платформе так и жило: cookie до BFF, JWT дальше. Браузерное хранение
— httpOnly cookie плюс SameSite и CSRF-токен; localStorage читается
XSS-ом. Библиотека JWT — белый список алгоритмов, проверка exp, iss,
aud».
