# OAuth 2.0, OIDC, PKCE и корпоративный SSO

Уровень 2. Здесь достаточно уверенно держать рамку: роли, главный
поток, отличие OIDC от OAuth и слова про корпоративный вход. Глубже
(все гранты, все расширения) на собеседовании бэкендера копают редко.

## Боль: не отдавать пароль каждому приложению

Исходная задача OAuth: приложение хочет доступ к твоим данным в
другом сервисе — без передачи ему твоего пароля. Решение: пользователь
разрешает у **владельца** данных, приложение получает **токен с
ограниченными правами**, пароль не покидает владельца.

Роли, которые нужно называть без запинки:

- **resource owner** — пользователь;
- **client** — приложение, которому нужен доступ;
- **authorization server** — кто аутентифицирует и выдаёт токены
  (identity, Keycloak, корпоративный IdP);
- **resource server** — API с данными, принимает access-токены.

## Authorization code + PKCE: главный поток

Единственный поток, который нужно знать в деталях:

1. Клиент отправляет браузер пользователя на authorization server:
   `client_id`, `redirect_uri`, `scope`, `state` (случайная строка
   против CSRF на колбэке) и `code_challenge` (хеш секрета PKCE).
2. Пользователь аутентифицируется у сервера авторизации (пароль,
   второй фактор — клиент этого не видит) и соглашается со scope.
3. Браузер возвращается на `redirect_uri` с одноразовым **кодом**.
4. Клиент **сервером** меняет код на токены, предъявляя
   `code_verifier` (исходный секрет PKCE) и, для конфиденциальных
   клиентов, client secret.
5. Получает access (+ refresh) и ходит в resource server.

**PKCE**: пара verifier/challenge доказывает, что код обменивает тот
же, кто начинал поток, — перехваченный код бесполезен. Родился для
мобильных и SPA (там нет client secret), сейчас рекомендован
**всем**. Устаревшее, что нужно узнавать и отвергать: **implicit
flow** (токен прямо в URL редиректа — в истории, логах, referer) и
password grant (приложение собирает пароль — ровно то, от чего OAuth
уходил).

Второй нужный поток — **client credentials**: без пользователя,
сервис получает токен под своим id/секретом. Это прошлый урок,
межсервисные вызовы.

## OIDC: личность поверх OAuth

OAuth — про **доступ** («можно читать счета»), в нём нет стандартного
«кто пользователь». OpenID Connect — слой поверх: добавляет
**id_token** (JWT с личностью: `sub`, имя, почта, как
аутентифицирован), endpoint userinfo и discovery-документ
(`/.well-known/openid-configuration`), из которого клиент узнаёт все
адреса и JWKS.

Разница, которую спрашивают: **id_token — для клиента** («кто
вошёл»), **access token — для resource server** («что можно»).
Слать id_token в API — ошибка; проверять личность по access — тоже
(его формат вообще не обещан клиенту).

«Вход через Google/GitHub» — это OIDC. И корпоративный SSO — тоже он.

## Корпоративный SSO

Вход оператора «Пульта»: identity не хранит пароли сам, а
доверяет корпоративному IdP (Keycloak, Active Directory + ADFS,
Okta). Схема: сервис → OIDC → корпоративный IdP; внутри IdP — учётки
из AD/LDAP, вторые факторы, политики. Однажды войдя, оператор входит
во все системы банка без пароля — это и есть single sign-on.

Слова, которые достаточно знать на уровне «что это»: **SAML** —
предшественник OIDC (XML, ассерции), жив в энтерпрайзе, концепция та
же; **SCIM** — синхронизация учёток/групп из HR в системы; выход из
всех систем (single logout) — существует и всегда сложнее, чем
хочется. Группы из IdP обычно **маппятся** в роли приложения — а
дальше работает твоя модель доступа (следующий урок).

## На чём валят

- **«OAuth — это аутентификация»** — OAuth про доступ; личность —
  OIDC с id_token.
- **id_token отправляют в API** — он для клиента; API принимает
  access.
- **Зачем PKCE** — не ответить «перехваченный код бесполезен без
  verifier» — значит, слово знакомо, механика нет.
- **state** — не назвать его как защиту от CSRF на колбэке.
- **«Сделаем свою форму логина, пароль проверим в AD»** — это
  password-антипаттерн: пароль корпоративной учётки достаётся
  приложению; правильный путь — редирект на IdP.

## Как ответить за минуту

«OAuth — делегированный доступ: пользователь разрешает у
authorization server, клиент получает ограниченный токен, пароль
приложению не достаётся. Рабочий поток — authorization code с PKCE:
редирект с state и challenge, одноразовый код, обмен на токены с
verifier сервер-сервером; implicit и password — устаревшие. OIDC
добавляет личность: id_token для клиента, access — для API, discovery
и JWKS. Корпоративный вход — OIDC к IdP вроде Keycloak поверх AD:
SSO, вторые факторы и группы там, приложение маппит группы в свои
роли. Межсервисно — client credentials».
