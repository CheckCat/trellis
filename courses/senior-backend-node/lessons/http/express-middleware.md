# Express: цепочка middleware, next(err) и async-ловушка

Уровень 1. Express — самый распространённый фреймворк Node, и вопрос
про его устройство — это на самом деле один вопрос: **как работает
цепочка middleware**. Кто понял цепочку, понял весь Express; остальное
— справочник.

## Боль: у каждого запроса десяток общих забот

Разбор JSON, аутентификация, проверка прав, логирование, лимиты,
обработка ошибок — это нужно каждому маршруту, но писать это в каждом
обработчике нельзя. Идея Express: запрос проходит через **конвейер
функций**, каждая делает свой кусок работы и передаёт дальше. Маршрут —
просто последняя функция конвейера.

## Middleware

Middleware — функция `(req, res, next)`, стоящая в цепочке обработки
запроса. У неё три варианта поведения:

- сделать свою работу и передать дальше: `next()`;
- завершить запрос: `res.send(...)` / `res.json(...)` — дальше цепочка
  не идёт;
- передать ошибку: `next(err)` — управление прыгает к обработчикам
  ошибок, минуя всё остальное.

```js
app.use(express.json({ limit: "1mb" }));   // парсинг тела
app.use(authenticate);                      // кто это
app.get("/cases/:id", authorize, getCase);  // маршрут со своей цепочкой
app.use(errorHandler);                      // в самом конце
```

**Порядок регистрации — это порядок выполнения**, и это главный
инвариант Express. Аутентификация, объявленная после маршрута, его не
защищает. Обработчик ошибок, объявленный до маршрутов, не поймает их
ошибок. Никакой магии приоритетов нет — только порядок `app.use`.

`Router` — та же цепочка в миниатюре: группа маршрутов со своими
middleware, смонтированная на префикс (`app.use("/cases",
casesRouter)`). Так BFF делит код по экранам, не смешивая цепочки.

## Ошибки: next(err) и обработчик с четырьмя аргументами

Обработчик ошибок Express отличается **арностью** — четыре аргумента:

```js
app.use((err, req, res, next) => {
  logger.error({ err }, "request failed");
  res.status(err.status ?? 500).json({ code: err.code ?? "internal" });
});
```

`next(err)` с любым аргументом, кроме `"route"`, переводит цепочку в
режим ошибки: обычные middleware пропускаются, выполняются только
четырёхаргументные, по порядку. Обработчик ошибки может ответить, а
может передать дальше — `next(err)` — следующему обработчику ошибок.
Если ни один не ответил, Express отдаст стандартный 500.

Два следствия, которые проверяют вопросами:

- обработчик ошибок ставится **после всех маршрутов** — иначе ему
  нечего ловить;
- в режиме ошибки обычные middleware не выполняются: логирование,
  стоящее обычной функцией после места ошибки, эту ошибку не увидит.

## Async-ловушка Express 4

Самый популярный вопрос про Express. В четвёртой версии:

```js
app.get("/cases/:id", async (req, res) => {
  const c = await repo.find(req.params.id);  // repo бросил
  res.json(c);
});
```

Отклонённый промис **никуда не попадает**: Express 4 писался до
промисов и не умеет их ждать. Ошибка становится unhandled rejection —
а это, как мы знаем из модуля про Node, падение процесса. Запрос при
этом висит до таймаута.

Лечение в Express 4 — оборачивать каждый async-обработчик:

```js
const wrap = (fn) => (req, res, next) => fn(req, res, next).catch(next);
app.get("/cases/:id", wrap(getCase));
```

или брать это из пакета. В **Express 5** (стабилен с конца 2024)
отклонённый промис наконец сам вызывает `next(err)` — и вопрос «чем
пятый отличается от четвёртого» имеет ровно этот главный ответ.

Вторая классическая ловушка — **двойной ответ**: middleware ответил и
всё равно вызвал `next()`, следующий обработчик тоже отвечает — и
получает `ERR_HTTP_HEADERS_SENT`. Правило: ответил — `return`.

## Типовой набор прода и его порядок

1. Логирование запроса (pino-http) — первым, чтобы видеть всё.
2. `helmet` — защитные заголовки.
3. CORS — если API зовут с браузера с другого origin.
4. `express.json` с лимитом тела.
5. Rate limiter — второй рубеж после граничного, на вход и на
   чувствительные маршруты.
6. Аутентификация → авторизация.
7. Маршруты.
8. Обработчик 404 — «до сюда никто не ответил».
9. Обработчик ошибок — последним.

Не порядок ради порядка: логирование до парсинга видит и невалидные
тела; лимитер до аутентификации защищает саму аутентификацию от
перебора; 404 работает только в самом конце.

## На чём валят

- **«Middleware выполняются в порядке специфичности маршрута»**. Нет:
  строго в порядке регистрации.
- **«Ошибка в async-обработчике попадёт в error handler»**. В Express 4
  — нет, будет unhandled rejection; в Express 5 — да.
- **«Обработчик ошибок — это try/catch вокруг маршрутов»**. Это
  функция с четырьмя аргументами в конце цепочки; активируется только
  через next(err) или синхронный throw.
- **«next() после res.send безвреден»**. Следующий обработчик может
  попытаться ответить второй раз — ERR_HTTP_HEADERS_SENT.

## Как ответить за минуту

«Express — это конвейер функций (req, res, next), выполняемых строго в
порядке регистрации: middleware либо передаёт дальше, либо отвечает,
либо через next(err) переключает цепочку на обработчики ошибок — это
функции с четырьмя аргументами в конце. В Express 4 отклонённый промис
в обработчике теряется — оборачиваем в catch(next), в Express 5 это
починили. Типовой порядок: логи, защитные заголовки, парсинг с лимитом,
rate limiter, аутентификация, маршруты, 404, обработчик ошибок».
