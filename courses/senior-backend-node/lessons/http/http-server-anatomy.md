# Путь запроса: сокет, парсер, keep-alive, таймауты, лимиты тела

Уровень 1. Прежде чем говорить об Express и Nest, нужно понимать, что
делает голый `node:http` — потому что фреймворки лишь тонкий слой над
ним, и половина продовых инцидентов случается на этом уровне: таймауты,
незакрытые соединения, загадочные 502 за балансировщиком.

## Боль: фреймворк не защитит от того, о чём не знает

Оператор жалуется: «Пульт» иногда отвечает 502, хотя сервисы живы. В
логах BFF пусто — запрос до кода не дошёл. Причина в итоге — на уровне
TCP-соединений между балансировщиком и Node: сервер закрыл простаивающее
соединение в тот момент, когда балансировщик отправил в него очередной
запрос. Ни Express, ни Nest об этом не знают: это настройки самого
`http.Server`.

## Что делает http-модуль

```js
import http from "node:http";
const server = http.createServer((req, res) => {
  res.writeHead(200, { "content-type": "application/json" });
  res.end(JSON.stringify({ ok: true }));
});
server.listen(3001);
```

Под капотом: принять TCP-соединение, распарсить стартовую строку и
заголовки, отдать тебе `req` — у которого заголовки уже разобраны, а
**тело нет**. `req` — поток чтения, `res` — поток записи. Тела «из
коробки» не существует: его нужно вычитать из потока, проверив размер.
Именно это — плюс маршрутизация и удобные ответы — и есть то, ради чего
появились фреймворки.

Ответ можно отдавать двумя способами: с заголовком `Content-Length`,
если размер известен заранее, или кусками с `Transfer-Encoding:
chunked`, если ответ стримится. `res.end(json)` посчитает длину сам;
`pipeline(файл, res)` уйдёт chunked.

## Keep-alive и его таймауты

HTTP/1.1 по умолчанию переиспользует TCP-соединение для многих
запросов подряд — это и называется keep-alive. Открыть TCP и провести
TLS-рукопожатие дорого, поэтому балансировщик держит к каждому инстансу
пул тёплых соединений.

У сервера Node три таймаута, и их взаимное устройство — источник тех
самых 502:

- `keepAliveTimeout` (по умолчанию 5 с) — сколько сервер держит
  простаивающее соединение между запросами;
- `headersTimeout` (60 с) — сколько ждать заголовки очередного запроса;
- `requestTimeout` (300 с) — предел на весь запрос.

Гонка выглядит так: соединение простаивает 5 секунд, сервер решает его
закрыть — и в эту же миллисекунду балансировщик кладёт туда новый
запрос. Запрос уходит в закрывающееся соединение, балансировщик
получает обрыв и отвечает клиенту 502. Лечение стандартное:
`keepAliveTimeout` сервера должен быть **больше**, чем idle-таймаут
балансировщика (у многих балансировщиков это 60 секунд — тогда серверу
ставят 65), чтобы простаивающее соединение всегда закрывал тот, кто
шлёт в него запросы, а не тот, кто их принимает. Это одна из немногих
цифр, которые стоит просто помнить: вопрос «почему за балансировщиком
редкие 502» — классика собеседования.

С этим же связана уборка при остановке из модуля Node: закрытие сервера
не завершает открытые keep-alive-соединения, их закрывают явно.

## Лимиты: сервер по умолчанию доверчив

Всё, что приходит от клиента, стоит памяти и времени парсера, поэтому
у всего должен быть предел:

- **Размер тела.** `http` сам не ограничивает: тело — поток, и если
  собирать его в буфер без счётчика, клиент пришлёт гигабайт. Все
  фреймворки дают лимит (обычно 100 КБ — 1 МБ по умолчанию); его
  поднимают точечно на маршрутах загрузки, а не глобально.
- **Заголовки.** `maxHeaderSize` — 16 КБ по умолчанию на всё про всё.
- **Медленные клиенты.** Атака slowloris: открыть сотни соединений и
  слать по байту заголовков в секунду, удерживая их вечно.
  `headersTimeout` ровно от этого.
- **Число соединений.** `server.maxConnections`, лимиты дескрипторов
  процесса; за этим обычно следит балансировщик.

Отсюда правило: в проде Node не смотрит в интернет голым. Впереди стоит
reverse proxy — nginx или балансировщик, — который терминирует TLS,
обрезает медленных клиентов, ограничивает размер тела первым рубежом и
отдаёт статику. Ограничение частоты запросов — rate limiter — тоже
чаще живёт там или на API gateway, а в приложении остаётся второй
рубеж на чувствительных маршрутах.

## Заголовки, о которых спрашивают

- `Content-Type` — формат тела; сервер обязан его проверять, а не
  верить: `application/json` с телом из HTML — повод для 415.
- `Content-Length` против chunked — выше.
- `ETag` / `If-None-Match` — условные запросы: BFF может отдать 304 на
  неизменившийся справочник и сэкономить трафик.
- `Cache-Control` — со стороны сервера это способ сказать
  балансировщику и браузеру, что можно кэшировать; для приватных
  данных операторов — `no-store`.
- `X-Forwarded-For` / `X-Forwarded-Proto` — за прокси реальный адрес
  клиента живёт здесь; доверять им можно только от своего прокси
  (`trust proxy` в Express, `trustProxy` в Fastify).

## HTTP/2 и HTTP/3 со стороны Node

HTTP/2 — мультиплексирование многих запросов в одном соединении,
сжатие заголовков, server push (на практике мёртв). Между
балансировщиком и браузером HTTP/2 — норма; между балансировщиком и
Node чаще остаётся HTTP/1.1, потому что выигрыш внутри дата-центра
мал, а поддержка (`node:http2`) заметно менее обкатана. HTTP/3 — тот же
смысл поверх QUIC/UDP, быстрее устанавливает соединение и переживает
смену сети; терминируется на границе, до Node обычно не доходит.
Честный ответ на собеседовании: «включаю на границе, внутрь — по
необходимости, gRPC — отдельная история, он живёт на HTTP/2».

## На чём валят

- **«Тело запроса приходит вместе с req».** Заголовки — да, тело —
  поток, который нужно вычитать с лимитом размера.
- **«502 за балансировщиком — значит сервис падал».** Частая причина —
  гонка keep-alive-таймаутов; сервис при этом жив и здоров.
- **«Лимит тела поставлю побольше, чтобы не мешал».** Лимит — защита
  памяти и парсера; поднимать его нужно точечно на маршрутах загрузки.
- **«X-Forwarded-For можно читать всегда».** Только за своим прокси;
  иначе клиент подставит любой адрес — и обойдёт лимиты, завязанные
  на IP.

## Как ответить за минуту

«node:http принимает соединение, парсит заголовки и отдаёт req-поток —
тело читается вручную и обязано иметь лимит. Соединения
переиспользуются по keep-alive; у сервера есть keepAliveTimeout,
headersTimeout и requestTimeout, и keepAliveTimeout должен быть больше
idle-таймаута балансировщика, иначе редкие 502 на закрытии соединения.
В проде впереди reverse proxy: TLS, медленные клиенты, первый рубеж
лимитов. HTTP/2 и HTTP/3 терминируются на границе; внутрь обычно идёт
HTTP/1.1».
