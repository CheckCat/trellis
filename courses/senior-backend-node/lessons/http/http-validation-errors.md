# Валидация входа и единый формат ошибок

Уровень 1. Тема, на которой у тебя реальное преимущество: ты
стандартизировал обработку ошибок между фронтом, BFF и сервисами
руками и знаешь, зачем это. Урок складывает этот опыт в системный
ответ — где валидировать, как оформлять и чего не отдавать наружу.

## Боль: у каждого сервиса ошибки в своём стиле

Оператор видит «Ошибка 500», поддержка гадает по скриншоту, фронтенд
парсит три формата ошибок от трёх сервисов, а причина инцидента ищется
получасовым раскапыванием логов. Всё это — одна и та же болезнь:
ошибки никто не спроектировал. Их формат — такой же контракт API, как
формат успешного ответа, и проектируется вместе с ним.

## Валидация: на границе, один раз

Правило: **всё, что пришло снаружи, проверяется на границе процесса** —
тело, параметры пути и запроса, заголовки. Инструменты по фреймворку:
JSON Schema у Fastify, `ValidationPipe` с class-validator у Nest, zod
как универсальный вариант с выводом типов TypeScript. Что именно
проверяется:

- **форма**: типы, обязательность, длины, форматы, enum-значения;
- **лишние поля отсекаются** — почему это критично, разберём в модуле
  про безопасность (подсказка: mass assignment);
- **преобразование**: строка `"25"` из query становится числом один
  раз здесь, а не в каждом обработчике.

Чего на границе не делают: бизнес-проверок. «Карта принадлежит этому
клиенту» — это сервисный слой и база, а не схема. Разница видна по
статусу: невалидная форма — 400/422, нарушенное бизнес-правило — 409
или 404 с доменным кодом.

Валидировать ли ответы сервисов, в которые ходит BFF? На собеседовании
хороший ответ: на критичных стыках — да, хотя бы мягко (лог вместо
отказа): чужой контракт ломается чаще своего, и лучше узнать об этом
из лога BFF, чем из белого экрана у трёх тысяч операторов.

## Единый формат ошибки

Стандарт для этого существует — problem details (RFC 9457, бывший
7807): `application/problem+json` с полями `type`, `title`, `status`,
`detail` и любыми расширениями. Брать его дословно не обязательно;
обязательно иметь **один формат на всю платформу**. Рабочий минимум:

```json
{
  "code": "case_already_closed",
  "message": "Обращение уже закрыто и не может быть переназначено",
  "correlationId": "req-7f3a9c",
  "details": [{ "field": "assigneeId", "issue": "required" }]
}
```

- **`code`** — машинный, стабильный, из общего реестра платформы.
  Фронтенд ветвится по нему, а не по тексту; текст можно менять и
  переводить, код — нет.
- **`message`** — для человека. Для оператора — на языке предметной
  области («карта уже перевыпущена»), не «constraint violation».
- **`correlationId`** — сквозной идентификатор запроса, он же
  correlation id: BFF генерирует (или принимает от фронтенда),
  прокидывает заголовком во все сервисы, пишет в каждую строку лога и
  возвращает в ошибке. Оператор диктует поддержке шесть символов — и
  поддержка находит весь путь запроса по всем сервисам одним поиском.
  Это самый дешёвый инструмент эксплуатации из существующих.
- **`details`** — структурированные частности: список полей с
  ошибками валидации, а не простыня в message.

Маппинг доменных ошибок в этот формат живёт в **одном месте** —
error-middleware в Express, exception filter в Nest, setErrorHandler в
Fastify. Сервисы бросают типизированные ошибки (`NotFoundError`,
`ConflictError` с кодом), граница превращает их в HTTP. Так у тебя и
было устроено в BFF — и это правильный ответ.

## Чего не отдавать наружу

Ошибка — любимое место утечек:

- **stack trace** — раскрывает структуру кода и версии; наружу
  никогда, в лог всегда;
- **текст ошибки базы или драйвера** — раскрывает схему («duplicate
  key value violates unique constraint cases_number_key»);
- **внутренние адреса и имена сервисов** из ошибок соединения;
- **чужой message.** Неожиданное исключение — это программная ошибка:
  наружу уходит анонимный `internal` с correlationId, всё остальное —
  в лог. Никогда не `res.json({ message: err.message })` для
  неизвестной ошибки.

Отдельно про 404 против 403: отвечать «нет доступа» на чужой ресурс —
значит подтвердить, что ресурс существует. Для приватных ресурсов
банковской системы правильный ответ на чужое — 404. Это вопрос с
собеседований по безопасности, вернёмся в модуле auth.

## Ошибки — тоже контракт

Раз формат один, его стоит записать в схему (тот же JSON Schema для
ответов 4xx/5xx) и тестировать: интеграционный тест на «невалидное
тело → 400 с details по полям» ловит регресс формата раньше фронтенда.
Реестр кодов — общий документ платформы; новый код добавляется, старый
не переименовывается: по кодам ветвится чужой код.

## На чём валят

- **«Валидирую в каждом сервисе по-своему, это внутренняя кухня»**.
  Формат ошибок — контракт: фронтенд и соседние команды пишут по нему
  код.
- **«В message кладу err.message»**. Для неизвестных ошибок это
  утечка; наружу — анонимный internal с correlationId.
- **«По тексту ошибки фронт поймёт, что случилось»**. Текст меняется и
  переводится; ветвление — только по коду.
- **«Валидация в контроллере и в сервисе — дублирование»**. Это два
  разных вопроса: форма на границе, бизнес-правила в домене. Дублируют
  друг друга только одинаковые проверки формы.

## Как ответить за минуту

«Вход валидируется на границе: форма, типы, отсечение лишних полей —
схемой или пайпом; бизнес-правила — в домене, и это видно по статусам:
400 против 409. Ошибки — единый формат на платформу в духе problem
details: машинный код из реестра, человеческий message, correlationId,
структурированные details. Маппинг доменных ошибок в HTTP — в одном
месте на границе. Наружу не уходят stack, тексты ошибок базы и чужие
message — неизвестная ошибка становится анонимным internal с
correlationId, по которому поддержка находит весь путь запроса в
логах».
