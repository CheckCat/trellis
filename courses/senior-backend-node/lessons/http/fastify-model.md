# Fastify: схемы, инкапсуляция, хуки и цена скорости

Уровень 1. Fastify — второй фреймворк, который нужно знать: на нём
всё чаще пишут новые сервисы, он лежит под капотом Nest как
альтернативный адаптер, и вопрос «чем Fastify быстрее Express и что
это стоит» — стандартный способ проверить, понимаешь ли ты, откуда
вообще берётся производительность фреймворка.

## Боль: Express ничего не знает о твоих данных

Express передаёт `req.body` как «что-то распарсенное» — любой формы.
Проверка входа — твоя забота, сериализация ответа — универсальный
`JSON.stringify`, который на каждом вызове заново выясняет, что за
объект перед ним. На 400 запросах в секунду это заметно: сериализация
больших ответов — одна из самых дорогих операций BFF.

Fastify строит всё вокруг обратной идеи: **маршрут объявляет схему
своих данных заранее**, и фреймворк этим пользуется.

## Схемы: JSON Schema как контракт маршрута

JSON Schema — стандартный способ описать форму JSON: какие поля, каких
типов, что обязательно. У маршрута Fastify схема объявляется прямо в
опциях:

```js
fastify.post("/cases", {
  schema: {
    body: {
      type: "object",
      required: ["customerId", "topic"],
      properties: {
        customerId: { type: "string", format: "uuid" },
        topic: { enum: ["card-blocked", "disputed-operation", "limits"] },
        comment: { type: "string", maxLength: 2000 },
      },
      additionalProperties: false,
    },
    response: {
      201: { type: "object", properties: { id: { type: "string" } } },
    },
  },
}, handler);
```

Из этого Fastify получает две вещи:

- **Валидацию входа до обработчика.** Схема компилируется (ajv) в
  функцию-проверку один раз при старте; невалидное тело — готовый 400
  с перечнем ошибок, обработчик не вызывается.
  `additionalProperties: false` заодно отсекает лишние поля — про то,
  почему это важно для безопасности, будет в модуле про auth.
- **Быструю сериализацию ответа.** По схеме ответа генерируется
  специализированный сериализатор: он заранее знает поля и типы и
  обгоняет универсальный `JSON.stringify` в разы. Побочный эффект,
  который надо знать: поля, которых нет в схеме ответа, **не попадут в
  ответ вовсе**. Это фича (случайно не утечёт лишнее) и источник
  классического недоумения «почему поле пропало».

Плюс схема — это документация: из неё генерируется OpenAPI-описание
без отдельного файла, который вечно отстаёт от кода.

## Откуда скорость

На бенчмарках Fastify в 2–3 раза быстрее Express. Из чего складывается:

- маршрутизатор на префиксном дереве (find-my-way) вместо перебора
  регулярок по списку;
- компилированные сериализация и валидация вместо универсальных;
- логгер pino, пишущий JSON без форматирования на горячем пути;
- меньше работы на запрос: никаких обходов цепочки там, где можно
  решить заранее.

Что это стоит: **дисциплина схем**. Без схем Fastify превращается в
Express с непривычным API — скорость сериализации исчезает, валидацию
пишешь сам. Схемы — не опция, а суть.

Честная оговорка для собеседования: на реальном BFF, где 90 % времени
— ожидание ответов сервисов и базы, разница фреймворков растворяется.
Скорость фреймворка решает в тонких прокси и на высоких RPS, а не в
среднем CRUD-сервисе.

## Инкапсуляция: плагины вместо глобального app

В Express всё, что повесили на `app`, видно всем. Fastify устроен как
дерево **плагинов**: `register` создаёт дочерний контекст, и всё
объявленное в нём — декораторы, хуки, парсеры — видно только внутри
поддерева.

```js
fastify.register(async (instance) => {
  instance.register(dbPlugin);            // instance.decorate("db", pool)
  instance.addHook("onRequest", authenticate);
  instance.register(casesRoutes, { prefix: "/cases" });
});
```

`decorate` добавляет свойство инстансу (`fastify.db`),
`decorateRequest` — запросу. Смысл: зависимости объявляются явно и
локально, у «всего приложения» нет общей свалки. Плагин, которому
нужно поделиться наружу, оборачивается в `fastify-plugin` — это
осознанное решение, а не поведение по умолчанию.

## Хуки жизненного цикла

Вместо одной цепочки — именованные точки на пути запроса:
`onRequest` → `preParsing` → `preValidation` → `preHandler` → handler →
`preSerialization` → `onSend` → `onResponse`.

Аутентификация — `onRequest` (до парсинга тела: незачем парсить тело
неавторизованного), проверка прав — `preHandler` (параметры уже
разобраны), подпись ответа или добавление заголовков — `onSend`, метрики
— `onResponse`. По сравнению с Express это тот же конвейер, но с
явными стадиями: меньше споров о порядке регистрации.

Ошибки: async-обработчики поддерживаются нативно — отклонённый промис
становится ошибкой запроса без обёрток. Ошибку оформляет
`setErrorHandler` на инстансе (и он тоже инкапсулирован: у каждого
поддерева может быть свой).

## Как выглядит типичный сервис

```js
const fastify = Fastify({
  logger: true,                 // pino из коробки
  requestIdHeader: "x-request-id",
  bodyLimit: 1_048_576,
});
fastify.register(helmet);
fastify.register(rateLimit, { max: 100, timeWindow: "1 minute" });
fastify.register(casesRoutes, { prefix: "/cases" });
fastify.setErrorHandler(errorHandler);
await fastify.listen({ port: 3001, host: "127.0.0.1" });
```

Каждому запросу автоматически присваивается request id — из заголовка
или сгенерированный, — и он попадает во все строки лога этого запроса.
Подробно о сквозной трассировке — в уроке про формат ошибок.

## На чём валят

- **«Fastify быстрее, потому что написан на другом языке»**. Тот же
  JavaScript; скорость — из компилированных схем, маршрутизатора и
  дешёвого логгера.
- **«Схема ответа — это только документация»**. Это сериализатор:
  поля вне схемы не попадут в ответ. И это же ответ на «куда пропало
  поле».
- **«Валидация Fastify заменяет всю проверку входа»**. Форму — да;
  бизнес-правила («у клиента нет такой карты») — по-прежнему код.
- **«Инкапсуляция — это про красоту»**. Это про области видимости:
  хук или декоратор не протекает в чужое поддерево, и это ловит
  реальные баги — например, аутентификацию, случайно повешенную на
  маршруты здоровья.

## Как ответить за минуту

«Fastify строится вокруг схем: маршрут объявляет JSON Schema тела,
параметров и ответа; вход валидируется компилированной функцией до
обработчика, ответ сериализуется генерированным сериализатором — отсюда
и скорость вместе с маршрутизатором на префиксном дереве и pino. Поля
вне схемы ответа отсекаются. Плагины дают инкапсуляцию: декораторы и
хуки видны только своему поддереву. Жизненный цикл — именованные хуки
от onRequest до onResponse. Цена — дисциплина схем; на I/O-bound BFF
разница с Express растворяется, и это стоит проговаривать честно».
