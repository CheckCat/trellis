# NestJS: конвейер запроса — middleware, guards, interceptors, pipes, filters

Уровень 1. Второй обязательный вопрос про Nest после DI: «в каком
порядке выполняются части конвейера и что где делать». Проверяется не
память — проверяется, положишь ли ты аутентификацию в правильное
место.

## Боль: одна цепочка на все случаи — это снова самоделка

В Express всё — middleware, и команда сама изобретает соглашения: где
у нас проверка прав, где преобразование данных, где оформление ошибок.
Nest разрезает конвейер на **именованные роли**: у каждой заботы своё
место, свой интерфейс и свой доступ к контексту. Спор «куда это
положить» решается типом, а не договорённостью.

## Порядок

```
запрос
  → middleware            (как в Express: логи, парсинг, сырой запрос)
  → guards                (можно ли: аутентификация, права)
  → interceptors (до)     (обёртка вокруг обработчика)
  → pipes                 (валидация и преобразование входа)
  → handler               (метод контроллера)
  → interceptors (после)  (преобразование ответа, метрики)
  → exception filters     (ошибка на любом шаге → ответ)
ответ
```

Мнемоника: **можно ли → в каком виде → сделать → оформить**.

## Кто за что отвечает

**Middleware** — как в Express, до всего остального: логирование,
`helmet`, разбор тела. Не знает, какой обработчик будет вызван.

**Guard** — отвечает на один вопрос: пускать ли запрос. Возвращает
`true`/`false` или бросает. Уже знает, **куда** идёт запрос (через
`ExecutionContext` виден класс и метод контроллера) — поэтому здесь
живут аутентификация и проверка прав, в том числе декларативная:

```ts
@Roles("supervisor")
@Post("cases/:id/reassign")
reassign() {}
```

Guard читает метаданные `@Roles` через `Reflector` и сверяет с ролями
оператора из сессии. В «Пульте» так: `AuthGuard` глобально —
устанавливает оператора, `RolesGuard` — сверяет роль для маршрутов
супервизора.

**Interceptor** — обёртка вокруг обработчика, видит и вход, и выход:
может замерить время, закэшировать ответ, преобразовать результат,
навесить таймаут. Это применение паттерна «декоратор» к обработчику;
внутри — RxJS (`next.handle()` возвращает Observable), и это
единственное место Nest, где RxJS придётся потрогать.

**Pipe** — валидация и преобразование входа: `ParseUUIDPipe` на
параметре, глобальный `ValidationPipe` с class-validator на DTO. Пайп
получает уже конкретный аргумент обработчика. Правило то же, что у
Fastify-схем: форма проверяется до обработчика, бизнес-правила — в
сервисе.

**Exception filter** — превращает исключение в HTTP-ответ. Доменная
ошибка «обращение уже закрыто» становится 409 в одном месте, а не в
каждом контроллере. Про единый формат ошибок — следующий урок.

## Как это ложится на «Пульт»

Запрос «переназначить обращение» проходит: pino-middleware пишет
строку со сквозным идентификатором → `AuthGuard` достаёт сессию
оператора → `RolesGuard` требует роль супервизора → interceptor
метрик засекает время → `ParseUUIDPipe` проверяет id → обработчик
зовёт сервис → interceptor дописывает длительность → при ошибке
`DomainExceptionFilter` отдаёт аккуратный 409. Каждая забота — в своём
типе, и тест на права не поднимает HTTP вовсе: guard тестируется как
класс.

## Типичные ошибки размещения

- **Аутентификация в middleware.** Работает, но middleware не видит
  метаданных маршрута — декларативные `@Roles` не прочитать; и
  выполняется даже для маршрутов, которым auth не нужен.
- **Валидация в guard.** Guard отвечает «пускать ли», а не «в каком
  виде»; вернёт 403 там, где должен быть 400.
- **Преобразование ответа в pipe.** Pipe видит только вход;
  выход — забота interceptor.
- **Логика в interceptor.** Обёртки — для сквозных забот; бизнес —
  в сервисе.

## Микросервисный транспорт Nest

Nest умеет вешать те же контроллеры на не-HTTP транспорт: TCP, Redis,
NATS, Kafka (`@MessagePattern`). Знать, что это есть, полезно;
выбирать это как основную интеграцию — спорно: у транспорта Nest свой
протокол поверх брокера, и он связывает обе стороны с Nest. На
собеседовании достаточно: «для очередей я бы взял обычный клиент
брокера, паттерны Nest — если обе стороны наши и обе на Nest».

## На чём валят

- **Порядок.** Guards до pipes: сначала «можно ли», потом «в каком
  виде». Наоборот — валидация выполняется для неавторизованных, и
  по ошибкам валидации можно прощупывать API без токена.
- **«Interceptor — это middleware»**. Middleware не знает обработчика
  и не видит результата; interceptor — обёртка вокруг вызова с
  доступом к обоим концам.
- **«Ошибки ловятся в interceptor»**. Можно, но для оформления ошибок
  есть filters; interceptor, глотающий исключения, прячет их от
  фильтров и метрик.
- **«Guard может изменить тело запроса»**. Технически может — и не
  должен: его контракт — решение о допуске.

## Как ответить за минуту

«Порядок: middleware → guards → interceptors до → pipes → обработчик →
interceptors после → exception filters на ошибке. Мнемоника: можно ли,
в каком виде, сделать, оформить. Аутентификация и права — guards, у
них есть доступ к метаданным маршрута для декларативных ролей;
валидация и преобразование входа — pipes; сквозные обёртки — метрики,
кэш, таймаут — interceptors; оформление ошибок — filters. Middleware —
как в Express, для того, что должно случиться до маршрутизации».
