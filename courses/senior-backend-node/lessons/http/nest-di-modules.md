# NestJS: модули, провайдеры, DI и scope

Уровень 1. Nest — то, на чём написана заметная часть банковских
Node-сервисов, и твой самый выгодный фреймворк на собеседовании:
это «Angular для бэкенда», и весь твой опыт с Angular-DI переносится
почти дословно. Проговаривать эту параллель стоит явно — и стоит
знать, где она заканчивается.

## Боль: в каждом проекте Express — своя самодельная архитектура

Express не навязывает структуру: где лежат сервисы, как они получают
зависимости, как подменять их в тестах — каждая команда решает заново.
На одном сервисе это свобода; на платформе из десятка сервисов и
нескольких команд — зоопарк. Nest продаёт ровно одно: **структуру из
коробки** — модули, слои, внедрение зависимостей, соглашения. Команда
из десяти человек пишет одинаково; новый человек открывает любой
сервис и знает, где что лежит.

Под капотом Nest — адаптер поверх Express (по умолчанию) или Fastify:
HTTP-слой он не переизобретает.

## Строительные блоки

**Провайдер** — класс (или фабрика), который контейнер умеет создать и
внедрить. **Контроллер** — принимает HTTP: декораторы маршрутов,
разбор параметров, делегирование сервису. **Модуль** — единица сборки:
объявляет, из чего состоит и что показывает наружу.

```ts
@Module({
  imports: [CustomersModule],          // чужие модули
  controllers: [CasesController],
  providers: [CasesService, CasesRepository],
  exports: [CasesService],             // что видно импортёрам
})
export class CasesModule {}
```

Ключевое правило, которое проверяют вопросом: **провайдер виден другому
модулю, только если экспортирован**. `providers` — приватная
реализация; `exports` — публичный контракт модуля. Импортировал
`CasesModule` — получил `CasesService`, но не `CasesRepository`. Это
инкапсуляция на уровне архитектуры, та же идея, что public API слоя
в FSD на фронте.

## DI: внедрение зависимостей

Внедрение зависимостей — это когда класс не создаёт свои зависимости
сам, а объявляет их в конструкторе, и контейнер подставляет нужные
экземпляры:

```ts
@Injectable()
export class CasesService {
  constructor(
    private readonly repo: CasesRepository,
    private readonly events: EventBus,
  ) {}
}
```

Зачем это на сервере — три причины, которые стоит уметь назвать:

- **Тестируемость.** В тесте контейнер (или ты руками) подставляет
  фейковый репозиторий — без моков модульной системы.
- **Один экземпляр тяжёлых вещей.** Пул соединений, клиент брокера —
  создаются один раз и внедряются всем.
- **Подмена реализации по конфигурации.** Порт «отправить уведомление»
  — в проде адаптер очереди, в тестах — запись в массив. Это принцип
  инверсии зависимостей в действии; подробно — в модуле архитектуры.

Токен зависимости — обычно сам класс. Когда класса нет (интерфейс,
конфиг, соединение), используется строковый или `Symbol`-токен и
явное описание провайдера: `useClass`, `useValue`,
`useFactory` (+ `inject` для зависимостей фабрики). Асинхронная
инициализация — фабрика, возвращающая промис: контейнер дождётся.

**Циклы.** А зависит от B, B от А — контейнер не может создать ни
того, ни другого. Nest предлагает `forwardRef`, но правильный ответ на
собеседовании: цикл — это почти всегда ошибка границ, и лечится
выделением третьего модуля, куда уезжает общая часть. `forwardRef` —
обезболивающее, не лечение.

## Scope: цена времени жизни

По умолчанию каждый провайдер — **синглтон**: создан один раз при
старте, живёт до конца процесса. Ещё два варианта:

- `Scope.REQUEST` — новый экземпляр на каждый запрос;
- `Scope.TRANSIENT` — новый экземпляр на каждое внедрение.

Ловушка, о которой спрашивают: request-scope **заразен**. Если
`CasesService` зависит от request-scoped провайдера, он сам становится
request-scoped, и так вверх по всему графу — вплоть до контроллера.
Значит, весь этот граф пересоздаётся на каждый запрос, и это заметная
цена на горячем пути.

Классическая причина хотеть request-scope — «контекст текущего
запроса» (кто оператор, каков идентификатор запроса). Правильная
альтернатива — `AsyncLocalStorage`: контекст едет с асинхронной
цепочкой без пересоздания графа. К нему вернёмся в модуле про
эксплуатацию.

## Где параллель с Angular заканчивается

Совпадает: декораторы, модули, конструкторная инъекция, токены,
`useFactory`. Отличается:

- **иерархия инжекторов.** В Angular инжекторы образуют дерево по
  компонентам; в Nest контейнер один на приложение, а видимость
  регулируют модули через `exports`;
- **жизнь экземпляров.** На сервере синглтон живёт месяцами и делится
  между всеми запросами — состояние в нём становится общим для всех
  пользователей. Поле `this.currentUser` в синглтон-сервисе — баг
  безопасности, а не стилистика; на фронте с одним пользователем это
  не стреляло;
- **scope по запросу** — серверное понятие, в Angular его нет.

## На чём валят

- **«providers модуля видны всем, кто его импортировал»**. Видны
  только exports.
- **«Request-scope — удобный способ хранить контекст запроса»**.
  Заразен и пересоздаёт граф на каждый запрос; контекст — через
  AsyncLocalStorage.
- **«Состояние в сервисе — нормально, это же класс»**. Синглтон общий
  для всех запросов; изменяемое состояние в нём — гонка и утечка
  данных между пользователями.
- **«forwardRef решает проблему циклов»**. Прячет её; лечение —
  пересмотр границ модулей.

## Как ответить за минуту

«Nest даёт структуру: модули с providers и exports — видимость
регулируется экспортом, — контроллеры для HTTP и DI-контейнер:
зависимости объявляются в конструкторе, токен — класс или явный токен
с useClass/useValue/useFactory. По умолчанию всё синглтоны, поэтому
состояния в сервисах нет; request-scope существует, но заразен и
пересоздаёт граф на каждый запрос — контекст запроса лучше нести через
AsyncLocalStorage. Мне модель знакома по Angular: та же конструкторная
инъекция, различие — один контейнер с модульной видимостью и серверная
жизнь синглтонов».
