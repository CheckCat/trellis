# Курсы

Каждый подкаталог здесь — один самостоятельный контент-пакет курса. Ядро
Trellis (`services/backend`) сканирует эту директорию при старте и по
явному запросу (`POST /courses/rescan`), проверяет каждый пакет по схеме
и показывает пользователю только те, что прошли проверку — сломанный
пакет не мешает остальным курсам работать (см. `docs/architecture.md`,
`.mvp/invariants.md`).

`courses/pilot-sql/` — пилотный курс «Основы SQL», собранный по этому
формату целиком (манифест, уроки, квиз, seed песочницы, практика,
проверяемая сравнением состояния базы с эталонным решением, практика,
проверяемая сравнением с эталонным запросом — и с учётом порядка строк,
и без, — и практика без песочницы, где ученик вписывает полученные
значения) — используйте его как образец при
добавлении нового курса.

## Что умеет движок

Этот README — объяснение для человека. **Машиночитаемый источник истины —
`docs/contracts/capabilities.json`**: типы песочниц, типы практики с их
полями и умолчаниями, правила квиза, лимиты (строки результата, предел
сравнения, таймаут запроса) и версия контракта манифеста. Он
генерируется из `services/backend/src/capabilities.ts`, коммитится в
репозиторий и проверяется в CI (`npm run capabilities:check`), так что
отстать от кода он не может. Поднятый стек отдаёт ровно тот же документ
по `GET /api/capabilities`.

Если вы (или генератор курсов) собираетесь писать `manifest.yaml` —
читайте этот файл, а не полагайтесь на память: механика практики или тип
песочницы существуют только если они там есть.

## Структура пакета курса

```
courses/<course-id>/
  manifest.yaml       # метаданные курса, структура модулей/уроков, квизы,
                       # практика, объявленные песочницы — см. ниже
  lessons/*.md         # текст уроков, на которые ссылается manifest.yaml
  sandbox/*.sql         # seed-скрипты объявленных песочниц (DDL + данные)
```

Пути к файлам урока (`lessons[].content`) и seed-файлам
(`sandboxes[].seed[]`) в `manifest.yaml` — относительные, отсчитываются от
корня пакета (`courses/<course-id>/`). Абсолютные пути, `..` и симлинки,
уводящие за пределы пакета, отклоняются при валидации.

## manifest.yaml — обязательные правила

- `id` курса — стабильный, используется как ключ реестра и в записях
  прогресса; формат: строчные латинские буквы/цифры/дефис, от 2 до 64
  символов, не начинается с дефиса (`^[a-z0-9][a-z0-9-]{1,63}$`).
- `version` — строка в формате semver (`1.0.0`, допустимы `-pre`/`+build`
  суффиксы).
- `title` — обязателен, не может состоять из одних пробелов.
- `modules` — минимум один модуль; у каждого модуля минимум один урок.
- `id` модуля и урока — стабильны (не индекс, не название — на них
  завязан прогресс пользователя и URL API), формат:
  `^[A-Za-z0-9][A-Za-z0-9._-]{0,63}$`. `id` урока уникален **по всему
  курсу**, а не только внутри своего модуля.
- Урок несёт хотя бы одно из: `content` (путь к Markdown-файлу), `quiz`,
  `practice` — можно любую комбинацию сразу.
- `quiz.options` — минимум 2 варианта, ровно один с `correct: true`;
  у каждого варианта **кроме верного** обязательно поле `explanation`
  (почему он неверный — показывается пользователю после ответа).
- `practice.type` — **тип практики**: `sql` (по умолчанию, если поле не
  указано) или `answer`. См. раздел «Типы практики» ниже; остальные поля
  `practice` принадлежат конкретному типу, и лишнее поле не игнорируется,
  а отклоняется валидацией.
- Зачёт практики — только те механики, что зарегистрированы в ядре.
  Своего кода-грейдера курс не поставляет — только декларативные поля.
  Для `type: sql` это `check`, `expected` и `solution`: все необязательны
  и независимы, если заданы несколько — урок засчитывается только когда
  пройдены все, а задание без единой механики засчитывается самоотметкой
  пользователя. Для `type: answer` механика всегда одна — сверка `fields`.

### Тип `sql` (по умолчанию)

Задание выполняется в песочнице курса: ученик пишет SQL, движок его
запускает и оценивает результат.

**Песочница пересевается перед каждой попыткой.** Ядро выполняет seed
курса заново, потом запускает запрос ученика — и так на каждое нажатие
«Выполнить». Из этого следуют два правила для автора:

- задание обязано быть самодостаточным: всё, что ему нужно, создаёт seed.
  Задание вида «в прошлом уроке вы собрали витрину — теперь запросите её»
  не сработает, потому что витрины уже нет;
- ученик не увидит результат своего `UPDATE` вторым запуском. Если это
  часть задания, покажите в тексте урока, как писать изменение и проверку
  одним запуском (`update ...; select ...;` — показывается результат
  последнего оператора).

- `practice.sandbox` — обязателен; должен ссылаться на `id` одной из
  `sandboxes`, объявленных этим же курсом.
- `practice.check` — ровно один SQL-запрос, который после попытки
  пользователя выполняется от роли песочницы и обязан вернуть **одну
  строку с одним boolean-столбцом** (`true`/`false` — зачтено или нет).
  Проверяет **состояние базы**, поэтому годится для заданий, которые
  что-то меняют (`INSERT`/`UPDATE`/`DELETE`), и бесполезен для `SELECT`.
- `practice.expected` — эталонный SQL-запрос. Ядро выполняет его от роли
  песочницы в read-only транзакции **до** запроса пользователя (на
  свежезасеянной базе) и сравнивает **результат** ученика с результатом
  эталона. Это способ
  проверять `SELECT`-задания, которые ничего не меняют в базе.
  - `practice.ordered` — важен ли порядок строк. По умолчанию `false`
    (сравниваются мультимножества строк); `true` — сравниваются
    последовательности, то есть `ORDER BY` становится частью
    правильного ответа. Поле допустимо **только вместе с** `expected`.
  - Как сравниваются результаты: должно совпасть число столбцов (имена
    столбцов не сравниваются — алиасы свободны); `NULL` равен только
    `NULL`; числовые столбцы (`int`/`bigint`/`numeric`/`float`) равны с
    точностью до 1e-9; остальные значения — по текстовому представлению
    Postgres (даты и временные метки при этом сравниваются по значению).
  - Предел сравнения — 10 000 строк на сторону. Эталон, возвращающий
    больше, — ошибка конфигурации задания: ядро отвечает 422 и не
    пытается трактовать это как неверный ответ ученика.
  - Если SQL ученика завершился ошибкой Postgres, сравнение не
    выполняется: сравнивать нечего, пользователь уже видит текст ошибки.
- `practice.solution` — **эталонное решение задания**: тот SQL, которым
  его решает автор. Ядро выполняет решение на засеянной базе и запоминает
  получившееся состояние, засевает песочницу заново, выполняет запрос
  ученика и сравнивает состояния целиком — таблица за таблицей, построчно,
  без учёта физического порядка строк.
  - Это строгая механика для заданий, которые **меняют данные**. `check`
    отвечает только на тот вопрос, который автор догадался задать: для
    задания «отметь книгу 1 как отсутствующую» проверка `книга 1
    отсутствует?` пропускает `update books set in_stock = false` без
    `WHERE`, испортивший ещё четыре строки. Сравнение состояния ловит это
    само, без единой дополнительной строчки в манифесте — поэтому
    `npm run course:lint` предупреждает о задании, у которого есть только
    `check` (правило `practice-check-without-solution`).
  - `check` остаётся для условий, которые состоянием не выражаются
    («ни одна зарплата не стала отрицательной»), и для заданий, у которых
    правильных конечных состояний несколько.
  - **Решение обязано быть детерминированным**: ни `now()`/`random()` в
    самом решении, ни колонки в seed, чей `DEFAULT` меняется от запуска к
    запуску (`created_at timestamptz default now()` делает невыполнимым
    любое задание на `INSERT`). Если решение оставляет разные состояния,
    ядро отвечает 422 «сломанный контент курса» — а не «не зачтено»,
    потому что виноват тут не ученик.
  - Предел сравнения — 50 000 строк в одной таблице песочницы.
  - Строгость распространяется и на `id`: `delete` + `insert` вместо
    `update` оставит другое состояние (другой `id`, сдвинутая
    последовательность) и зачтён не будет.
- Ни `check`, ни `expected`, ни `solution` (как и верный вариант квиза)
  не покидают backend: клиенту достаётся только вердикт, а для `expected`
  и `solution` — ещё причина в терминах количеств («ожидалось строк: 19,
  получено: 22»; «таблица "books": ожидалось строк 5, получено 4»).

### Тип `answer`

Задание выполняется **за пределами платформы** — в Excel, в BI-дашборде,
на бумаге, — а сюда ученик вписывает полученные значения. Движок не видит
процесс и не проверяет его; он сверяет только результат. Песочница такому
заданию не нужна, и курс, состоящий только из таких заданий, может вообще
не объявлять `sandboxes`.

- `sandbox`, `check`, `expected`, `ordered`, `solution` при `type: answer`
  **запрещены** (валидация отклонит манифест, а не проигнорирует поле).
- `fields` — обязателен, минимум одно поле; `id` уникальны в пределах
  задания (это ключи, под которыми клиент отправляет ответы).
- У каждого поля: `id`, `label` (что показать ученику), `kind`
  (`number` или `text`) и `expected` — верный ответ.
  - `kind: number` — `expected` должен быть числом; необязательный
    `tolerance` (абсолютный допуск, `≥ 0`, по умолчанию `0` — точное
    равенство). Ответ ученика читается «как человек его пишет»: запятая
    как десятичный разделитель (`18,5`), пробелы как разделители тысяч
    (`1 234`, включая неразрывные пробелы из Excel), оба разделителя
    сразу в любой из двух конвенций (`1,234.56` и `1.234,56` — последний
    из `,`/`.` считается десятичным).
  - `kind: text` — `expected` должен быть непустой строкой; сравнение
    после `trim`, без учёта регистра и с нормализацией Unicode (NFC), то
    есть текст, скопированный из macOS-таблицы, не считается ошибкой.
    Ничего другого ядро не нормализует: внутренние пробелы и знаки
    сравниваются как написано, синонимы не угадываются. `tolerance` для
    текстового поля запрещён.
- Урок засчитывается, когда **все** поля верны; повторная отправка
  разрешена (исправить и проверить снова), а зачтённый урок не
  расзачитывается.
- Клиенту уходят только `id`/`label`/`kind` полей, а в ответ на отправку —
  один boolean на поле. Ни эталона, ни допуска, ни того, насколько ответ
  промахнулся, наружу не отдаётся.

  ```yaml
  practice:
    type: answer
    prompt: "Откройте romashka.xlsx и посчитайте показатели."
    fields:
      - id: headcount
        label: "Сколько сотрудников работает сейчас?"
        kind: number
        expected: 112
      - id: turnover
        label: "Текучесть за год, %"
        kind: number
        expected: 18.5
        tolerance: 0.2
      - id: top-reason
        label: "Самая частая причина увольнения"
        kind: text
        expected: "По собственному желанию"
  ```

> **Ограничение.** Эталонные ответы (`fields[].expected`, как и
> `check`/`expected` у `type: sql` и верный вариант квиза) лежат в
> `manifest.yaml` открытым текстом. Ученик, у которого есть доступ к
> файлам курса, может их прочитать. Для локального однопользовательского
> сервиса это приемлемо: пакет курса лежит на его же машине, и прятать
> ответы от владельца файла не имеет смысла.

- `sandboxes[].type` — на данный момент только `"postgres"`.
  `sandboxes[].seed` — список путей к `.sql`-файлам, выполняются по
  порядку от роли песочницы (никогда от роли приложения) при подключении
  курса и при каждом сбросе песочницы; вместе они должны пересоздавать
  всё, что нужно для практики курса с нуля (DDL + данные).

### Пример: `SELECT`-задание (`type: sql`)

```yaml
practice:
  sandbox: main
  prompt: "Выберите title и author книг в наличии."
  expected: "select title, author from books where in_stock = true"
  ordered: false
```

Если бы в задании требовался ещё и определённый порядок строк
(`ORDER BY` как часть правильного ответа), то же задание писалось бы с
`ordered: true`. Готовые примеры — уроки `practice-instock` (порядок не
важен), `practice-by-year` (`ordered: true`), `practice-add-book`
(`check`) и `self-check-books` (`type: answer`) в
`courses/pilot-sql/manifest.yaml`.

Полная схема (структурные правила, которые проверяет ядро до показа
курса пользователю) — `services/backend/src/courses/manifest.schema.json`;
её перечисления (`sandboxes[].type`, `practice.type`, `fields[].kind`)
тестами сверяются с реестром возможностей, так что схема и
`docs/contracts/capabilities.json` разойтись не могут.

## `skills.yaml` — план курса и его линт

Необязательный файл рядом с `manifest.yaml`. **Движок его не читает
вообще** — он нужен только линту. В манифесте лежит то, что исполняется; в
`skills.yaml` — замысел: какие умения курс строит, в каком порядке и чем
проверяется каждый урок. Разделение позволяет пересмотреть (или выбросить)
план, не трогая уже работающий манифест, и — главное — отревьюить **скелет**
курса машинно, до того как написан хоть один урок.

```yaml
version: 1                               # версия формата ЭТОГО файла, не курса
skills:
  - id: turnover-formula
    title: "Посчитать текучесть через среднесписочную численность"
    requires: [headcount-average]        # id других skills
lessons:
  - id: metrics-turnover                 # должен существовать в manifest.yaml
    teaches: [turnover-formula]
    requires: [metrics-headcount]        # id уроков, которые должны идти раньше
    verify: quiz                         # quiz | sql-state | sql-result | answer | self
    hours: 2
modules:
  - id: metrics
    budget_hours: 24
```

Значения `verify` и то, чему они должны соответствовать в манифесте:

| `verify`     | урок обязан нести                       |
|--------------|-----------------------------------------|
| `quiz`       | `quiz`                                  |
| `sql-state`  | `practice.check` (тип `sql`)            |
| `sql-result` | `practice.expected` (тип `sql`)         |
| `answer`     | `practice.type: answer`                 |
| `self`       | ни квиза, ни механики зачёта            |

Урок, несущий сразу и `check`, и `expected`, устраивает любой из двух
планов. Рабочий пример файла целиком — `courses/pilot-sql/skills.yaml`.

### Команда

```bash
npm run course:lint -- courses/pilot-sql        # можно перечислить несколько пакетов
```

Линт не требует ни поднятого стека, ни базы: он читает `manifest.yaml`,
`skills.yaml` и реестр возможностей движка. Код возврата — `1`, если есть
ошибки (предупреждения код возврата не меняют: предупреждение, способное
уронить сборку, начинают затыкать, а не читать). Пути в находках — из
манифеста (`modules[1].lessons[3]`), а если речь о записи самого плана —
с префиксом `skills.` (`skills.lessons[2].id`).

**Ошибки (E)**

- `lesson-unknown`, `lesson-undocumented`, `lesson-duplicated` — списки
  уроков в манифесте и в плане обязаны покрывать друг друга ровно.
- `lesson-requires-unknown`, `lesson-requires-order`,
  `lesson-requires-cycle` — пререквизиты урока существуют и идут **раньше**
  по порядку манифеста; кольца запрещены.
- `skill-unknown`, `skill-not-taught`, `skill-requires-unknown`,
  `skill-requires-order` — каждое умение кем-то преподаётся, все ссылки
  разрешаются, а пререквизит умения преподаётся раньше него самого.
- `verify-unsupported` — механика, которую называет `verify`, не
  зарегистрирована в движке (см. `docs/contracts/capabilities.json`).
- `verify-mismatch` — `verify` не совпадает с содержимым урока.
- `module-unknown` — бюджет выписан модулю, которого нет в манифесте (то
  есть бюджет, который никогда не применится).

**Предупреждения (W)**

- `long-stretch-without-checks` — 4+ урока подряд без квиза и практики.
- `module-without-checks` — в модуле нечего проверить вообще.
- `module-over-budget` — сумма `hours` модуля больше его `budget_hours`.

**Скелет.** Если версия курса в `manifest.yaml` несёт semver-суффикс
`-skeleton` (`0.1.0-skeleton`), то `verify-mismatch` понижается до
предупреждения: план пишется раньше контента, и требовать соответствия
ненаписанным урокам бессмысленно. `verify-unsupported` не понижается
никогда — возможности движка от готовности контента не зависят.

**Без `skills.yaml`** линт всё равно работает: он прогоняет те правила,
которым план не нужен (`long-stretch-without-checks`,
`module-without-checks`). Это полезно для курса, который ещё не
планировали.
