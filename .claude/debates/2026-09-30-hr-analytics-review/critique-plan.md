## Вердикты по фронтам (с расчётами)

### 1. A-1 (eNPS «весеннего опроса») — согласованный severity: **minor** (отзываю major)

Предлагаю явный критерий, по которому и сверялись с B:

- **blocker** — честный ученик не может пройти, или курс учит ложному без коррекции;
- **major** — дефект лежит на *основном честном пути*: ученик, следующий уроку/заданию
  как написано, получает незачёт или неверное знание (эталонный пример — Д-1 у B:
  формулы urока `E:E;"<>"` в настоящем Excel дают 52 и ~1 048 572 вместо напечатанных
  51 и 4, и приём урока валит его же практику);
- **minor** — основной честный путь цел; чтобы пострадать, нужно нетипичное прочтение.

Прогон A-1 через критерий: страница практики (metrics-practice-set.md:47-59) содержит
единственный опрос — декабрьский, таблица стоит прямо над полями, и «Впишите пять
ответов в поля ниже» связывает поля с таблицами страницы. Ответ 12 = (21−15)/50×100
выводится, не покидая страницы. Чтобы вписать 15 (опрос из metrics-engagement.md:27),
ученик должен предпочесть одно слово подписи («весеннего») всему условию — при том что
«весеннего» не соответствует и тому опросу тоже («в конце 2025 года»). Основной честный
путь цел → **minor**. Мой довод про tolerance 0 остаётся верным (цена ошибки — незачёт
поля), но он про цену маловероятной ветки, а не про вероятность. B прав; рассинхронизация
трёх файлов (manifest.yaml:283 ↔ metrics-practice-set.md:49 ↔ metrics-engagement.md:27)
остаётся фактом и правится одним словом и одной датой.

### 2. C-3 (константный SELECT) — **подтверждаю по коду**; фронт — задания; severity: minor изолированно, major только в связке C-1/C-2

Проверил сам, довод C воспроизводится:

- `services/backend/src/plugins/practice/sql/compare.ts:215-218` — дословно: «column
  COUNT must match. Column NAMES are not compared»; правила (строки 224-261): число
  столбцов → число строк → ячейки, причём столбец сравнивается численно, когда обе
  стороны числовые (:249-257 — «count(*) (bigint) против sum(1) (numeric) — всё ещё
  numeric»).
- `sql-aggregates`: эталон `select count(*), sum(fte) ... where termination_date is
  null` → 1 строка, 2 числовых столбца (120; 118.5). `select 120, 118.5` → 1 строка,
  2 числовых литерала → все три правила проходят. Значения напечатаны в том же уроке
  выше задания: sql-aggregates.md:23 «на 31 декабря 2025 она равна 118,5 при 120 людях».
- `sql-turnover-query`: эталон возвращает 1×1 `round(...,1)` = 19,4 (это видно и по
  README.md:126: «23 / ((117 + 120) / 2) = 19,4 %»). `select 19.4` — numeric против
  numeric → зачёт. Алиас не нужен — имена не сверяются.

Вердикт по принадлежности: это **фронт заданий (C)**, не плана. Мой фронт — порядок,
словарь, соответствие manifest↔skills↔уроки — этим дефектом не задет: лестница решаема
честно ровно пройденным материалом (что C сам подтвердил проходом всех 16 SQL). Дефект —
в сочетании «однострочный expected» + «значение опубликовано до/в уроке», т.е. в
конструкции проверки конкретных заданий.

Вердикт по severity: **изолированно C-3 — minor**: (а) обход требует намеренного
самообмана — ученик должен сам найти правильное число, чтобы его перепечатать; (б) навык
агрегатов переаттестуется в шести последующих многострочных SQL-заданиях (group-by 4
строки, joins 23, final-practice 5, capstone-data 8 — константой не пройти), т.е.
списавший провалится на следующей же ступени. **Major** этот вектор становится только
в совокупности с C-1/C-2 — на финальной трети (viz-практики, capstone-metrics), где
следующей ступени, которая бы переаттестовала, уже нет. Эту агрегатную оценку C
поддерживаю.

Следствие для моей позиции — см. «Что отзываю», п. 2.

### 3. B Д-3 (README «~150 человек» против 185) — **подтверждаю; признаю пропуск**

Проверил: README.md:19 — «Вымышленная ООО „Ромашка“: ~150 человек в данных за
2023–2025»; README.md:100 — «Сотрудников в данных всего | 185»; `employees.csv` — 185

среднесписочная 2024–2025 — 112,8–119,6. Строка неверна при любой трактовке.

Признаю пропуск честно: в раунде 1 я заявлял проверку «сквозной согласованности чисел»,
но мой охват был «уроки ↔ manifest ↔ данные»; прозу README (шапку-бриф) я не сверял —
Д-3 лежал ровно там. Это находка B, мой sweep её пропустил по границе охвата.

Уточнение к смягчению B («ученик README не видит — потому minor»): смягчение фактически
неточно — `lessons/capstone/capstone-story.md` отсылает ученика к README-таблицам
(артефакт C-2), так что README — объявленный учебный материал. Но строка 19 — в шапке
брифа, не в таблицах, к которым отсылают; severity **minor** оставляю согласованной.

## Атаки

- **На C, пункт C-4 («допуск покрывает неверный метод счёта») — отозвать или
  переименовать.** Research-digest B6: формула (HC начала + HC конца)/2 — это
  международный канон (SHRM/Mercer), а не «неверный метод»; курс сам учит обеим
  методикам и объясняет расхождение 19,2/19,4 (sql-turnover-query). Допуск ±0,3,
  покрывающий каноническую вторую методику, — осознанное и правильное решение плана,
  а поле `avg-headcount` 119,6 ± 0,2 (manifest.yaml:105-109) всё равно валит
  двухточечный метод, что C сам и показал. «Дефекта метода» здесь нет — есть
  корректная композиция полей; предлагаю C-4 снять.
- **На B — только уточнение смягчения Д-3** (см. вердикт 3: README — объявленный
  учебный материал по capstone-story.md); severity не меняю. По Д-1 возражений не
  имею — это лучший артефакт дебатов (эмпирический прогон инструмента).
- **На D, пункт D-1 (ФОТ/план-факт — major).** Его собственный falsifier требовал
  «обязанность из ≥2 независимых источников профиля»; предъявлен один источник
  (deynekina.ru). AIHR, changellenge, practicum (research-digest D2, D3) ФОТ/план-факт
  в требованиях к джуниору не называют, а замер hh.ru (research-digest D1) показал, что
  устоявшегося списка junior-требований на открытом рынке нет вовсе. По критериям самого
  D («если … в <20 % джуниорских вакансий — мои major понижаются до minor») D-1 без
  подтверждения частоты обязан быть minor. Пробел в покрытии реален (grep «ФОТ» — 0),
  major — нет.

## Что отзываю

1. **Severity A-1: major → minor** (критерий согласован с B, расчёт в вердикте 1).
   Отзыв с числом: вероятность вреда мала, потому что верный ответ выводится из таблицы
   на той же странице; цена (tolerance 0) не компенсирует вероятность.
2. **Свою атаку раунда 1 на C** — «анти-обходная конструкция заданий — явная и
   проверяемая» — **сужаю**: утверждение верно для многострочных SQL-эталонов (14 из 16)
   и композиции answer-полей модулей 1–2, и опровергнуто кодом compare.ts для двух
   однострочных SQL (C-3) и утечками чисел для финальной трети (C-1/C-2). Требование
   «покажи конкретный обход» C выполнил — признаю.
3. **Формулировку раунда 1 «единственное место, где честная работа может не зачесться, —
   мой A-1»** — отзываю как ошибочную: Д-1 (excel-formulas) — более сильный случай
   ровно этого класса (и на основном пути, потому major), C-6 (`::date`) — третий,
   маргинальный. Исполнение формул в инструментах мой статический sweep не покрывал —
   границу охвата фиксирую явно.
