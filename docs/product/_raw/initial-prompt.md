# Trellis — локальный конструктор учебных курсов

Этот документ описывает **только сам сервис** — движок, на котором работают курсы. Он намеренно ничего не знает о содержимом конкретных курсов (первый пилотный курс генерируется отдельно, в другом рабочем процессе, и подключается к этому сервису как контент-пакет).

## 1. Идея и цель

Локальный, бесплатный, самостоятельно разворачиваемый сервис для прохождения учебных курсов. Не привязан к одной теме: ядро специальность-агностично, а конкретный курс подключается как отдельный контент-пакет — так же, как модуль подключается к конструктору. Первый курс — пилот, на котором обкатывается сама платформа; после него курсов может быть несколько, разных тематик.

MVP делается вручную (один человек проходит один курс на одном компьютере), но с самого начала проектируется так, чтобы:
- легко добавлялся второй, третий курс без переделки ядра;
- архитектура не противоречила описанному ниже долгосрочному видению (раздел 7), даже если само видение сейчас не реализуется.

## 2. Ключевые принципы архитектуры

- **Ядро + контент-пакеты.** Движок (прогресс, квизы, импорт/экспорт, Docker-оркестрация) не содержит знаний о конкретном курсе. Курс — это данные, которые проходят валидацию по схеме, а не код.
- **Развязка контента и прогресса.** Формат определения курса (модули/уроки/квизы) и формат состояния прогресса пользователя — разные сущности с чёткой границей. Замена или обновление курса не должна ломать сохранённый прогресс по другому курсу.
- **Практика — через декларируемые песочницы.** Если курсу нужна практическая среда (например, реальная база данных для SQL-упражнений), это не часть ядра, а отдельный, изолированный ресурс, который курс сам объявляет в своей конфигурации. Ядро умеет поднимать объявленные ресурсы, но не обязано знать, что это за ресурс конкретно.
- **Локально, без внешнего бэкенда.** Всё работает на компьютере пользователя. Нет облачного сервера, нет отправки данных наружу.

## 3. Архитектура MVP

- **Fullstack**: React-фронтенд + backend (кандидат: Node/Express; альтернатива — PostgREST поверх схемы, если хочется меньше кастомного серверного кода — решение не финализировано) + Postgres.
- **Docker**: весь стек поднимается через `docker-compose`. Без Electron. Не разворачивается на удалённый сервер — только `localhost`.
- **Запуск**: единый скрипт для Windows (`.bat`/`.ps1`, не `.sh` — целевая платформа пользователя Windows). Скрипт должен быть отказоустойчивым:
  1. проверить, запущен ли Docker Desktop; если нет — попытаться запустить и дождаться готовности демона;
  2. поднять контейнеры (`docker-compose up`);
  3. дождаться healthcheck у Postgres;
  4. открыть браузер на `localhost:<порт>`.
  Каждый шаг — с понятным сообщением пользователю, а не тихим зависанием.
- **Postgres**: обязательно именованный volume — иначе пересборка контейнеров = потеря прогресса.
- **Практика с БД**: отдельная схема/роль внутри того же Postgres-инстанса, с правами, ограниченными только этой схемой — пользователь физически не может испортить данные платформы через практические задания.

## 4. Прогресс пользователя

- Хранится локально в Postgres.
- Перенос между компьютерами (например, дом/работа) — через экспорт/импорт: дамп или выгрузка состояния в переносимый файл.
- Файл экспорта должен нести метку времени последнего сохранения. При импорте — предупреждать, если импортируемый файл старше уже существующего локального прогресса, чтобы не затереть более новые данные более старыми.

## 5. Формат курса (контракт для контент-пакетов)

Курс — это строго валидируемая структура (JSON/YAML), а не свободный текст. Ядро должно уметь:
- проверить курс на соответствие схеме до того, как показать его пользователю;
- работать с любым количеством модулей/уроков без хардкода конкретных названий.

Минимально курс описывает:
- метаданные (название, версия, требуемые песочницы практики, если есть);
- список модулей → уроков;
- для урока — текстовый контент и/или квиз;
- квиз — вопрос, варианты ответа, единственно верный вариант, текст объяснения для каждого неверного варианта.

Квиз-механика на уровне UI: при выборе неверного варианта — подсветка и объяснение, почему он неверен; попытки не блокируются до выбора верного варианта; при верном — визуальное подтверждение.

*(Точная спецификация схемы — отдельная задача, её нужно закрыть до начала генерации содержимого курсов. Этот документ фиксирует только требования к схеме, не саму схему.)*

## 6. Дизайн

Минималистичный, дружелюбный интерфейс. Базовая палитра — мягкие зелёные тона.

## 7. Долгосрочное видение (НЕ входит в MVP)

Ниже — направление, в которое сервис может вырасти в будущем. Это не задача для текущей разработки, но архитектурные решения MVP не должны явно противоречить этому направлению:

- Упаковка в SaaS, где пользователи сами создают курсы с помощью ИИ.
- Общий marketplace курсов с оценками.
- Тарифы для физлиц и компаний.
- Авторы курсов назначают цену, платформа берёт комиссию с продажи.
- Ключевая фича: подключение внешних сервисов как «коннекторов» (по аналогии с коннекторами Claude) — например, курс по Excel мог бы через Excel API создавать страницы для практики прямо внутри урока.

Практическое следствие для MVP: механизм «песочниц практики» (раздел 2 и 3) стоит проектировать как интерфейс, у которого Postgres — только одна из реализаций, а не единственная. Это не требует делать полноценную систему плагинов сейчас, но называть вещи и структурировать код так, чтобы второй тип песочницы не потребовал переписывать первый.

## 8. Открытые вопросы

- Выбор бэкенд-стека: Node/Express vs PostgREST.
- Как засчитывать выполнение практики во внешних инструментах: для SQL возможна программная проверка (выполнить запрос, сравнить результат), для Excel и подобного — решение не найдено (самоотметка vs разбор загруженного файла).
- Точная схема курса и схема прогресса — нужно спроектировать до начала генерации содержимого курсов.
- Название сервиса — рабочее (Rostok / Trellis), не финализировано.
