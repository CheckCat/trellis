# Analysis: grey zones

## Принятые решения (X, а не Y)

- **Docker + браузер, а не Electron** — весь стек через `docker-compose`, UI в браузере на `localhost`.
- **Скрипт запуска `.bat`/`.ps1`, а не `.sh`** — целевая платформа пользователя Windows.
- **Песочница SQL — отдельная схема/роль в том же Postgres-инстансе, а не отдельный инстанс** — права ограничены схемой, данные платформы недоступны из практики.
- **Курс — данные со схемой, а не код/свободный текст** — валидация до показа пользователю.
- **Песочницы — интерфейс, а не хардкод Postgres** — Postgres лишь одна из реализаций; без полноценной системы плагинов сейчас.
- **Backend — Fastify (Node/TypeScript), а не Express/PostgREST** — источник оставлял вопрос открытым (Node/Express vs PostgREST); оператор при упаковке brief выбрал Fastify (2026-09-15). Под этот выбор в mvp-плагин добавлена поддержка `backend: fastify`.
- **Deploy — docker-compose локально, а не docker-dokploy** — allowlist mvp-плагина содержал только docker-dokploy, что противоречило требованию «только localhost»; оператор выбрал docker-compose, поддержка добавлена в плагин (2026-09-15).

## Решения прогона задач 001–006 (2026-09-16)

Приняты главной сессией по ходу реализации фаз 1–3; каждое проверено фактически.
Записаны здесь, потому что это входные условия для ещё не сделанных задач.

- **Внутри контейнера backend слушает `0.0.0.0`, а не `127.0.0.1`** — «наружу не
  публикуется ничего» обеспечивается публикацией порта как `127.0.0.1:3001:3001`
  в compose. Бинд на loopback внутри контейнера сделал бы сервис недостижимым.
- **Порты, роли, схемы (контракт всего стека)**: БД `trellis`; роли
  `trellis_app` (владелец схемы `core`) и `trellis_sandbox` (владелец `sandbox`);
  volume `trellis_pgdata`; порты на хосте только `127.0.0.1` — frontend `3000`,
  backend `3001`, postgres `5433`.
- **Тесты backend гоняются по скомпилированному выводу** (`tsconfig.test.json` →
  `dist-test/`), а не через нативный type-stripping Node: он требует Node ≥22.18,
  а на машине разработки 22.16, и `node --test` по `.ts` там молча находил ноль
  тестов, выходя с кодом 0. Прод-сборка исключает `*.test.ts`.
- **Init-скрипты Postgres выполняются ровно один раз**, на пустом volume.
  Следствие: пароли ролей фиксируются при первом запуске, смена их в `.env`
  превращает стек в кирпич, единственный выход — `down -v` с потерей прогресса.
  Механизм ротации — задача 018 (см. ниже).

### Входные условия для конкретных задач

- **008 (песочница)**: «сбросить песочницу» делать как
  `DROP OWNED BY trellis_sandbox; CREATE SCHEMA sandbox;`, а НЕ через
  `DROP SCHEMA sandbox CASCADE`. Проверено: sandbox-роль имеет `CREATE` на базе
  (нужен для пересоздания своей схемы) и может создать постороннюю схему,
  которая переживёт сброс по имени. Данные платформы при этом недостижимы —
  изоляция цела, неполон именно сброс.
- **008 (песочница)**: формат контент-пакета допускает несколько песочниц на
  курс и несколько курсов, а инфраструктура даёт одну схему `sandbox`. До начала
  реализации нужно решить, что такое «песочница курса», когда курсов больше
  одного — иначе придётся либо сужать формат, либо переписывать init-скрипты,
  которые после первого запуска пользователя недостижимы.
- **009 (выполнение практики)**: `resolveSafePath` из
  `services/backend/src/courses/validate/validate.ts` экспортирована — используй её,
  не дублируй защиту от `..` и симлинков. `Course.dir` НЕЛЬЗЯ использовать как
  базу проверки принадлежности (он лексический, не realpath) — только
  `resolveSafePath`.
- **017 (пилотный курс)**: эталон схемы манифеста — в `.mvp/reports/task-006.md`.
  Битый симлинк непосредственно в `courses/` должен попадать в «отклонённые» с
  человекочитаемой причиной; сейчас он исчезает молча, и в контейнере
  (`./courses:/courses:ro`) любой симлинк наружу заведомо висячий.
- **018 (скрипт запуска)**: диагностика «ядро не поднялось» не может жить в UI —
  при нездоровом backend фронт поднимается, но показывает только «связи с ядром
  нет», без причины; при провале миграций backend уходит в бесконечный рестарт и
  никогда не станет healthy. Всё это скрипт обязан объяснить на консоли. Туда же
  — механизм смены паролей ролей. И `docker compose up --wait` использовать
  нельзя (или ждать только postgres/backend): healthcheck фронта теперь зависит
  от `/api/health`, поэтому при мёртвом backend фронт числится unhealthy, хотя
  исправно показывает экран «связи нет».
- **011/015 (UI)**: `App.tsx` из скелета ходит в API через `useEffect` + `fetch`
  без слоя данных — это временное решение, его надо заменить типизированным
  HTTP-клиентом, а не тиражировать по экранам.
- ~~**007 (прогресс) — долг**: `.mvp/ci-mirror.sh` не поднимает Postgres~~ —
  закрыто 2026-09-16: скрипт сам поднимает одноразовый Postgres (свой контейнер,
  эфемерный порт, без тома, гарантированная уборка) и даёт 62/62 без скипов.
  Применение init-скриптов вынесено в общий `docker/postgres/init/apply-all.sh`,
  который используют CI, compose и ci-mirror. Важное свойство, которое нельзя
  потерять при правках: зелёный выход невозможен, если БД-тесты не исполнились —
  готовность проверяется по тому же внешнему адресу, что уходит в
  `DATABASE_URL`, а после прогона скрипт падает, если при доступном Docker
  остались пропущенные тесты.

## Практика кода (2026-09-23)

- **Механика — функция + `cases` + `solution`, а не программа со stdin/stdout** — возвращаемые значения сравниваются структурно (JSON с маркерами для undefined/NaN/Infinity/bigint/Date/Map/Set), вывод в консоль показывается, но не проверяется. Текстовое сравнение stdout хрупко (пробелы, переводы строк), а инвариант запрещает авторский код-грейдер — значит эталон должен быть данными или решением.
- **Исполнение — дочерний процесс `node` в backend-контейнере, а не отдельный контейнер и не `worker_threads`** — симметрично Postgres-песочнице (отдельная роль в том же инстансе). Отдельный контейнер дал бы настоящую границу ценой четвёртого сервиса, паритета лаунчеров и более долгого холодного старта; `worker_threads` делил бы процесс с backend (OOM/нативное падение роняет сервер, `process.env` с паролями БД доступен коду). Процессная изоляция достаточна для локального продукта одного пользователя; при появлении многопользовательского сценария первым делом выносить раннер в контейнер — интерфейс `CodeRunner` (`plugins/practice/code/run-node.ts`) это позволяет без правок маршрута.
- **Без нового типа песочницы** — `SandboxDriver` (`provision(seed)`, одна живая песочница, `withFreshSandbox`) описывает накапливающее состояние; у кода его нет. Раннер живёт внутри плагина, `language` — свойство задания, не курса.
- **TypeScript через `--experimental-strip-types`, без транспилятора** — ноль зависимостей backend; флаг обязателен на 22.16 (машина разработки) и безвреден на 22.23 (образ). Цена: только «стираемый» TS (`enum`, `namespace`, parameter properties отклоняются Node при импорте → `load_failed`), типы не проверяются. Записано в capabilities и в README курсов.
- **Правила кодирования значений продублированы** в `compare.ts` и в тексте harness (`harness.ts`): harness — самостоятельный скрипт во временной папке и импортировать пакет не может. Совпадение двух копий закреплено тестом `run-node.test.ts` («the harness encodes values exactly like compare.ts»).
- **Harness держит event loop живым таймером** — иначе функция, вернувшая неразрешающийся Promise, завершала бы процесс кодом 13 (unsettled top-level await) и читалась как «аварийное завершение», а не как «превышено время». Найдено тестом Review Focus 1 при реализации.
