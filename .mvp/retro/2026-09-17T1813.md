надо исключать.

## Дефекты пайплайна, найденные этим прогоном

Два halt'а, оба — в плагине, не в проекте. `blockers.md` в проекте нет: ни один
диспатченный агент не сообщил о дефекте вне своей границы.

### 1. Финализирующий relay переписывает команду вместо дословного исполнения

Задача 018. `finalize()` собирает цепочку из трёх звеньев и отдаёт её relay-агенту
(haiku) с инструкцией «Run exactly this command». Concern-текст 018 был
многострочным (3 concern'а, внутри — JSON ревью-находок с экранированными
кавычками) и пришёл в `--concern` одним `shQuote`-аргументом. Агент строку не
воспроизвёл, а **переписал**: закрыл кавычку `--concern` раньше и вынес остаток в
выдуманный флаг.

Verbatim из его Bash-вызова (journal `agent-ae2b835e2d76981b7.jsonl`):

```
... --concern 'CONCERN 1: ... все ветки дали ожидаемый результат.' --findings '[{"severity":"bug","file":"start.ps1",...}]'
```

Результат: `{"ok":false,"reason":"unknown flag: --findings","hint":null,"data":null}`.

Цена: первые два звена уже отработали — задача была помечена `done` и **закоммичена**
(`4aba7f6`), упало третье. `park()` перевёл 018 в `failed`, аудит-след (строка Task
и 4 concern'а) потерялся. Восстановление стоило одного повторного вызова
`plan-io.mjs ledger` тем же аргументом, но сам факт «relay может переписать
команду» делает ненадёжным любой вызов с длинным свободным текстом в argv.

### 2. Парсер `CANNOT_VERIFY` считает `none — <пояснение>` за «не none»

Задача 019, halt `stop-and-ask`: «2 of 3 reviewers could not verify». Фактически
содержательный `CANNOT_VERIFY` был один. Verbatim из `.mvp/review/task-019.verdicts.md`,
reviewer-019-2:

```
CANNOT_VERIFY: none — ran `npm run test:e2e` myself (docker compose up --build
against the real stack): 15/15 subtests pass; verified teardown leaves no
containers/volumes/networks and `git status` clean afterward.
```

Ревьюер написал `none` и добавил, **как именно** он это проверил — то есть повёл
себя лучше требуемого. Парсер поднял на этом ложный halt.

### 3. Гейт полноты ревью недостижим, когда deliverable намеренно вне CI

Тот же halt, вторая половина. Verbatim, reviewer-019-1:

```
`.mvp/ci-mirror.sh` runs `npm run lint/build/test`, never `test:e2e` — this is a
deliberate, documented choice, but it means the pre-dispatch "CI mirror is green"
confirmation never actually executes this task's core deliverable.
```

Это верно по существу и **перезапуском не лечится**: условие гейта (предревьюная
сверка исполняет deliverable) недостижимо, пока e2e осознанно вне CI. Задача
такого класса уходит в бесконечный halt-цикл.

### 4. `dirty-check` в `next` стоит до ветки `--task` — запаркованную задачу с
границей в корень репозитория нельзя передиспатчить

`lib/plan-io.mjs:705-707` — проверка грязного дерева выполняется **до** выбора
задачи, то есть и до ветки с явным `task_id`. Одновременно `park()` по design note
18 осознанно **не** сбрасывает дерево, когда граница нормализуется в корень. Два
верных по отдельности решения дают тупик: работа задачи остаётся в дереве, дерево
грязное, `next` отдаёт `dirty-tree` раньше, чем успевает посмотреть на `--task`.
Выходов ровно два — снести готовую работу или финализировать в обход workflow.

### 5. Роли из bootstrap не диспатчатся в той же сессии

Три задачи (007, 008, 021) прошли на `general-purpose` вместо назначенной роли.
Verbatim из `ledger.md`:

```
agentType "backend-implementer" did not dispatch — this task ran on
general-purpose, WITHOUT the _common.md contract (boundary rules, report format,
blocker protocol) that mvp:bootstrap assembled for it. Agents register at session
start, so a bootstrap run in this same session yields files that are not
dispatchable until the next one.
```

Диагностика в concern'е точная и самим пайплайном записана — не хватает только
того, чтобы `mvp:bootstrap` не отпускал оператора в `mvp:build` до перезапуска сессии.

## Открытые риски проекта (не плагина)

Не кандидаты в правку плагина — вход для приёмки и для `.mvp/invariants.md`:

1. **Windows не исполнялся ни разу.** `start.bat` и ветка автозапуска Docker
   Desktop вычитаны построчно, но не запускались: Windows в окружении нет.
   `start.ps1` прогнан под PowerShell 7.4.6 на macOS по шести сценариям.
   Сквозной тест 019 Windows-вход не покрывает. Первый запуск на реальной Windows
   остаётся приёмочной проверкой за пользователем.
2. **`npm run test:e2e` вне CI осознанно** (нужен Docker Compose ≥ 2.24). Значит
   регресс сквозного сценария CI не поймает — команду надо гонять руками перед
   выпуском. Это же и есть причина halt'а на 019.
3. **NUL-гейт покрывает исходники, но не `.mvp/`** (задача 021 сузила область
   намеренно: ревью-пакеты законно цитируют произвольные байты). Значит класс
   «исходник стал бинарным для git» закрыт, а «аудит-след стал бинарным» — нет.
