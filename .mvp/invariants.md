# Project invariants — Trellis

## Architectural invariants

- Ядро специальность-агностично: код backend/frontend не содержит знаний о конкретном курсе. Курс — данные (контент-пакет в `courses/`: manifest.yaml + Markdown-уроки), проходящие валидацию по схеме до показа пользователю. Хардкод названий модулей/уроков курса в коде запрещён.
- Развязка контента и прогресса: формат курса и формат прогресса — разные сущности с чёткой границей. Прогресс привязан к стабильным id модулей/уроков, никогда к индексам или названиям.
- Зачёт одного урока необратим: поурочной отмены нет. Стереть прогресс можно только целиком по курсу и только по явной просьбе ученика (`DELETE /courses/:id/progress`, «Перепройти курс») — это единственная удаляющая операция над `core.lesson_progress`.
- Эталоны ответов не уезжают вместе с заданием. Единственный способ их увидеть — отдельный маршрут раскрытия для `answer`-заданий, вызываемый только по явному действию ученика; ни `GET /courses/:id/lessons/:id`, ни один ответ проверки эталона не содержат.
- Песочница практики — интерфейс с реализациями; Postgres — лишь одна из них. Именование и структура кода не должны требовать переписывания первой реализации при появлении второй.
- Postgres-песочница: отдельная схема + роль с правами только на эту схему. Seed-, check-, expected- и solution-запросы курса, как и запросы пользователя, выполняются от sandbox-роли — никогда от роли приложения или суперпользователя.
- Каждая попытка SQL-практики выполняется на песочнице, только что пересобранной из seed курса. Состояние не переносится ни между уроками, ни между попытками одного урока: задание не может опираться на то, что ученик сделал раньше, и не может быть испорчено этим. Отсюда же следствие: ручного сброса песочницы нет — сбрасывать нечего.
- Эталон механики (`expected`, `solution`) снимается с эталонной базы ДО запроса ученика. Иначе `delete from t; select * from t;` сравнивает два пустых набора и получает зачёт.
- SQL-задание обязано быть самодостаточным: всё, что ему нужно, даёт seed курса. Задание, рассчитывающее на результат предыдущего урока, при пересеве невыполнимо — это ограничение движка, а не недосмотр автора.
- Зачёт практики — только декларативные механики, зарегистрированные в ядре (сейчас: `check` — состояние базы → один boolean; `expected` — сравнение результата с эталонным запросом; `solution` — сравнение состояния базы с состоянием после эталонного решения автора; `fields` — сверка введённых учеником ответов с эталонными значениями, для заданий без песочницы; `cases` — вызов экспортированной функции ученика на объявленных аргументах и сравнение возвращённого значения с `cases[].expected` или с результатом `solution` автора, для заданий на код). Произвольный код-грейдер в составе курса запрещён: `solution` — это решение задачи, а не логика проверки.
- Код практики (`practice.type: code`) исполняется дочерним процессом `node` внутри backend-контейнера: свежий процесс на каждый прогон, пустой `env`, временный `cwd`, таймаут с `SIGKILL`, лимит кучи, лимит вывода. Изоляция процессная, не security-граница (код видит ФС и сеть контейнера) — модель угроз та же, что у `node file.ts` в терминале ученика на его же машине. Эталон (`solution`) исполняется до кода ученика, отдельным процессом. Нового типа песочницы нет: у кода нет накапливаемого состояния, которое `SandboxDriver` описывает.
- Механика практики или тип песочницы существует, только если зарегистрирована в `services/backend/src/capabilities.ts`. Реестр — единственный источник истины: из него выводятся доменные типы, с ним сверяются enum'ы `manifest.schema.json`, и он же экспортируется в `docs/contracts/capabilities.json` (проверяется в CI) и по `GET /capabilities`. Добавление механики = новый модуль + запись в реестре; `routes/practice/index.ts` и `sandbox/provisioner.ts` при этом не меняются — они диспетчеризуют по реестру.
- Всё локально: backend слушает только 127.0.0.1, наружу порты не публикуются; никаких внешних сервисов и отправки данных наружу.
- Данные прогресса — только в Postgres с именованным volume; пересоздание контейнеров не должно терять данные.
- Frontend работает с данными только через HTTP API backend; прямых подключений frontend к Postgres нет.

## Service boundaries

- backend: services/backend
- frontend: services/frontend
- postgres (инфраструктура, без кода): docker-compose.yml + docker/postgres/

## Forbidden edges

FORBIDDEN_EDGE: frontend --> postgres
FORBIDDEN_EDGE: frontend --> sandbox
BOUNDARY_EXEMPT: package.json
BOUNDARY_EXEMPT: package-lock.json
