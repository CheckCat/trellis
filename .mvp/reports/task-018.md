# Task 018 — скрипт запуска для Windows — отчёт

## Что создано

| Файл | Что это |
|---|---|
| `start.ps1` | вся логика запуска (748 строк, UTF-8 **с BOM**, комментарии/сообщения по-русски) |
| `start.bat` | точка входа для двойного клика: подбирает pwsh/powershell, `-ExecutionPolicy Bypass`, `chcp 65001`, `pause`, прокидывает `%*` и код возврата. Только ASCII |
| `docs/run-windows.md` | пользовательская инструкция: установка, запуск, остановка, `.env`, смена паролей, таблица «симптом → что делать», полный сброс |
| `.gitattributes` | **новый файл, сверх списка в брифе**: `*.bat`/`*.ps1` → `text eol=crlf` (см. ниже) |

`docker-compose.yml`, `.env.example`, CI и код сервисов **не трогались**.

## Контракт запуска (для задачи 019 и для ревью)

```
start.bat            → start.ps1              # обычный запуск
start.bat -SyncPasswords → start.ps1 -SyncPasswords
.\start.ps1 [-SyncPasswords]                  # то же напрямую из PowerShell
```

- Код возврата: `0` — платформа готова; `1` — любая диагностированная проблема
  (единственная точка выхода с ошибкой — `Stop-WithProblem`).
- Успешный финал печатает `http://localhost:<FRONTEND_PORT>` и **не открывает
  браузер** (инвариант проекта, Q-013).
- Скрипт работает из своей папки (`Set-Location $PSScriptRoot`) — его можно
  запускать двойным кликом из любого места.
- При ошибке контейнеры **намеренно не останавливаются**: журналы остаются
  доступны, а интерфейс (если поднялся) показывает своё «Связи с ядром нет».
- Переменная окружения `TRELLIS_NO_PAUSE=1` отключает `pause` в `start.bat`
  (для вызова из другого скрипта — например, из smoke-теста задачи 019).

### Разбор журналов (какие строки ищутся)

- **postgres**: `APP_DB_PASSWORD|SANDBOX_DB_PASSWORD` → пустые пароли в `.env`;
  `database files are incompatible` → чужая версия PG, только `down -v`.
- **backend**: `password authentication failed` → расхождение пароля `.env` и
  базы + рецепт `-SyncPasswords`; `ECONNREFUSED|getaddrinfo|ENOTFOUND` → сеть до
  базы; `migration|migrate|миграц` → миграции не применились (тот самый вечный
  рестарт из analysis-grey-zones). В любом случае добавляется строка о том, что
  интерфейс покажет «Связи с ядром нет», а настоящая причина — в журнале.
- **frontend**: объяснение, что его healthcheck идёт через `/api/health`, то есть
  зависит от живого ядра.

Журнал печатается ДО объяснения и обрезается: `--tail 25`, каждая строка до 300
символов (ядро пишет pino-JSON со стеком — целиком это стена текста; ключевое
«password authentication failed…» в 300 символов попадает, проверено).

## Механизм смены паролей ролей (`-SyncPasswords`)

Закрывает долг, оставленный `final-review-fixes-infra.md` (Important 3):
`/docker-entrypoint-initdb.d` отрабатывает только на пустом томе, поэтому смена
пароля в `.env` после первого запуска раньше означала вечный рестарт backend и
единственный выход `down -v` (потеря прогресса).

```
$sql | docker compose exec -T postgres psql -v ON_ERROR_STOP=1 -U postgres -d trellis
ALTER ROLE trellis_app      WITH PASSWORD '<APP_DB_PASSWORD из .env>';
ALTER ROLE trellis_sandbox  WITH PASSWORD '<SANDBOX_DB_PASSWORD>';
ALTER ROLE postgres         WITH PASSWORD '<POSTGRES_PASSWORD>';
```

- Работает изнутри контейнера через unix-сокет, где официальный образ Postgres
  доверяет суперпользователю без пароля → механизм работает даже когда в `.env`
  лежит уже неверный `POSTGRES_PASSWORD`.
- SQL идёт в **stdin**, не в argv: пароль не светится в списке процессов.
  Экранирование — `ConvertTo-SqlLiteral` (удвоение `'`).
- Выполняется после того, как postgres стал healthy, затем
  `docker compose restart backend`, затем обычное ожидание готовности.
- `.env` — источник правды; база подстраивается под него. Прогресс не теряется
  (проверено: том `trellis_pgdata` тот же самый до и после).

## Решения, влияющие на других

- **`up -d --build`, а не `up -d`**: иначе после обновления исходников Docker
  молча оставит старый образ. Побочный эффект — сборка обращается к Docker Hub
  даже за локально существующим базовым образом, поэтому есть откат: сеть
  недоступна → повтор → `up -d` без сборки на ранее собранных образах (запуск
  «без интернета» работает) → и только потом отказ с объяснением.
- **Никакого `--wait`** у compose — как и требовала analysis-grey-zones:
  healthcheck фронта ходит в `/api/health`, при мёртвом ядре compose откатил бы
  запуск, и пользователь получил бы «connection refused» вместо честного экрана
  «Связи с ядром нет».
- **Пароли только `[A-Za-z0-9._~-]`** (и генерируются из `[A-Za-z0-9]`, 28
  символов, crypto-RNG с отбраковкой для равномерности): пароль подставляется в
  `postgres://trellis_app:<пароль>@postgres:5432/trellis`, спецсимволы ломают
  разбор URL раньше, чем дело дойдёт до базы. Проверка — до запуска, с
  человекочитаемым объяснением.
- **`.env` пишется UTF-8 без BOM, CRLF**: BOM уехал бы в имя первой переменной.
  CRLF проверено фактически — `docker compose config` отдаёт значения без `\r`.
- **`start.ps1` сохранён с BOM**: Windows PowerShell 5.1 читает BOM-less файл в
  ANSI-кодировке системы, и весь русский текст стал бы кракозябрами. `.bat` —
  наоборот, строго ASCII (cmd читает его в текущей кодовой странице).
- **`.gitattributes`** (файла в проекте не было): `*.bat`/`*.ps1` →
  `text eol=crlf`. cmd.exe требует CRLF в `.bat` (LF ломает многострочные
  блоки), а `.ps1` с LF выглядит одной строкой в Notepad — том самом редакторе,
  которым файл откроет не-разработчик. В репозитории хранится LF.

## Верификация (фактические прогоны)

PowerShell на Windows здесь нет, поэтому скрипт прогонялся под PowerShell 7.4.6
на macOS (ветка автозапуска Docker Desktop под `$IsWindows` в этом случае
пропускается — на macOS демон уже запущен) против **настоящего стека**:

1. Синтаксис: `[Parser]::ParseFile` — 0 ошибок.
2. Чистый старт с нуля (нет `.env`, нет тома, нет образов): `.env` создан со
   случайными паролями → сборка → postgres/backend/frontend healthy → адрес,
   код 0. `curl http://localhost:3000/` → 200, `/api/health` → `{"status":"ok","db":"ok"}`.
3. Порт занят (питоновский listener на 127.0.0.1:3000) → «нужный порт уже занят
   другой программой», названы все три `*_PORT`, код 1.
4. Обрыв связи с Docker Hub (случился сам, дважды) → автоповтор → объяснение про
   интернет/прокси, код 1. Регулярки проверены отдельно: реальный текст ошибки
   реестра матчится, «port is already allocated» и «unexpected EOF» — нет.
5. Пароль в `.env` изменён после первого запуска → backend в crash-loop →
   скрипт не ждёт таймаут, печатает обрезанный журнал с `password
   authentication failed` и рецепт `-SyncPasswords`, код 1.
6. `.\start.ps1 -SyncPasswords` → пароли ролей обновлены, backend перезапущен,
   стек снова полностью healthy, код 0; `trellis_pgdata` — тот же том (создан
   при шаге 2), схемы `core`/`sandbox` на месте, прогресс не потерян.
7. Пустой `APP_DB_PASSWORD` и `SANDBOX_DB_PASSWORD=p@ss/word` → два разных
   отказа на шаге 2/5, до запуска Docker.
8. `bash .mvp/ci-mirror.sh` — код 0 (12 файлов тестов, 43 + backend-тесты, без
   скипов).
9. `git status` вне границы чист: изменены только `start.ps1`, `start.bat`,
   `docs/run-windows.md`, `.gitattributes` (+ `.mvp/ledger.md` и
   `.mvp/briefs/task-018.md` — не мои, артефакты пайплайна).

## Не проверено (честно)

- `start.bat` и ветка автозапуска Docker Desktop **не прогонялись на живой
  Windows** — Windows в этом окружении нет. `start.bat` вычитан построчно:
  `if errorlevel 1` вместо `%ERRORLEVEL%` внутри блока (иначе раннее
  раскрытие), `%~dp0` с кавычками (пробелы в пути), код возврата сохраняется
  до `pause`. Ветка автозапуска Docker Desktop под `$IsWindows` на macOS не
  исполнялась ни разу.
- Совместимость с Windows PowerShell 5.1 обеспечена конструктивно (нет `??`,
  тернарников, `-Encoding utf8NoBOM`, `::GetInt32`; splatting, `[pscustomobject]`,
  `New-Object` — всё 5.1-совместимое), но исполнением не подтверждена.

## Deferred decisions

- Ожидание готовности — собственный цикл по `docker inspect`, а не
  `docker compose up --wait`: `--wait` завязан на healthcheck фронта, который
  зависит от живого ядра (см. выше), и не даёт разного объяснения для разных
  сервисов.
- `--tail 25` и обрезка строки до 300 символов вместо полного журнала —
  trade-off читаемости против полноты; полная команда `docker compose logs
  <service>` названа в подсказке.
- Порог crash-loop — 3 рестарта: меньше даёт ложные срабатывания на медленном
  холодном старте, больше — бессмысленное ожидание.
- Один автоматический повтор `up --build` при сетевой ошибке (не два и не
  экспоненциальный backoff): обрыв до Docker Hub в этом окружении случался
  через раз, а длинная серия повторов превращает «отказоустойчивость» в то
  самое тихое зависание.
- `ALTER ROLE postgres` в `-SyncPasswords` тоже выполняется, хотя пароль
  суперпользователя стеку не нужен (backend ходит под ролями приложения,
  healthcheck — `pg_isready` без пароля): иначе `.env` остался бы частично
  враньём. `log_statement` в образе по умолчанию `none`, в журнал пароли не
  попадают.
- Пароли в сгенерированном `.env` — 28 символов `[A-Za-z0-9]`: длина
  компенсирует сужение алфавита, сделанное ради безопасной подстановки в URL.

## Fix round (ревью findings)

Найдено 5 findings (1 bug, 4 minor). Разобраны по одному ниже.

### 1. [bug] `Get-ServiceContainerId`: единственный `docker compose ps -q` без
`--all` может дать пустой id на контейнере, попавшем в crash-loop сразу после
`up` — REFUTED

Проверено экспериментально на реальном Docker (28.1.1 / Compose v2.35.1), а не
по памяти о поведении CLI:

1. Поднят одноразовый compose-стек с сервисом, который падает мгновенно
   (`exit 1`) и имеет `restart: unless-stopped` — ровно та политика, что стоит
   у `postgres`/`backend`/`frontend` в `docker-compose.yml` этого проекта (все
   три — `restart: unless-stopped`, проверено `grep restart docker-compose.yml`).
2. Сразу после `docker compose up -d` (без задержки) `docker compose ps -q
   <service>` вернул id, `docker inspect` показал `State.Status=restarting`.
3. 30 замеров подряд с интервалом 0.4 с (≈12 секунд, несколько циклов
   падение→рестарт при мгновенном крэше) — id и state стабильно
   `[id]`/`restarting`, ни разу пусто.
4. `docker ps` (без `-a`) на этом же контейнере тоже показывает его —
   `docker compose ps` (без `--all`) фильтрует по тому же критерию «не
   terminal-stopped», и `restarting` в этот фильтр входит наравне с
   `running`. Пустым `ps -q` становится только когда контейнер в состоянии
   `created`/`exited` без активной политики рестарта, которая немедленно его
   перезапускает.

Вывод: с `restart: unless-stopped` (все три сервиса стека) контейнер, который
крэшится и уходит в рестарт-цикл, НЕ покидает набор, который возвращает
`docker compose ps -q` без `--all` — он либо `running`, либо `restarting`,
никогда не голый `exited`/`created` между попытками. Чтобы finding
подтвердился, нужен был бы сервис без такой restart-политики (или с истёкшим
`on-failure:N`) — в этом проекте таких нет. Код не менялся.

### 3. [minor] `.gitattributes` — новый файл сверх списка брифа — REFUTED

`BOUNDARY` этого fix-раунда — `.` (весь репозиторий), `.gitattributes` внутри
границы. Файл не «побочный», а зависимость двух заявленных deliverable'ов
самой задачи 018: `*.bat` без CRLF ломает многострочные блоки cmd.exe, а
`*.ps1` без CRLF читается Notepad'ом (целевым редактором для
не-разработчика) одной строкой — оба факта уже зафиксированы и обоснованы в
исходном отчёте (раздел «Решения, влияющие на других») в момент реализации,
как требует правило «нетривиальное решение → зафикси сразу». Список файлов в
брифе — подсказка о планируемом объёме, а не контракт: файл, без которого
заявленные `start.bat`/`start.ps1` не работают корректно на целевой
платформе, — легитимная часть их реализации, не scope creep. Код не менялся.

### 4. [minor] `-SyncPasswords` на полностью свежем окружении гоняет лишний
`ALTER ROLE` + рестарт backend — FIXED

Путь воспроизводится буквально (`.env` только что создан + том
`trellis_pgdata` ещё не существовал ⇒ `00-init.sh` заведёт роли с паролями из
ТЕКУЩЕГО `.env`, и `-SyncPasswords` в этом случае гарантированно no-op) —
это не «ложный finding», а реальный, просто низкой цены. Раз путь реален,
рефутация здесь была бы неправомерна; исправлено кодом, а не подавлено.

Исправление НЕ основано на факте «`.env` только что создан» (это отслеживало
бы неправильный сигнал: пользователь мог удалить `.env`, сохранив старый том
`trellis_pgdata` с прежними паролями — тогда пропуск синхронизации был бы уже
багом, а не оптимизацией). Вместо этого перед `docker compose up` добавлена
проверка `docker volume inspect trellis_pgdata` (exit code 0 = том уже
существовал, 1 = том будет создан этим запуском) — `start.ps1:649-650`. Это
не эвристика, а точный факт: если тома не было ДО `up`, то он создаётся
именно этим прогоном, и init-скрипт Postgres заводит роли с паролями из
ТЕКУЩЕГО `.env` — синхронизация в этом и только в этом случае гарантированно
избыточна.

Семантика `docker volume inspect` проверена напрямую (не по памяти):
```
docker volume inspect <несуществующий>  → exit 1
docker volume create <новый> && docker volume inspect <тот же> → exit 0
```
подтверждено в этом окружении (Docker 28.1.1).

`bash .mvp/ci-mirror.sh` — exit 0 (тот же прогон, что и для finding 2 —
изменения в одном файле, один общий прогон верификации).

### 5. [minor] `Stop-WithProblem`: «контейнеры оставлены запущенными» может
быть неточно при отказе `docker compose up` до старта контейнера — FIXED

Воспроизведено на реальном Docker: одноразовый compose-стек с занятым
host-портом (`127.0.0.1:15999` уже слушал `python3 -m http.server`) —
`docker compose up -d` вернул exit 1, контейнер при этом реально создан
(`docker compose ps -a` показывает `STATUS: Created`), но `docker compose ps
-q` (без `--all`, то же, что использует скрипт) вернул пусто — то есть
формулировка «контейнеры оставлены **запущенными**» была бы неточна именно в
этой (уже отдельно обрабатываемой скриптом) ветке отказа по занятому порту, и
шире — в любом отказе `docker compose up` до фактического старта контейнера.

Переформулировано без утверждения «запущены»: `'Что успело подняться — не
тронуто: посмотреть состояние и журналы можно'` / `'командами docker compose
ps и docker compose logs, а остановить всё: docker compose down'` —
формулировка верна независимо от того, реально ли что-то запущено, создано
без старта, или отказ произошёл уже после полного успешного `up` (обычный
случай — таймаут healthcheck/crash-loop на шаге 4, где контейнеры
действительно бегут).

`bash .mvp/ci-mirror.sh` — exit 0 (тот же общий прогон).
