# Task 005 — слой данных ядра: пул, миграции, lifecycle

## Task

Реализовать слой данных ядра backend'а: пул соединений под ролью приложения,
миграции схемы прогресса и их прогон при старте, корректное закрытие пула на
всех путях завершения.

Домен прогресса (API, статусы, согласование при обновлении курса) — задача 007.
Здесь только фундамент: подключение, схема в БД, жизненный цикл.

### Требования

1. **`services/backend/src/db/pool.ts`** — пул `pg` под ролью приложения:
   - строка подключения — `DATABASE_URL` из конфига (роль `trellis_app`,
     `search_path = core`)
   - **`SANDBOX_DATABASE_URL` здесь не используется никогда** — песочница живёт
     отдельной реализацией (задача 008); не заводи «универсальный» пул с
     параметром роли
   - разумные лимиты пула и таймауты подключения; ошибка подключения при старте
     — внятное сообщение, а не стек `ECONNREFUSED` без контекста
   - тонкая обёртка `query`/`withTransaction` (BEGIN/COMMIT/ROLLBACK с
     обязательным release клиента в `finally`) — без самодельного ORM

2. **`services/backend/migrations/001_progress.sql`** — схема прогресса в схеме
   `core` (сама схема и роли уже созданы init-скриптами Postgres из задачи 002;
   миграция их НЕ создаёт и `CREATE ROLE` не делает):
   - `core.lesson_progress`:
     `course_id text not null`, `lesson_id text not null`,
     `status text not null check (status in ('completed'))`,
     `course_version text`, `completed_at timestamptz not null default now()`,
     `updated_at timestamptz not null default now()`,
     первичный ключ `(course_id, lesson_id)`
   - Обоснование модели (следуй ей, не изобретай свою): статус урока —
     «не начат / пройден», история попыток не хранится, поэтому строка есть
     только у пройденного урока. Прогресс курса, которого нет локально
     (импорт), хранится в этой же таблице — **никаких внешних ключей на курсы**,
     курсы это файлы, не строки в БД.
   - `core.schema_migrations`: `version text primary key`,
     `applied_at timestamptz not null default now()`

3. **`services/backend/src/db/migrate.ts`** — прогон миграций при старте:
   - читает `migrations/*.sql` в лексикографическом порядке, применяет
     непринятые, каждую — **в транзакции**, с записью в `core.schema_migrations`
   - защита от параллельного прогона: `pg_advisory_lock` с фиксированным
     ключом (два инстанса/перезапуска не должны драться за миграции)
   - уже применённые пропускаются; несовпадение набора файлов и записей в
     таблице (файл исчез) — внятная ошибка, не тихое продолжение
   - вызывается при старте до того, как API начнёт отвечать

4. **`services/backend/src/lifecycle.ts`** — корректное завершение:
   - закрытие пула на `SIGINT`, `SIGTERM`, `beforeExit` и при ошибке старта —
     ни один путь завершения не оставляет висящих соединений (в контейнере это
     значит, что `docker compose down` не ждёт таймаута)
   - повторный сигнал во время shutdown не запускает процедуру второй раз
   - закрытие идёт через `fastify.close()` → `onClose`-хуки, а не отдельным
     хардкодом в трёх местах
   - незакрывающийся процесс — дефект: убедись, что после закрытия event loop
     пустеет (проверь руками: запуск и `SIGTERM`, процесс завершается с 0)

5. **`/health`** — расширь эндпоинт задачи 003: помимо `status`, отдавай
   состояние БД (например `{"status":"ok","db":"ok"}`); при недоступной БД —
   `503` с `{"status":"degraded","db":"down"}`. На этот эндпоинт завязан
   healthcheck compose: «healthy» должен означать «БД доступна и миграции
   применены».

6. **Тесты** (`node:test`, внутри границы):
   - миграции идемпотентны: повторный прогон на той же БД ничего не ломает и
     не дублирует записи
   - `withTransaction` откатывает при ошибке (клиент возвращается в пул)
   - `/health` отвечает `503`, когда проверка БД падает (подмена зависимости,
     без реальной БД)
   - Тесты, которым нужна настоящая БД, должны **самодиагностироваться**: если
     `DATABASE_URL` не задан/БД недоступна — тест пропускается (`t.skip`) с
     внятной причиной, а не падает. CI поднятой БД не имеет — `npm test` обязан
     оставаться зелёным без Postgres. Как поднять БД локально — `docker compose
     up -d postgres` (см. отчёт задачи 002).

### Готов когда

- `npm run build -w @trellis/backend`, `npm test -w @trellis/backend` зелёные
  **без** поднятого Postgres (тесты с БД — пропущены)
- С поднятым Postgres (`docker compose up -d postgres` + `.env` с паролями):
  миграции применяются, повторный старт не падает, `/health` отвечает
  `{"status":"ok","db":"ok"}` — приложи вывод в отчёт
- `bash .mvp/ci-mirror.sh` завершается кодом 0
- `git status` чист вне `services/backend/**`, корневых
  `package.json`/`package-lock.json` и твоего отчёта

## Общий контракт проекта (соблюдать)

- Node 22, TypeScript ESM (`NodeNext`), strict; тесты — `node:test`.
- `DATABASE_URL` — роль приложения (`trellis_app`, схема `core`).
  `SANDBOX_DATABASE_URL` — роль песочницы, в этом слое не используется.
- Формат прогресса и формат курса — разные сущности; здесь нет ни одного знания
  о структуре курса, кроме строковых id.

## Project invariants

Полный список — `.mvp/invariants.md`. Критичное здесь:

- Прогресс привязан к стабильным id модулей/уроков, никогда к индексам/названиям.
- Данные прогресса — только в Postgres с именованным volume; пересоздание
  контейнеров не теряет данные (миграции обязаны быть повторно-безопасными).
- Запросы ядра выполняются только от роли приложения; sandbox-роль — только для
  песочницы.
- Backend слушает только localhost; внешних сервисов нет.
