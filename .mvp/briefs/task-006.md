# Task 006 — формат контент-пакета и загрузчик курсов

## Task

Реализовать формат контент-пакета и его загрузку: JSON-схема `manifest.yaml`,
загрузчик директории `courses/` с валидацией **до показа**, чтение
Markdown-уроков, реестр курсов в памяти и явное пересканирование.

Это контракт, от которого зависят прогресс (007), практика (009) и пилотный
контент-пакет (017). Ядро не знает ни одного конкретного курса: никаких
названий модулей/уроков в коде.

### Формат пакета (контракт, менять нельзя)

Каждый курс — поддиректория `courses/<dir>/` с `manifest.yaml` в корне.
Схема манифеста (значения — дословно):

```yaml
id: sql-basics                 # стабильный id курса: ^[a-z0-9][a-z0-9-]{1,63}$
version: 1.0.0                 # semver, строка
title: Основы SQL
description: Короткое описание  # опционально
sandboxes:                     # опционально; объявляемые курсом песочницы
  - id: main                   # стабильный id в пределах курса
    type: postgres             # enum; пока единственное значение
    seed:                      # опционально; пути относительно корня пакета
      - sandbox/01-schema.sql
      - sandbox/02-data.sql
modules:
  - id: intro                  # стабильный id модуля
    title: Введение
    lessons:
      - id: what-is-sql        # стабильный id урока
        title: Что такое SQL
        content: lessons/what-is-sql.md   # опционально; путь к Markdown
        quiz:                             # опционально
          question: Что делает SELECT?
          options:
            - id: a
              text: Читает данные
              correct: true
            - id: b
              text: Удаляет таблицу
              explanation: Удаление таблицы — это DROP TABLE.
        practice:                         # опционально
          sandbox: main                   # ссылка на sandboxes[].id
          prompt: Выведите всех студентов
          check: SELECT count(*) = 3 FROM students   # опционально
```

Правила формата:

- `id` модуля и урока — стабильные: прогресс привязан к ним, не к индексам и не
  к названиям (инвариант). В пределах курса id уроков уникальны глобально (не
  только внутри модуля), id модулей уникальны.
- Урок обязан нести хотя бы одно из: `content`, `quiz`, `practice`.
- `quiz.options`: минимум 2 варианта, **ровно один** с `correct: true`;
  у неверных вариантов `explanation` обязателен (бизнес-требование: при
  неверном ответе объясняем, почему он неверен); у верного — опционален.
  `correct` у остальных отсутствует или `false`.
- `practice.check` — SQL, который по контракту возвращает **одну строку с одним
  boolean**; проверять сам SQL на этапе валидации не нужно, но поле обязано быть
  непустой строкой, если присутствует. Задание без `check` засчитывается
  самоотметкой.
- `practice.sandbox` обязан ссылаться на объявленный `sandboxes[].id`.
- Неизвестные поля запрещены (`additionalProperties: false`) — опечатка в
  манифесте должна ловиться, а не молча игнорироваться.

### Требования к реализации

1. **`services/backend/src/courses/manifest.schema.json`** — JSON Schema
   (draft 2020-12), описывающая формат выше. Схема — данные, не код.

2. **`services/backend/src/courses/validate.ts`** — валидация манифеста:
   - структурная по JSON-схеме (используй `ajv`, при необходимости
     `ajv-formats`; YAML разбирай через `yaml`)
   - семантические проверки, которые схема выразить не может:
     уникальность id модулей/уроков/вариантов/песочниц; ровно один верный
     вариант квиза; `explanation` у неверных вариантов; ссылка
     `practice.sandbox` разрешается; урок не пустой; пути `content` и
     `seed[]` не выходят за пределы директории пакета (никаких `..`,
     абсолютных путей и симлинков наружу) и указывают на существующие файлы
   - результат — **дискриминированный результат** (`{ ok: true, course }` /
     `{ ok: false, errors }`), не исключение: один битый курс не должен ронять
     старт приложения
   - все ошибки собираются списком с указанием пути в манифесте
     (`modules[1].lessons[0].quiz.options`), а не «первая и до свидания»

3. **`services/backend/src/courses/loader.ts`** — загрузка одного пакета и
   сканирование `COURSES_DIR`:
   - читает `manifest.yaml`, валидирует, читает Markdown-файлы уроков
     (содержимое урока отдаётся как есть — рендер на стороне frontend)
   - отсутствие директории `COURSES_DIR` — не ошибка, а «курсов нет»
   - невалидный курс не загружается, но фиксируется с причиной (её должен уметь
     показать API/логи) — «валидация до показа» из инвариантов

4. **`services/backend/src/courses/registry.ts`** — реестр в памяти:
   - `list()` — валидные курсы; `get(courseId)`; список отклонённых с причинами
   - `rescan()` — явное пересканирование (перечитать директорию целиком)
   - первичное сканирование — при старте приложения, до готовности API отдавать
     курсы
   - courseId → курс; при дублирующихся `id` в разных директориях — курс
     отклоняется с внятной причиной, а не «последний выигрывает»

5. **`services/backend/src/routes/courses.ts`** — HTTP API (Fastify-плагин):
   - `GET /courses` — список курсов: `id`, `version`, `title`, `description`
   - `GET /courses/:courseId` — структура курса: модули → уроки с id/title и
     флагами наличия `content`/`quiz`/`practice`. **Правильные ответы квиза и
     `check`-запросы наружу не отдаются** — это ответы на задания.
   - `GET /courses/:courseId/lessons/:lessonId` — урок: Markdown-контент, квиз
     без пометки правильного варианта (варианты с id и text), условие практики
     без `check`
   - `POST /courses/rescan` — явное пересканирование, возвращает итог
     (сколько принято/отклонено)
   - отсутствующий курс/урок — `404` с внятным телом
   - Всё под `GET`-контрактом стабильных id: клиент оперирует id, не индексами.

6. **Тесты** (`node:test`, внутри границы) — обязательный минимум:
   - валидный манифест проходит; манифест с двумя `correct: true` — отклоняется;
     неверный вариант без `explanation` — отклоняется; дубль id урока —
     отклоняется; `practice.sandbox` без объявленной песочницы — отклоняется;
     `content: ../../etc/passwd` — отклоняется
   - загрузчик: директории нет → пустой список; один валидный + один битый курс
     → валидный виден, битый в отклонённых с причиной
   - API: `GET /courses/:id/lessons/:lid` не содержит `correct`/`explanation`
     верного варианта и не содержит `check`
   - фикстуры курсов — во временной директории или в `test/fixtures/` внутри
     границы; никакой зависимости от реального `courses/` в репозитории

## Project invariants

Полный список — `.mvp/invariants.md`. Критичное здесь:

- Курс — данные, проходящие валидацию по схеме **до показа** пользователю.
- Прогресс привязан к стабильным id модулей/уроков, никогда к индексам/названиям
  — поэтому id обязаны быть стабильными и уникальными, а валидация обязана это
  гарантировать.
- Контракт check-запроса: одна строка, один boolean; никакой другой логики
  зачёта в ядре.
- Seed- и check-запросы курса исполняются только от sandbox-роли — здесь они
  только читаются и передаются дальше, не исполняются.
